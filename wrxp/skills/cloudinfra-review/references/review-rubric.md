# 단계와 유형에 따른 검토 기준

운영 요청·후속 질의에서 반복되는 판단 공백을 일반화한 기준이다. 특정 조직의 공식 정책이나 특정 담당자의 승인 규정이 아니다. 확인된 현행 조직 가이드와 사용자가 정한 범위를 우선한다.

## 공통 판정

| 확인할 것 | 판단에 충분한 정보 | 적용 범위와 주의점 |
| --- | --- | --- |
| 목적 | 어떤 업무·사용자의 어떤 상태를 바꾸려는지 | “Redis 생성”, “외부 오픈”만으로 목적이 드러나지 않으면 보완한다. |
| 대상 | 환경, 정확한 리소스/서비스명, 찾아갈 수 있는 직접 링크 | 새로 만들 ID나 ARN을 미리 요구하지 않는다. 기존 대상도 정확한 링크로 식별되면 모든 ID를 중복 요구하지 않는다. |
| 변경 계약 | 현재 → 목표, 유지·제외·삭제 범위 | `추가`/`교체`/`이관`/`제거`를 혼동하지 않는다. “기존과 동일”이면 어떤 기준의 어느 부분이 같은지 적는다. |
| 경로·권한 | 해당 작업의 실행 주체, 대상, 필요한 동작, 연결 방향 | 인프라 연결·메타데이터 표시·IAM 권한·앱 설정을 분리한다. “연결해 주세요”가 무엇을 뜻하는지 확인한다. |
| 준비·소유권 | 요청자 선행 작업, 인프라 작업, 다른 팀 결정, 준비 상태 | 표준 셀프서비스 사용과 타 팀 저장소 직접 수정은 다르다. 읽기/검토 권한을 수정 권한으로 해석하지 않는다. |
| 표준·영향 | 표준 구성 적용 가능 여부, 공유 자원·비용·운영 영향 | 모든 요청에 설계 심의나 비용 견적을 강제하지 않는다. 신규/전용 구성·상시 리소스·공유 설정 변경 등 구체적 영향이 있을 때 근거를 요구한다. |
| 일정 | 희망일, 실제 반영 가능 조건, 연동/검증 가능 시점 | 단순 표준 작업에서 기한 공란만으로 제출을 막지 않는다. 배포 연계·외부 테스트·긴급 변경에서 일정 충돌은 필수 보완이다. |
| 완료 | 확인할 동작과 확인 역할, 결과를 남길 곳 | 변경 완료 보고와 실제 사용 가능 확인을 구분한다. 원복은 영향 있는 변경에 맞춰 제안하며 모든 조회 요청에 강제하지 않는다. |

**필수 여부를 정하는 질문:** 이 정보가 없으면 지금 요청한 단계의 대상·정책 판단·구성·적용·완료 확인 중 무엇을 결정할 수 없는가? 구체적으로 답할 수 없으면 기본적으로 권고다. 단, 확인하지 못한 정책을 임의로 충족했다고 단정해서는 안 된다.

**세 가지 함정:** 짧아서 부실하다고 판단하지 않는다. 상세해서 준비됐다고 판단하지 않는다. 댓글이 많거나 반려됐다는 이유만으로 요청자의 잘못으로 판단하지 않는다. 일정 조율·정책 협의·취소·새 범위 추가를 정보 누락 질문과 구분한다.

## 도메인·외부 API·경로 라우팅

작업 요청에서는 다음 관계가 구체적이어야 한다.

`호출자/접근 범위 → 공개 호스트 + 메서드 + 경로 → 기존/신규 대상 서비스 + 전달 경로`

- **공개 경로 계약:** 경로 목록, Exact/Prefix 또는 이에 준하는 매칭 의미, rewrite 여부, 나머지 경로 처리, 기존 호스트 동작. 대소문자·쿼리·슬래시 예외는 실제 계약이나 기존 동작에 영향이 있을 때 확인한다. 추정 엔드포인트를 실제 경로처럼 작성하지 않는다.
- **접근·인증:** 특정 공급사 콜백인지 불특정 공개 API인지 구분한다. 송신 IP 제한 가능 여부와 API 인증의 담당 위치를 확인한다. IP가 유동적이면 부재 자체를 영구 차단 사유로 삼지 말고, 공급사 제약과 가능한 인증 방식을 보안 검토 질문으로 넘긴다. 키·토큰 값은 문안에 쓰지 않고 필요한 헤더명·형식·Secret 식별자만 쓴다.
- **인입 구성:** 희망 호스트와 필수 외부 접근 조건을 제공하고, 조직 표준 경로·TLS 종료·공유 리소스 재사용·WAF 등의 필요성을 담당팀이 판단하도록 한다. ALB/CloudFront/API Gateway를 동시에 만들어야 한다고 단정하지 않는다. 기존 내부 주소를 공개 DNS로 가리키면 외부 연결이 해결된다고 가정하지 않는다.
- **공급사 제약:** 이미 알려진 인증 헤더·본문 전달·요청 크기·응답 제한·재시도가 인입 설정을 좌우하면 포함한다. 새로운 외부 연동에서는 계약 문서 링크와 미확인 항목을 제공한다. 모든 간단한 DNS 변경에 트래픽 연구를 요구하지 않는다.
- **완료:** 실제 호출자의 정상 수신, 인증 실패/비허용 경로 처리, IP 제한을 합의했다면 출발지별 결과, 기존 주요 API의 동작을 확인할 계획을 둔다. 정확한 거부 코드가 계약에 없으면 임의로 401/403/404를 확정하지 않는다.

서버 간 콜백이라는 사실만으로 브라우저 CORS 신청을 추가하지 않는다. 브라우저 경유 요청이 실제로 있는 경우에만 Origin/메서드/헤더를 검토한다. 도메인·TLS 생성과 인증 검증 구현을 혼동하지 않는다.

## 신규 애플리케이션·Worker·배포 환경

Jenkins 유지·GitLab CI 신규 구성·단계적 전환은 [배포 경로와 병존 검토](deployment-paths.md)로 분기한다. 아래 항목은 해당 서비스·환경의 경로가 확인된 범위에서 적용한다.

- 저장소, 배포할 브랜치/모듈, 애플리케이션명, 환경, 신규/기존 런타임 구분.
- 조직이 요구하는 빌드·배포 방식과 이미지/ECR 신규·재사용 여부. 기존 CI를 복제했다는 사실만으로 표준 준수를 인정하지 않는다. 공유 템플릿을 직접 바꾸라는 해결책을 제시하지 않는다.
- 필요한 CPU·메모리·복제 수·스토리지, 서비스 포트, Health 경로. 구체적 자원 산정이 아직 없으면 준비 단계와 산정 책임을 밝히고 표준 초기 사양 제안을 요청할 수 있다.
- 필요한 Secret/Role과 접근 대상. Secret 값을 코드·티켓·이미지에 넣도록 지시하지 않는다. 조직이 지원하는 저장·조회 방식과 해당 실행 주체의 권한을 확인한다.
- DB·캐시·메시징·외부 통신 등 이번 앱에 실제 필요한 의존성. 기존 앱과 동일하다면 근거와 차이만 적는다.
- 런타임·특수 OS·대화형 세션·전용 노드처럼 표준에서 벗어나는 제약은 기획 단계에서 협의한다. 개발 완료를 근거로 특정 인프라 선택을 기정사실화하지 않는다.

기존 앱에 도메인/경로만 추가하는 요청에 이 절 전체를 강제하지 않는다. 이미지·ARN·최종 주소가 아직 생성되지 않았어도 현재 구성 단계에 불필요하다면 차단하지 않는다.

## 권한·Secret·계정

`누가/어떤 실행 주체 → 어느 환경의 어떤 리소스 → 어떤 동작 → 어떤 목적/기간`

- 사람의 계정 권한, 빌드 Runner/CodeBuild Role, 애플리케이션 Role, 대상 리소스 정책을 구분한다.
- 실제 거부된 동작과 대상이 있으면 그 근거를 사용한다. `403`만으로 광범위한 쓰기·관리 권한을 요청하지 않는다.
- Secret 리소스 생성, 조회 권한 부여, 환경변수 주입, 애플리케이션 직접 조회를 구분한다. 서비스별·환경별 매핑은 필요하면 표로 쓴다.
- 이미 생성된 자원의 정확한 이름/ARN을 제공하되 비밀값은 가린다. 오류 로그에도 토큰·개인정보가 있는지 점검한다.
- 표준 권한 신청 경로가 확인되면 그 경로에 맞는 문안을 작성한다. 직접 권한이 없다는 사실을 시스템 미지원으로 단정하지 않는다.

## 네트워크·방화벽·CORS

- 통신: 환경별 출발지 → 목적지, 프로토콜/포트, 방향, NAT/Proxy/CF 등 알려진 경유 구간, 기존 신청/적용 이력.
- 실패 조사: 어느 출발지에서 언제 어떤 명령·요청으로 실패했는지, DNS/TCP/TLS/HTTP 중 확인된 단계와 미확인 단계를 구분한다. 타임아웃을 방화벽 원인으로 확정하지 않는다.
- CORS: 실제 브라우저 Origin의 스킴·호스트·포트, 요청 URL, S3 직접 접근인지 CF 경유인지, 필요한 메서드/헤더/credentials, 추가할 값과 유지할 값.
- `any`/전체 포트/전체 경로는 정확한 업무 요구와 정책 근거가 있을 때만 요청안으로 다룬다. 급하다는 이유로 기본 허용값으로 채우지 않는다.

## 변경·증설·제거·이관

- 현재 값과 목표 값, 변경할 환경, 실제 사용량·장애 근거, 임시/상시 여부.
- 셀프서비스가 있다면 현재 사용자·리소스에서 가능한지 확인한다. 미지원 또는 실패하면 시도한 위치와 오류를 붙여 지원 요청으로 전환한다.
- 공용 자원 분리는 업무 영향과 비용·운영 책임을 함께 설명한다. 캐시, 세션, 영속 저장 등 요구 의미를 구분한다.
- 삭제/이관은 제거·유지 대상과 의존성을 특정하고 요청자 측 선행 정리를 확인한다. 자동 동기화/재생성 등 원인이 남으면 한 번의 삭제를 완료로 보지 않는다. 이 스킬이 직접 삭제하지 않는다.
- 영향 있는 전환은 준비 완료와 실제 반영 신호, 검증, 원복 범위를 구분한다. 과거 환경의 성공을 새 환경의 검증으로 대체하지 않는다.

## 장애·배포 실패 조사

필요한 정보는 발생 시각·환경·영향 범위, 기대/실제 결과, 실행 URL/Job/Pod/요청 식별자, 비밀값을 제외한 원문 오류, 재현 조건, 최근 변경, 이미 확인한 내용이다. 모든 항목이 모든 장애에 필수인 것은 아니다.

“인프라 문제인 것 같다”를 확정 원인으로 고치지 않는다. 애플리케이션 배포·설정·의존성 확인을 했는지 확인하되, 진행 중인 장애의 초기 보고를 완벽한 RCA가 없다는 이유로 막지 않는다. 확인된 영향·시각·대상과 미확인 사항을 먼저 공유하는 초기 조사 문안을 만든다.

## 사례를 근거로 판단할 때

- 실제 재질문이 대상 식별 때문인지, 신규 정책 협의인지, 요청 변경 때문인지 구분한다.
- `반려`는 셀프서비스 안내·담당팀 변경·중복/취소일 수 있다. 요청자가 취소한 것을 담당자의 거절로 바꾸지 않는다.
- `완료`는 설정 반영만 의미할 수 있다. 권한 실패·외부 검증 대기가 남았는지 답글을 확인한다.
- 링크는 근거를 뒷받침하지만 핵심 요구를 대신하지 못한다. 수신자가 읽을 수 없는 자료는 필요한 내용을 본문에 요약하고 접근 한계를 표시한다.
- 오래된 환경·도메인·배포 정책의 예외를 현행 규칙으로 복제하지 않는다. 관측된 관행, 공식 규정, 이번 권고를 구분한다.
