# 조율 규칙

조율자(이 스킬을 실행하는 메인 세션)는 슬롯·큐·묶음·감사·재배정·게시·보고만 합니다. 행 실행과 판정은 작업자가 `worxsales-qa-executor` 규칙대로 합니다. 2026-10-10~10-23의 실제 운영에서 얻은 규칙입니다.

## 조율 스크립트 (`<skill>/scripts/`)

작업 폴더(QA_HOME)에서 실행합니다. `<run_dir>`는 `runs/run-…/`, `<slot>`은 `.slots/app-<port>`입니다.

| 스크립트 | 용도 |
|---|---|
| `qa_queue.py build <run_dir> [--exclude-run DIR] [--only-ids FILE]` | 대상 행으로 `queue.json` 작성. `--only-ids`는 재실행으로 고른 TC ID 목록. 역할·권한 순서로 정렬 |
| `qa_queue.py next <run_dir> <n> [--group=역할/권한]` | 다음 묶음 파일 작성, 경로 출력 |
| `qa_queue.py status <run_dir>` | 완료·대기·판정별 수 |
| `qa_rollout.sh <port> <slot> <build.json>` | 쉬는 슬롯을 그 빌드로 다시 띄우고 DEV 로그인. 슬롯마다 자기 사용자 데이터(`.userdata/<port>`)와 설정 폴더를 씀. 설정 폴더가 없으면 다시 만듦. 종료 코드 4는 사람이 로그인해야 함. 여러 슬롯은 **하나씩** 띄움 |
| `slots.sh status <slot>…` / `slots.sh relogin <slot>…` | 슬롯마다 ready·login·down. relogin은 로그인 화면인 슬롯만 하나씩 DEV로 다시 로그인 |
| `audit_batch.py <run_dir> <batch> [--lanes refresh/lanes.json] [--reject]` | 묶음 감사(아래). `--reject`는 어긋난 행을 `_rejected/<batch>/`로 옮김 |
| `merge_reverify.py <reverify_dir> <run_dir>` | 재검증 결과를 원래 결과에 합침 |
| `publish_pending.py <run_dir> list / mark <ids>` | 게시 안 된 결과 목록, 게시 기록 |
| `prune_builds.sh <desktop repo> <keep worktree>` | 슬롯을 모두 새 빌드로 바꾼 뒤 이전 QA 빌드 worktree(`desktop-dev*`, `desktop-stg*`, 같은 상위 폴더)를 지움 |
| `cdp_tab.mjs <port> list/eval/open/close/shot` | raw CDP. 사용자 브라우저 작업, 앱 bridge 읽기 확인 |

큐 도구는 묶음 파일에 들어간 행을 「이미 배정됨」으로 봅니다. 다시 맡길 행은 새 묶음 파일(예: `batch-011r.json`)로 직접 만듭니다.

## 슬롯 확인

- 일을 맡기기 **직전마다** `slots.sh status`로 모든 슬롯을 봅니다. 세션은 몇 시간 쉬면 끊겨 로그인 화면으로 돌아갑니다.
- 로그인 화면인 슬롯은 `slots.sh relogin`으로 하나씩 DEV에 다시 로그인합니다. 동시에 하면 브라우저 인증이 엇갈립니다.
- 응답하지 않는(down) 슬롯은 그 슬롯만 `qa_rollout.sh`로 다시 띄웁니다. 와일드카드 종료(`pkill`, `killall`)는 쓰지 않습니다.
- Mac 화면이 잠겨 있으면 새로 띄운 앱이 CDP에 응답하지 않을 수 있습니다. 이미 떠 있는 앱은 조작되지만 모달 그림이 갱신되지 않는 사례가 있으니 작업자에게 알립니다.

## 작업자 배치

- 앱 슬롯마다 작업자 한 명입니다. 작업자는 Sonnet 에이전트이고, 프롬프트에 레인 WORKER.md 경로, 묶음 파일, 포트와 슬롯 폴더, 빌드 문자열을 줍니다.
- 영업자 행: 11~20행 묶음. 메뉴가 섞이지 않게 자릅니다.
- 작업자는 자기 묶음의 결과·그림과 자기 `_tmp/<batch>/`만 씁니다. 다른 파일은 지우거나 옮기지 않습니다. 세션 공용 scratch 폴더를 쓰지 않습니다.
- 로그아웃이 필요한 행은 묶음 맨 끝에 둡니다.

## 역할 묶음

- 「역할 전환」 선택은 슬롯마다 따로입니다(2026-10-13 확인). 권한 **부여**는 계정 단위라 바꾸면 모든 슬롯에 걸립니다.
- 순서는 ① 영업자 묶음과 그 재검증 → ② 부여를 바꾸지 않는 역할 묶음(이미 있는 「수정 가능」 부여로 도는 팀장·영업운영 등)을 슬롯마다 병렬 → ③ 부여를 바꿔야 하는 묶음(「조회만」, 권한 관리자 행, 본인 권한 회수가 필요한 행)을 **작업자 한 명이 순차로** 실행합니다. ③은 ②가 모두 끝난 뒤에 시작합니다.
- 역할 묶음 첫 행에는 역할 확인 신호(`role_sanity`)가 있어야 합니다.
- ③의 작업자는 부여·회수할 때마다 레인의 `_grant_log.txt`에 한 줄을 씁니다: `시각 | 묶음 | 사번 이름 | before: [...] | after: [...] | action: ...`. 사번은 권한 관리 부여 창의 [확인]으로 본인 이름이 나온 값만 씁니다.
- ③이 끝나면 조율자가 권한 관리 화면에서 부여가 시작 전과 같은지 직접 확인하고 `_grant_log.txt` 마지막 줄에 「복원 확인」을 적습니다. 부여가 회수된 채로 남은 상태로 레인을 끝내지 않습니다.
- 부여가 화면에 반영되기까지 6~15분이 걸립니다(2026-10-22 기록). 작업자에게 기다리는 동안 홈과 권한 관리를 몇 분 간격으로 오가며 확인하라고 알립니다.

## 진행 감시

- 작업자가 「Monitor로 기다리겠다」, 「sleep 뒤 다시 보겠다」처럼 대기를 말하고 끝나면 다시 깨어나지 않을 수 있습니다. 조율자는 묶음마다 진행을 직접 봅니다: 결과 파일 수와 마지막 수정 시각, `_grant_log.txt`의 마지막 시각, `qa_queue.py status`.
- 15분 넘게 새 결과도 새 부여 기록도 없으면 그 작업자를 SendMessage로 이어서 깨우거나, 남은 행으로 새 묶음을 만들어 다시 맡깁니다. 부여를 바꾸던 작업자가 멈췄으면 먼저 부여 상태를 확인하고 되돌립니다.

## 묶음 감사

묶음이 끝날 때마다 `audit_batch.py <run_dir> <batch> --lanes refresh/lanes.json`을 돌립니다. 확인 항목은 다음과 같습니다.
- 행마다 자기 그림이 있습니다. 같은 차단 화면에 막힌 「실행 불가」·「미구현」 행만 `details.shared_figure_with`로 앞 행의 그림을 함께 쓸 수 있고, 그 행도 화면 확인은 따로 해야 합니다.
- 시작·종료 시각이 행마다 다르고 겹치지 않습니다. 결과 파일 여러 개를 한꺼번에 쓴 흔적이 없습니다.
- `role_before`·`role_after`가 있습니다. 직전 판정이 「문제」였는데 바뀐 행에는 근거 조항(`verdict_reason`)이 있습니다.
- 본인 대상 발송·통화 행에는 `self_recipient`가, 본인 한정 쓰기 행에는 `self_only_check`가 있습니다(감사 스크립트가 보지 않으므로 조율자가 읽어 봅니다).

어긋난 행은 `--reject`로 `_rejected/<batch>/`에 옮기고 새 묶음으로 다시 맡깁니다. 판정 자체는 조율자가 바꾸지 않습니다. 레인 결과를 이전 레인의 그림·결과로 채우지도 않습니다.

## 일시 장애·배포 직후 실패

- 한 화면의 조회가 계속 실패하고 다른 화면은 정상이면, 조율자가 앱 bridge(`cdp_tab.mjs <port> eval worxsales:// …`, 읽기 호출만)나 화면 검색으로 같은 조회를 직접 다시 합니다.
- 지금 정상이면 일시 장애로 보고 해당 결과(장애 때문에 「부분 OK」가 된 행 포함)를 `_superseded/<사유>-<날짜시각>/`로 옮기고 새 묶음으로 다시 맡깁니다. 결과는 지우지 않습니다.
- 지금도 실패하면 서버 측 막힘으로 두고 WORKER.md에 「조율자 확인」 절로 오류 문구·시각을 적어 다음 작업자가 오래 재시도하지 않게 합니다(예: `LEAD_POPULATION_NOT_CONFIGURED`, `CORE_SOURCE_UNAVAILABLE`).

## 재검증

- 대상: 이번 레인에서 「문제」인 행, 직전 판정이 「문제」였는데 바뀐 행.
- 작업자는 Opus 에이전트이고, 지시는 [재검증 작업자 틀](reverify-worker-template.md)로 채워 보냅니다. 규칙은 executor의 `references/reverify.md`입니다. 결과는 `<run_dir>/_reverify/`에 쓰고 `merge_reverify.py`로 합칩니다.
- 재검증 결론이 「시나리오 문제」이면 최종 판정은 「보류-기록」입니다(`merge_reverify.py`가 그렇게 합칩니다). 그 행은 다음 refresh에서 시나리오를 고칩니다.

## 게시

- 감사를 통과한 묶음만 게시합니다. 묶음 몇 개가 쌓이면 `publish_pending.py list`로 모아 executor의 `publish_results.py --only <ids>`로 한 번에 올립니다.
- `publish_pending.py mark`는 게시 명령이 **성공으로 끝난 뒤에만** 실행합니다. 실패하면 mark하지 않고 다시 게시합니다.
- 레인 사이의 덮어쓰기는 오래된 레인부터 게시해 최신 레인이 마지막에 오게 합니다.
- `publish_results.py`는 보관된 블록을 건너뛰고, 액션이 문자열이어도 게시하며, 그림 번호표는 열린 대화상자·팝오버 안에도 그립니다. 그래서 이 이유로 결과를 손으로 고칠 필요가 없습니다.

## 정리

- 레인이 끝나면 레인의 `_tmp/`와 조율자가 만든 임시 파일·임시 브라우저 탭을 지웁니다. 증거 그림은 레인 폴더 바로 아래라 남습니다.
- 슬롯이 쓰는 현재 빌드와 슬롯 설정 폴더는 슬롯을 쓰는 동안 지우지 않습니다. 모든 슬롯을 새 빌드로 바꾼 뒤에 `prune_builds.sh`로 옛 빌드 worktree를 지웁니다.
