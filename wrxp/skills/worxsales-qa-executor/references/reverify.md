# 「문제」 재검증

1차 실행자가 `문제`로 판정한 행과, 직전 판정이 `문제`였는데 이번에 다른 판정이 나온 행은 다른 실행자가 처음부터 다시 확인한다. 2026-10-09 전체 스캔에서는 1차 「문제」 중 상당수가 기능 부재나 문서를 넓게 읽은 판정이었다. 재검증 실행자는 판단이 중요하므로 상위 모델을 쓴다.

## 행마다
1. 시나리오 행, 1차 결과 JSON과 그림, 근거 원천(`sources/`의 화면 문서와 행의 근거 조항, 그 화면의 CBT 범위 절)을 읽는다.
2. 문서가 실제로 요구하는 것을 정한다. 1차 판정이 문서에 없는 요구나 CBT 미제공·제거 기능을 기준으로 했다면 뒤집는다.
3. 행과 같은 역할·데이터 문맥에서 직접 재현한다. 문맥을 맞출 수 없으면 그렇게 적는다.
4. 결론을 하나 고른다.
   - `문제 확정`: 재현됐고 문서가 분명히 다르게 요구한다. 번호 박스 그림을 새로 하나 이상 남긴다.
   - `문제 아님`: 문서대로 동작하거나 1차가 요구를 잘못 읽었다. 올바른 판정(`OK`·`미구현`·`알려진 차이`·`보류-기록`·`실행 불가`)을 함께 정한다.
   - `재현 불가`: 지금은 데이터·환경·역할 때문에 재현할 수 없다. 이유를 적는다.
   - `시나리오 문제`: 행이 원천보다 넓게 기대한다. 원천을 인용한다. 최종 판정은 `보류-기록`이며, 시나리오는 다음 refresh에서 고친다.
5. 행마다 결과 파일 `runs/<레인>/_reverify/<tc_id>.json` 하나를 쓴다. 그림 PNG도 같은 `_reverify/` 폴더에 두고 `figures`에는 파일 이름만 쓴다. 원래 결과 파일(`runs/<레인>/<tc_id>.json`)은 고치지 않는다. 합치기는 조율자가 `merge_reverify.py`로 한다.

| 필드 | 값 |
|---|---|
| tc_id | 행 ID |
| first_verdict | 1차 판정 |
| reverify | `문제 확정` / `문제 아님` / `재현 불가` / `시나리오 문제` |
| final_verdict | 최종 판정(`시나리오 문제`면 `보류-기록`, `재현 불가`면 1차 판정) |
| headline | 30~50자 한 줄 결론 |
| reason | 문서 조항을 인용한 2~4문장 |
| figures | `[{"file", "zoom"?, "caption", "marks"}]` (result-schema와 같은 형식) |
| role_shown | 재현할 때 「역할 전환」에 보인 역할 |
| started_at, ended_at | 실제 `date` 값 |
| reviewer_model | 재검증 작업자 모델(예: `opus`) |

작업자 지시 틀은 QA 한 바퀴 스킬의 `references/reverify-worker-template.md`이다.

## 반영
재검증 결과는 원래 결과에 합쳐 최종 판정만 DB에 반영한다. 원래 결과의 details.verdict_revision에 바뀐 내역을 남긴다. 역할 감사로 이미 「권한 미적용」으로 고친 행은 재검증 대상에서 뺀다.
