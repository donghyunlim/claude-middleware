# Cloud Infra Review

클라우드 인프라팀에 보낼 요청을 **담당자가 티켓 하나로 대상·변경·영향·선행 조건·적용 시점·완료 여부를 판단할 수 있는 문안**으로 만든다. 정보 부족에 엄격하되, 요청 규모와 단계에 맞는 정보만 요구한다. 승인 여부를 예언하거나 특정 담당자의 성격을 흉내 내지 않는다.

## 호출과 작업 범위

- 사용자가 이 스킬을 명시적으로 호출한 경우에만 실행한다. 단순히 “배포해 줘”, “인프라 요청 작성해 줘”라고 했다는 이유로 자동 호출하지 않는다. 다른 스킬·훅·전역 규칙에 선행 조건으로 연결하지 않는다.
- 입력은 요청 초안, Slack 스레드, 설계/배포 문서, 또는 대화의 요구사항이다. 사용자가 명시한 대상과 자료부터 읽는다.
- 기본 산출물은 **검토 결과와 제출 문안**이다. 호출만으로 Slack 게시, 티켓 생성, 배포, 저장소·클라우드 설정 변경을 허가받은 것으로 보지 않는다. 별도 실행 지시가 있으면 검토된 범위와 기존 권한 안에서만 이어간다.

## 검토 절차

### 1. 무엇을 판단받으려는지 고정한다

요청을 `구성/정책 검토`, `구체적 작업`, `장애 조사` 중 적합한 단계로 분류한다. 주된 변경과 종속 작업을 식별하고, 같은 결과를 만드는 작업은 함께 설명한다. 이미 종료된 티켓에 새로운 작업을 붙이거나 다른 담당·일정의 업무가 섞이면 별도 요청으로 나누고 서로 연결한다.

초안의 업무 목적, 환경, 필수 요구, 범위, 일정, 합의 내용을 보존한다. 문장 교정으로 요구를 바꾸지 않는다. “정보가 부족하니 다른 아키텍처로 하겠다”는 결정을 대신 내리지 않는다.

배포 구성·실패·이관 요청이면 [배포 경로와 병존 검토](references/deployment-paths.md)를 읽는다. 서비스·환경별 **현재 지원/실행 경로와 이번 변경 경로**를 구분한다. Jenkins와 GitLab CI가 병존할 수 있으며, 최근의 다른 서비스 사례나 GitLab 저장소·CI 파일의 존재만으로 어느 경로가 정답인지 결정하지 않는다.

### 2. 근거를 먼저 좁혀 확인한다

현재 대화와 제공 자료에서 사실을 채운 뒤, 변경을 좌우하는 공백만 도구로 확인한다. 저장소의 코드는 구현 근거이며 실제 배포 상태나 승인 근거는 아니다. 과거 스레드와 현재 운영 사실도 구분한다.

슬랙 링크가 있으면 부모 메시지와 관련 답글을 읽는다. 권한·문서·코드 접근이 없으면 읽지 못한 범위를 밝히고 확보된 정보로 계속 작성한다. 연결 복구를 위해 다른 채널·개인 세션·자격 증명을 탐색하지 않는다.

조직 관행 확인이 필요한 경우에만 같은 종류·환경·단계의 최근 사례와 공식 가이드를 좁혀 찾는다. 최초 문의와 보완 후 작업 요청을 비교하고, 워크플로 봇도 검색에 포함할 수 있는지 확인한다. 한두 문구나 `반려`/`완료` 표시만으로 원인·성공을 판정하지 않는다. 사용자가 기간 분석을 요청하지 않았다면 두 달 전수조사를 반복하지 않는다.

근거가 충돌하면 같은 환경·시점·리소스인지 확인한다. 현재 권한 있는 담당자의 결정과 공식 가이드를 우선하되, 충돌을 해소하지 못하면 표시한다. 예전 사례의 도메인·배포 도구·보안 예외·버전을 현재의 보편 규정으로 승격하지 않는다.

### 3. 해당하는 기준만 적용한다

[검토 기준](references/review-rubric.md)의 공통 판정과 **이번 유형에 해당하는 부분만** 읽어 적용한다. 장문의 요청도 신청 경로·담당 범위·표준 지원·사전 합의가 틀리면 보완한다. 표준 작업이 짧고 충분하면 그대로 통과시킨다.

각 공백은 다음 중 하나로 다룬다.

- **개발/요청자가 확정할 정보:** API 경로, 업무 요구, 실제 오류, 공급사 조건 등. 확인할 자료가 있으면 먼저 찾고, 없으면 담당 역할과 필요한 답을 구체적으로 제시한다.
- **인프라/보안팀이 판단할 정보:** 표준 인입 방식, 공유 리소스 재사용, 정책 예외 등. 요구와 제약을 갖춘 검토 질문으로 바꾼다. 요청자에게 답을 추측하도록 요구하지 않는다.
- **구성 후 생기는 정보:** 새 리소스 ID, 최종 엔드포인트 등. 요청 시 누락으로 막지 않고 완료 회신 항목으로 둔다.
- **권고 또는 해당 없음:** 없어도 현재 단계의 판단·작업이 가능한 정보. 필수 누락과 섞지 않는다.

질문은 제출 여부·변경 범위·정책·일정을 바꾸는 미확정 사항에 한정해 묶어서 제시한다. 사용자가 질문 없이 초안을 원하면 `[확인 필요: 무엇 / 확인할 역할]`로 남기고 문안을 완성한다. 답이 없어도 가능한 검토와 작성은 끝낸다.

### 4. 판정과 제출 문안을 함께 낸다

판정은 현재 단계에 대해 내린다.

| 판정 | 조건 |
| --- | --- |
| **제출 가능 — 작업 요청** | 현재 단계의 실행 필수 정보가 갖춰졌고 해결되지 않은 범위·정책·준비 모순이 없다. 담당팀의 실제 승인을 뜻하지 않는다. |
| **제출 가능 — 검토 문의** | 목적·대상·제약과 담당팀이 결정할 질문이 명확하다. 실제 작업 준비 완료와 구분한다. |
| **제출 가능 — 조사 요청** | 확인된 영향·대상·현상과 조사할 질문이 명확하다. 원인 확정이나 변경 작업 승인을 뜻하지 않는다. |
| **보완 필요** | 요청자가 제공할 핵심 사실이 없거나 충돌하여 대상·범위·작업을 결정할 수 없다. 보완 전 실행 가능한 문안처럼 표시하지 않는다. |
| **신청 경로 조정** | 현재 근거로 셀프서비스·다른 담당팀·별도 선행 절차가 맞는다. 해당 경로와 막힌 지점을 설명하는 문안을 제공한다. |

출력은 다음 순서로 작성하되, 작은 요청은 짧은 문단으로 합친다.

1. **판정과 핵심 이유:** 지금 제출할 수 있는 단계와 그 판단을 결정한 사실.
2. **필수 보완:** `항목 / 현재 근거 또는 미확인 / 빠지면 못 하는 판단 / 확인할 역할`을 적는다. 권고는 별도로 짧게 쓴다. 근거 없는 점수·승인 확률은 만들지 않는다.
3. **복사해 보낼 문안:** 실제 요청 범위만 포함한 제목과 본문. 대화 밖 수신자도 이해할 수 있게 쓴다. 추정·희망안·검토 질문·빈칸이 확정된 약속처럼 보이지 않게 한다.
4. **남은 결정과 근거:** 필요한 답, 참조 링크와 미확인 범위. 후속 답을 받으면 기존 내용을 재사용해 문안·판정을 갱신한다.

문안은 [작성 예시](references/request-examples.md)를 필요할 때 참고한다. 대괄호가 남은 실행 필수 항목을 숨기고 “바로 보내면 된다”고 하지 않는다. 미확정 일정을 임의로 확약하거나, 전체 공개·권한 확대·신규 리소스 생성을 임시 해결책으로 끼워 넣지 않는다.

### 5. 마지막으로 실행 가능성을 대조한다

처음 보는 담당자가 문안만 읽고 “어느 대상을 왜 어떻게 바꾸며, 무엇이 준비됐고, 누구의 결정이 남았고, 언제 무엇으로 완료를 확인하는가”에 답할 수 있는지 점검한다. 답에 영향을 주지 않는 장식적 항목은 제거한다.

`접수`, `승인`, `구성 완료 보고`, `요청자 검증 완료`는 서로 다른 상태로 유지한다. 외부 연동이면 내부 확인만으로 외부 정상 동작을 주장하지 않는다. 오류 재현·검증 방법을 제시할 수 있지만 이 스킬을 이유로 실제 운영 API를 호출하거나 테스트 메시지를 발송하지 않는다.
