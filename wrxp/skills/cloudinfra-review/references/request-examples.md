# 제출 문안의 크기와 상태 예시

아래 이름·주소는 설명용 가상 값이다. 실제 요청에서 그대로 사용하지 않는다. 문안을 채우기 위한 형식이며 조직의 필수 양식은 아니다.

## 짧은 표준 요청: 필요한 정보가 있으면 확장하지 않는다

입력:

> SAST 연동용 Runner를 기존 표준으로 연결해 주세요. 대상은 `https://git.example.com/team/service-a`, `https://git.example.com/team/service-b`입니다. 빌드/배포 환경 생성은 이번 범위에 없습니다. 사내 가이드의 해당 신청 경로를 확인했습니다. 완료 후 제가 SAST 실행 결과를 확인하겠습니다.

검토: **제출 가능 — 작업 요청**. CPU·메모리·WAF·도메인·롤백 계획을 추가로 요구할 근거가 없다. 목적·대상·표준 경로·검증 역할을 보존해 짧게 다듬는다. 승인 또는 SAST 성공까지 보장하지 않는다.

## 필수 정보가 빠진 외부 콜백: 검토와 실제 개방을 구분한다

입력:

> 기존 atlas-backend에 PartnerBridge 콜백을 받겠습니다. POST와 API Key를 쓰며 새 도메인에서 연동 API만 열어 주세요. 실제 경로와 송신 IP 조건은 미정입니다. 내일까지 부탁드립니다.

검토: 실제 경로가 없어 **보완 필요 — 외부 개방 작업**이다. 인프라팀에 표준 구성을 묻는 **검토 문의**는 다음처럼 작성할 수 있다. 송신 IP가 고정이 아니라는 사실이 확인된 경우에는 미확인과 구분하고 대안 인증 검토를 요청한다.

```text
[DEV / atlas-backend] PartnerBridge 콜백 외부 인입 구성 검토

기존 atlas-backend에 PartnerBridge 서버의 HTTPS POST 콜백을 수신하려고 합니다.
같은 애플리케이션을 사용하며 신규 호스트에는 합의된 콜백 경로만 공개하려고 합니다.

현재 확정된 내용
- 대상 환경/서비스: DEV / atlas-backend
- 호출 주체: PartnerBridge 서버
- 인증 요구: API Key 사용. 검증 위치와 전달 규격은 아래 확인 항목에 포함합니다.

개발/연동 측 확인 필요
- 실제 공개 경로, 매칭 범위와 백엔드 전달 경로
- 송신 IP 고정 여부와 인증 헤더·형식
- 현재 앱 식별 링크, 키 검증 담당과 준비 상태
- 배포 및 공급사 테스트 가능 시점

검토 부탁드리는 사항
- 위 요구를 수용하는 표준 외부 인입 경로와 기존 구성 재사용 가능 여부
- 도메인·인증서·접근 제한 구성을 위해 필요한 보안 신청 대상과 선행 순서

희망 일정은 내일까지입니다. 핵심 정보가 미확정이므로 작업 가능 범위와 일정을
협의하고 싶습니다. 정보가 확정되면 경로·인증·검증 조건을 보완해 실제 반영을 요청하겠습니다.
```

이 문안을 실행 준비가 완료된 작업 신청서라고 표시하지 않는다. 위 정보만으로 도메인·인증서 생성까지 내일 확정 완료하라고 범위를 재배정하지 않는다.

## 상세한 요청도 다른 경로가 맞을 수 있다

입력:

> DEV 서비스의 메모리가 1Gi를 넘으며 OOMKilled가 발생했습니다. 2Gi로 올려 주세요. 서비스와 Pod 링크가 있습니다. 현재 공식 가이드는 이 서비스 소유자가 서비스 콘솔에서 변경하도록 안내하고 있습니다.

검토: **신청 경로 조정**. 콘솔의 직접 변경 절차를 안내한다. 사용자에게 현재 권한이 없는 경우에는 권한/콘솔 지원 요청으로 바꾼다. 명확한 증설 근거가 있어도 인프라팀의 수동 변경을 기본 경로로 만들지 않는다. 직접 설정을 변경하는 것은 별도 실행 지시에 따른다.

## 실행 정보가 충분한 장애 보고: 원인 단정 없이 보낸다

입력:

> PRD Job 412의 14:03 KST 업로드 단계에서 대상 버킷의 HeadObject가 403입니다. Job URL, 실행 Role, 대상 객체 경로와 원문 오류를 확인했습니다. 같은 버킷의 다른 객체 조회는 성공했습니다.

검토: **제출 가능 — 조사 요청**. 동작·대상·차이를 보존하고 해당 실행 주체와 객체 접근 정책 확인을 요청한다. `s3:*`나 관리자 권한 추가를 확정 해결책으로 쓰지 않는다. 조직 가이드가 요구하는 별도 신청 경로가 확인되면 그 경로에 맞춘다.

## 기존 Jenkins 유지와 GitLab CI 시범 전환

**기존 경로 유지:** 담당팀이 `ledger-api`의 Jenkins → 이미지 push → ArgoCD 경로를 계속 지원한다고 확인했고, DEV build 42가 이미지 빌드 전 Gradle 단계에서 실패했다면 Jenkins 조사 요청으로 작성한다. 다른 팀의 신규 GitLab CI 안내를 이 서비스의 전환 의무로 적용하지 않는다.

```text
[DEV / ledger-api] Jenkins build 42의 Gradle 단계 실패 조사 요청

현재 이 서비스는 Jenkins에서 빌드·이미지 push 후 ArgoCD로 배포하며,
담당팀이 해당 경로를 계속 지원한다고 확인했습니다.
이번 요청은 DEV build 42의 Gradle 단계 permission denied 조사입니다.
- 실패 실행: [정확한 build 콘솔 URL]
- 저장소/브랜치 및 대상 앱: [확인된 링크와 ref]
- 확인된 범위: 이미지 빌드 이전 중단. 실제 서비스 영향은 [확인 결과/미확인].

실패한 명령·접근 대상과 실행 환경을 확인하고 필요한 조치를 안내해 주세요.
이번 작업에서는 배포 방식 전환을 요청하지 않습니다.
```

**부분 전환:** DEV만 GitLab CI 시범 적용 중이고 STG/PRD는 Jenkins를 유지한다. 새 Pipeline의 SAST만 통과했고 배포 job과 현재 이미지가 미확인이라면 전환 완료나 기존 Job 종료를 요청하지 않는다. 다음과 같이 검증·전환 조건 문의로 보완한다.

```text
[DEV / ledger-api] GitLab CI 시범 검증 및 기존 Jenkins 전환 조건 검토

DEV만 GitLab CI로 시범 전환하고 STG/PRD는 Jenkins를 유지하려고 합니다.
현재 새 Pipeline의 SAST 성공은 확인했으나 build/push/deploy 실행과
DEV 앱에 적용된 이미지는 미확인입니다.
- 새 Pipeline / 기존 DEV Job / 대상 앱: [각 직접 링크]
- 개발팀 확인: 단계별 실행 결과, 산출물과 적용 버전의 대응, 앱 동작 검증
- 담당팀 판단: 지원 컴포넌트·실행 권한과 전환 절차

같은 DEV 대상에 두 경로가 동시에 반영되지 않도록 전환 경로와
기존 트리거 중지 시점·담당을 협의하고 싶습니다.
새 경로의 실제 배포·앱 검증과 복구 방법을 확인한 뒤 기존 DEV Job의
중지 시점을 정하겠습니다. STG/PRD Jenkins는 유지합니다.
```

신규 GitLab CI 경로의 ECR/Role 생성을 요청하는 준비 단계에는 아직 없는 ARN이나 최종 배포 성공을 필수로 요구하지 않는다. 단계별 판정은 [배포 경로와 병존 검토](deployment-paths.md)를 따른다.

## 영향 있는 작업의 문안 틀

다음 중 해당하는 항목만 사용한다. 빈칸을 채우기 위해 값을 만들지 않는다.

```text
[환경 / 서비스] 변경 결과가 드러나는 제목

목적: [업무 목적과 필요한 결과]
대상: [정확한 리소스명과 직접 링크]
현재 → 요청: [추가/변경/유지/제거 범위]
연결·권한: [실행 주체 → 대상 → 동작, 이번 작업에 필요한 부분]
선행 준비: [완료 근거 / 미완료 항목과 담당]
담당팀 판단 요청: [요구·제약·선택이 필요한 질문]
일정: [희망일 / 실제 반영 가능한 시점과 조건]
확인: [확인 역할, 성공/거부 동작, 결과 회신 위치]
원복: [영향 있는 전환에 해당하는 범위와 협의 사항]
참고: [직접 근거와 관련 티켓]
```

수신 문안에는 검토자의 점수표·개인 평가·불필요한 내부 추론을 붙이지 않는다. 확인되지 않은 내용을 승인·구현·검증 완료처럼 쓰지 않으며 미결 항목의 책임과 다음 행동을 알아볼 수 있게 한다.
