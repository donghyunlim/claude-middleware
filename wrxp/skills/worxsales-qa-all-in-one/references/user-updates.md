# 사용자에게 알리는 내용

## 진행 상황 (실행 중)

- 묶음이 끝날 때마다, 그리고 사용자가 물을 때 한 줄로 알립니다: `레인 <id>: 완료 <n>/<전체> (영업자 a/b, 역할 c/d), 재검증 대기 e, 게시 f`.
- 숫자는 `qa_queue.py status`와 `publish_pending.py list`에서 읽습니다. 추정하지 않습니다.
- 멈춘 작업자, 다시 로그인한 슬롯, 새로 확인한 서버 막힘은 생길 때 바로 알립니다.

## 결과 분류 (회차 끝)

이번 레인과 DB 최신 상태(대상 = 범위 제외가 아닌 행)를 함께 적습니다. 각 묶음은 행 수와 비율을 씁니다.

| 묶음 | 판정 | 뜻 |
|---|---|---|
| 실제 결함 | 문제(재검증 확정) | 개발에 넘길 것. TC ID, headline, 링크 |
| 아직 안 만듦 | 미구현(권한 미적용 포함) | 기획에는 있고 빌드에는 없음 |
| 동작함 | OK, 알려진 차이 | 알려진 차이는 문서가 정책과 다르다고 적은 곳 |
| 일부만 확인 | 부분 OK | 확인 못 한 항목과 이유(`details.unverified`) |
| 보류 | 보류-기록 | 정책 미확정 또는 시나리오 문제 |
| 환경 때문에 못 봄 | 실행 불가 | 사유별 수: 쓰기 범위 밖, 외부 조건(Google·MC·MAGMA·두 번째 사용자), 서버 설정·장애, 데이터 없음, 도구 한계 |

지표는 dashboard-update의 정의를 그대로 씁니다. 구현도 = (OK + 부분 OK + 문제 + 알려진 차이) ÷ 판정 가능(실행 − 실행 불가 − 보류-기록), 무결함률 = (실행 − 문제) ÷ 실행입니다. 이 둘이 핵심이고, 실동작 확인율 = (OK + 부분 OK) ÷ 실행, 미구현율 = 미구현 ÷ 판정 가능을 함께 적습니다.

## 사용자가 풀 수 있는 것

「실행 불가」 행을 사유별로 묶어, 사용자가 해 줄 수 있는 일을 **풀리는 행 수가 많은 순서로** 적습니다. 예를 들면 다음과 같습니다.
1. MatrixCloud 앱 로그인 → 통화 행 n
2. MAGMA DEV 리드 시드 요청(요청서 틀 첨부) → 리드 행 n
3. 새로 쓰기 범위 밖이 된 조작의 허용 여부 → n
4. 두 번째 사용자 계정 → n

조율자가 스스로 만들 수 있는 사전조건([직접 만드는 사전조건](preconditions.md))은 이 목록에 올리지 않고 다음 회차 전에 만듭니다.
