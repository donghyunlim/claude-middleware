- 상태: **스펙 락인 (2026-10-28)**. 구현은 브랜치 `wrxp/ha-absorption`(0.1.74)에 있다. 10절이 구현 기준이고, 그 뒤 시뮬레이션 피드백으로 바뀐 점은 [시뮬레이션 결과](2026-10-28-ha-absorption-sim-results.md)와 CHANGELOG 0.1.74에 있다.
- 대상 저장소: wrxp (작성 당시 v0.1.72)

## 1. 합의된 의도

pstack(poteto-mode)의 강점을 wrxp로 흡수하고, `ha`를 "뭔가 애매하면 이것만 부르면 되는" 마스터 실행어로 만든다. pstack 플러그인 자체는 설치하지 않는다.

### 이미 합의된 결정

| 결정 | 근거 |
|---|---|
| 방향은 wrxp 흡수. wrxp는 사용자 소유이며 유지한다 | 사용자 지시 |
| superpowers는 제거한다 (완료) | 30일 호출 16회, hook 부작용 |
| 마스터 실행어는 `ha`를 확장한다. 질문 레버는 `haq`/`haqq`/`haqqq`를 그대로 쓴다 | 사용자 지시 |
| 질문 분류 규칙 채택: 실행해서 알 수 있는 사실은 묻지 않고 확인하거나 프로토타입으로 결정하고, 취향·제품 판단만 묻는다 | 사용자 동의 |
| 설계 단계 채택. 코드뿐 아니라 글쓰기·기획서에도 적용한다 | 사용자 지시 |
| 버그 수정은 3단계 강도로 흡수한다 (원인 확실 / 원인 불명 / 재발·고위험). 1줄 수정에 전체 절차를 돌리지 않는다 | 사용자 우려 (토큰 낭비) |
| 검증 규칙 1개 추가: 대체물(다른 환경, 목업, 자기 보고)로 확인한 결과와 결론이 불확실한 결과는 통과로 보고하지 않고 한계를 명시한다 | 사용자 동의 |
| 원칙은 리뷰를 거쳐 선별 흡수한다 | 사용자 지시 |
| wrxp 저장소 변경은 6단계 스펙 락인 전까지 작업 브랜치에만 커밋하고, main 병합·푸시는 락인 뒤 사용자가 요청할 때 한다. 구현 커밋마다 새 맥락 검토 에이전트로 검증한다. 예외: 세 스킬 제거 커밋 12c0872는 이미 main에 나갔고 유지한다 | 2026-10-27 사용자 지시 (절차를 건너뛴 병합 지적) |
| 자동 실행 hook은 만들지 않는다. 사용자가 부를 때만 켜진다 | wrxp의 수동적 성격 유지 |
| pstack의 "Just do it" 자율성과 "Never Block on the Human"은 가져오지 않는다 | wrxp 합의 중심 철학, Slack·Notion 연결 환경 |
| 회사 인프라는 플러그인에 포함하고 개인 인프라는 제외한다. 회사 인프라(magma, worxsales MCP, Metabase, Tableau, Slack, Notion 등)는 `ha`와 트랙 파일에 이름으로 적는다. 개인 전용 도구(muffiny 등)는 플러그인 밖 `~/.claude/wrxp/sources.md`에 둔다. 목록에 없는 도구는 실행 시 연결된 MCP를 출처 종류로 분류한다 | wrxp는 사내 공유 플러그인 (5-6 리뷰 중 사용자 지적·보정) |

### 진행 절차 (사용자 합의)

1. 마스터 플랜: 후보군을 최대한 펼치고 대략적인 배치를 정한다 (완료)
2. 스킬을 하나씩 리뷰한다 (완료)
3. 완성된 wrxp 상태를 보고 뺄 것은 빼고 더할 것은 더한다 ← **지금** (세 스킬 제거만 완료)
4. 상황을 가정하고 에이전트로 시뮬레이션을 돌린다
5. 시뮬레이션 피드백을 사용자와 함께 리뷰한다
6. 최종 리뷰 후 스펙을 락인한다

## 2. 목표 구조 (초안)

```
/ha [요청]        마스터 실행어. 질문 상한 0 (실행 통제 게이트는 예외)
/haq  [요청]      같은 엔진 + 질문 상한 4, 1라운드
/haqq [요청]      같은 엔진 + 표준 탐색 질문
/haqqq [요청]     같은 엔진 + 깊은 탐색 질문
```

`ha` 엔진의 흐름:

1. **분류**: 요청을 트랙 하나로 분류한다. 맞는 트랙이 없으면 맞춤 절차를 설계한다.
2. **강도 결정**: S(직접 처리) / M(핵심 단계만) / L(전체 절차). 강도가 비용을 결정한다.
3. **질문 판정**: 기존 QuestionGate에 질문 분류 규칙을 더한다. 질문 상한은 q 레벨이 정한다.
4. **설계**: 산출물의 구조를 먼저 정하고, M 이상이면 구조안 2~3개를 비교한다.
5. **실행**: 트랙 절차를 따른다. 구현 위임은 `code-delegation` 계약을 따른다.
6. **검증**: 성공 조건별 근거. 대체물 확인은 통과가 아니다.
7. **보고**: 주장마다 근거 또는 "측정/추정/추측" 표시를 단다.

파일 배치 초안:

```
wrxp/skills/ha/SKILL.md                 엔진 본체 (분류, 강도, 흐름)
wrxp/skills/ha/references/tracks/*.md   트랙별 절차 (필요할 때만 읽음)
wrxp/skills/ha/references/questioning.md   기존 + 질문 분류 규칙
wrxp/skills/ha/references/verification.md  기존 + 대체물 규칙
wrxp/skills/ha/references/model-routing.md 기존 유지
wrxp/shared/principles.md               선별·통합한 원칙 (트랙이 필요한 원칙만 가리킴)
```

### 트랙 후보

| 트랙 | 출처 | S / M / L 강도 차이 (초안) |
|---|---|---|
| 조사 (how/why/어디에 둘지) | Investigation, `how`, `why` | S: 직접 읽고 답 / M: 근거 인용 / L: Slack·Notion·muffiny 등 MCP 근거까지 |
| 버그 | Bug fix | S: 원인 확실, 고치고 1회 확인 / M: 직접 재현 + 가설 좁히기, 같은 전제 2회 실패 시 전제 검증 / L: 위임, 실패 재현 선커밋 |
| 기능 | Feature | S: 직접 구현 / M: 데이터 형태 먼저 + 위임 / L: 설계안 비교 + 병렬 점검표 + worktree 분리 |
| 리팩터링 | Refactoring | 동작 보존 확인 방법을 먼저 정한다 |
| 기획서·글쓰기 | 신규 (architect 아이디어 일반화) | 독자, 핵심 메시지 한 문장, 목차를 먼저 정하고 구조안을 비교 |
| 데이터·수치 | Perf issue, `benchmark-checklist`, Explain the Number | 수치를 제한하는 요인과 다른 것을 잰 가능성을 배제한 뒤 보고 |
| 프로토타입 | Prototype | 질문 분류에서 "실행하면 알 수 있는 사실"일 때 호출 |
| 맞춤 절차 | `figure-it-out` | 맞는 트랙이 없을 때 절차 자체를 먼저 설계 |

## 5. 2단계 리뷰 기록

### 5-1. ha 엔진 뼈대 (확정: 아래 "리뷰에서 정할 것" 4개 모두 추천안 채택)

현재 `ha`는 CAPABILITY_RESOLVE → OBSERVE → IDENTIFY_DECISIONS → QUESTION_GATE → COMMIT_INTENT → ROUTE_AND_EXECUTE → VERIFY 상태 흐름이다. 질문 판정과 DAG 실행은 이미 단단하므로 유지하고, 아래 세 상태를 끼워 넣는다.

```text
CAPABILITY_RESOLVE        (S에서는 생략)
  → OBSERVE
  → CLASSIFY              [신규] 트랙 + 강도(S/M/L)
  → IDENTIFY_DECISIONS
  → QUESTION_GATE
      ├─ 실행하면 알 수 있는 사실 → PROBE [신규] → IDENTIFY_DECISIONS
      ├─ must_ask / 예산 내 decision_quality → 질문 → IDENTIFY_DECISIONS
      └─ 전송할 질문 없음
  → COMMIT_INTENT
  → DESIGN                [신규] M 이상. 산출물 구조 먼저, 필요 시 구조안 2~3개 비교
  → ROUTE_AND_EXECUTE     트랙 절차를 따름
  → VERIFY                대체물 확인은 통과 아님
  → 최종 출력             track, tier, 주장별 근거 표시 추가
```

**CLASSIFY: 트랙**
- 트랙 하나를 주 트랙으로 고른다. 요청이 여러 트랙에 걸치면 주 트랙 하나와 보조 트랙을 정한다.
- 맞는 트랙이 없으면 맞춤 절차 트랙(절차 자체를 먼저 설계)으로 간다.
- 서로 독립된 목표가 여러 개면 목표별로 나누어 각각 분류한다.

**CLASSIFY: 강도**

| 강도 | 조건 (하나라도 해당하면 그 강도 이상) | 적용 |
|---|---|---|
| S | 결과가 뻔하고, 되돌리기 쉽고, 산출물 하나에 국한되며, 사용자 판단이 필요 없다 | 트랙 참조를 읽지 않는다. 설계·위임·별도 검증 없이 처리하고 실제 결과를 1회 확인한다 |
| M | 여러 파일·산출물 구조 판단이 필요하거나, 원인을 모르거나, 기존 구조에 새 요구를 넣는다. 되돌릴 수는 있다 | 트랙 참조를 읽고 핵심 단계만 수행한다. 구조를 먼저 정하고, 대안 비교는 구조가 둘 이상 가능할 때만 한다. 위임은 `code-delegation` 조건을 충족할 때만 한다 |
| L | 되돌리기 어렵거나(데이터, 외부 공개, 계약 변경), 여러 모듈 계약에 걸치거나, 재발 버그거나, 여러 단계에 걸쳐 사용자 합의가 핵심이다 | 트랙 전체 절차를 따르고 `staged-development` 정본을 사용한다. 구조안 비교는 필수다 |

- 강도 조정: 실행 중 증거가 현재 강도를 넘으면 한 단계 올리고 한 줄로 보고한다. 같은 전제의 수정이 두 번 실패하면 자동으로 한 단계 올린다. 생각보다 단순하면 내린다.
- 질문 레버(q)와 강도는 독립이다. `haqqq`라고 L이 되지 않고, `ha`라고 S가 되지 않는다.

**PROBE**
- QUESTION_GATE에서 후보의 답이 "실행해 보면 관찰할 수 있는 사실"(동작, 출력, 성능, 화면 배치 등)이면 사용자에게 묻지 않는다.
- 가장 작은 실험이나 프로토타입으로 확인하고, 그 결과를 증거로 IDENTIFY_DECISIONS에 돌려보낸다.
- 조사만 하는 요청이면 프로토타입을 만들지 않고 증거로 답한다.
- 취향·제품 판단·승인처럼 실험으로 정할 수 없는 것만 질문 후보로 남는다.

**최종 출력 추가 항목**
- `track`, `tier`
- 주장마다 근거를 붙이거나 측정/추정/추측을 표시한다.

**리뷰에서 정할 것**
1. 강도 결정 권한: 에이전트가 정하고 시작할 때 "버그 트랙, M으로 진행합니다"처럼 한 줄 보고만 할지. L은 `staged-development`의 아웃라인 합의가 사실상 확인 절차가 되므로 별도 확인을 두지 않는 안을 추천한다.
2. S 빠른 경로에서 CAPABILITY_RESOLVE와 YAML 정리(Observation, CommittedIntent)를 생략해도 되는지.
3. PROBE에 비용 상한을 둘지 (예: S·M에서는 실험 1회, 그래도 불명확하면 질문으로 전환).
4. `ha` 설명(description)을 "어떤 절차가 맞을지 애매하면 이것을 쓴다"로 바꿔 마스터 진입점으로 삼는다.

### 5-2. 질문 분류 규칙 (확정: 추가안 6개 그대로 채택)

**현재 상태:** `references/questioning.md`는 이미 "파일·문서·도구로 확인할 수 있는 사실은 묻지 않는다"(`answer_owner: evidence`)를 갖고 있다. 빠진 것은 **실행해야만 관찰되는 사실**이다. 화면 배치가 넘치는지, 쿼리가 빨라지는지, 두 방식 중 어느 쪽이 실제로 동작하는지는 파일을 읽어도 안 나온다. 지금 규칙에서는 이런 결정이 `user`로 분류되어 "어느 방식으로 할까요?" 질문이 되기 쉽다.

**추가안**

1. `answer_owner`에 `experiment` 값을 추가한다. 실행·측정·렌더링·작은 시안으로 관찰할 수 있는 사실이다. `experiment` 후보는 질문하지 않고 PROBE로 보낸다.
2. 판별 문장 하나를 둔다. "이 답은 사용자가 말해 줘야만 알 수 있는가, 아니면 해 보면 관찰되는가?" 해 보면 관찰되면 `experiment`, 말해 줘야만 알면 `user`다.
3. PROBE 비용 상한(5-1에서 확정): S·M은 실험 1회, L은 정본 기획서의 작업 상한을 따른다. 결과가 여전히 불명확하면 실험 결과를 근거로 첨부해 질문 후보로 전환한다.
4. PROBE 안전 경계: 실험은 읽기 전용이거나 버릴 수 있는 곳(스크래치 폴더, 임시 브랜치)에서만 한다. 외부 시스템 변경, 메시지 발송, 승인이 필요한 실험은 PROBE가 아니라 `must_ask`다.
5. 시안을 붙인 질문: 취향 판단(레이아웃, 문체, 문서 구조 등)이라서 결국 물어야 하는 경우, M 이상에서는 추상적인 질문 대신 짧은 시안 2~3개를 붙여 묻는다. S에서는 붙이지 않는다.
6. 기본값 보고 강화: `none` 프리셋 등으로 `decision_quality` 질문을 건너뛰고 기본값을 적용했으면, 결과에 적용한 기본값과 "다르게 원하면 무엇이라고 말하면 되는지"를 평이한 문장으로 적는다.

**제외한 pstack 요소**
- "전면 자율 위임이면 묻지 않고 결정한 뒤 보고": wrxp는 질문 레버(q)로 질문 깊이를 사용자가 고르므로 필요 없다.

**예시 추가안**

| 요청 속 결정 | 분류 | 처리 |
|---|---|---|
| 이 인덱스를 추가하면 쿼리가 빨라질까? | `experiment` | 실행 계획(EXPLAIN)이나 측정으로 확인 |
| 이 표를 모바일 폭에서 가로 스크롤 없이 보여 줄 수 있나? | `experiment` | 렌더링해서 확인 |
| 두 구현 방식 중 기존 테스트를 깨지 않는 쪽은? | `experiment` | 둘 다 짧게 돌려 보고 결정 |
| 보고서를 결론부터 쓸지, 경과 순으로 쓸지 | `user` (`decision_quality`, 독자에 따라 달라짐) | M 이상이면 목차 시안 두 개를 붙여 질문 |
| 버튼 색을 브랜드 색으로 할지 회색으로 할지 | `user` (취향) | 위험이 낮으면 기본값 적용 후 바꾸는 방법 안내 |
| 이 결과를 Slack 채널에 올려도 되나? | `must_ask` | 외부 발송이므로 즉시 확인 |

### 5-3. 설계 단계 DESIGN (확정: 3가지 결정 모두 추천안 채택)

**출처:** pstack `architect` (Ground → Sketch → Agree → Implement → Scrap). 여러 모델이 병렬로 설계안을 만드는 `arena` 부분은 비용 때문에 빼고, 메인 에이전트가 한 문맥에서 수행한다. 코드 전용 용어(타입, 시그니처)는 산출물 종류별로 일반화한다.

**적용 강도:** S는 생략한다. M과 L에서 수행한다.

**단계**

| 단계 | 내용 | M | L |
|---|---|---|---|
| D1 파악 | 산출물이 들어갈 기존 맥락을 파악한다(기존 코드, 기존 문서, 이전 결정). 이름만 아는 것은 파악이 아니다 | 관련 부분만 | 조사 트랙(how/why) 수준 |
| D2 사용 장면 먼저 | 산출물을 쓰는 사람이 그것으로 무엇을 하는지 한두 줄로 먼저 쓴다 | 필수 | 필수 |
| D3 뼈대 | 내용을 채우기 전에 구조만 만든다 | 필수 | 필수 |
| D4 대안 비교 | 전체 모양이 다른 뼈대 2개 이상을 비교한다. 한 뼈대 안의 부분 수정은 대안이 아니다 | 구조가 둘 이상 가능할 때만 | 필수 |
| D5 합의 | 뼈대를 사용자와 맞춘다 | 한 줄 보고 후 진행 (멈추지 않음). 취향 판단이 걸리면 5-2의 시안 붙인 질문 | `staged-development` 아웃라인 합의에 포함 |
| D6 뼈대 기준 실행 | 뼈대가 계약이다. 실행 중 뼈대에서 벗어나면 조용히 흡수하지 말고 기록하고 뼈대를 갱신한다 | 필수 | 필수, 정본에 기록 |
| D7 폐기 판단 | 같은 모양의 우회나 예외 처리가 두 번 이상 반복되면 뼈대가 틀린 것이다. 덧대지 말고 D1부터 다시 설계한다. 새 뼈대는 이전보다 작게 시작한다 | 필수 | 필수 |

**산출물별 D2·D3 내용**

| 산출물 | D2 사용 장면 | D3 뼈대 |
|---|---|---|
| 코드 | 이 코드를 호출하는 쪽 코드를 먼저 쓴다 | 데이터 형태, 함수·모듈 경계, 빈 본문 |
| 기획서 | 이 문서를 읽고 누가 무엇을 결정하는가 | 문제, 성공 조건, 범위와 제외 범위, 결정이 필요한 항목 |
| 보고서·공유 글 | 독자가 읽은 뒤 무엇을 해야 하는가 | 핵심 메시지 한 문장, 섹션 제목과 섹션별 한 줄 요지 |
| 슬라이드 | 발표 후 청중에게 남길 결론 | 장마다 한 줄 헤드라인 |
| 데이터 분석 | 이 수치로 어떤 결정을 하는가 | 지표 정의, 분해 구조, 비교 기준 |

**D4 비교 기준**
- 받는 사람의 부담: 읽는 사람이나 호출하는 사람이 알아야 할 것이 적은 쪽
- 표면 대비 깊이: 작은 표면 뒤에 더 많은 복잡성을 숨기는 쪽
- 변경 안전성: 한 곳을 고쳤을 때 다른 곳이 함께 맞는 쪽
- 코드는 pstack `architect`의 설계 경고 신호 목록(`design-red-flags.md`)을 기능 트랙 리뷰 때 함께 검토한다

**제외한 pstack 요소**
- 여러 모델 병렬 설계(`arena`)와 적대적 검토(`interrogate`): 비용. 필요하면 애매 항목 리뷰에서 L 고위험 한정으로 다시 본다.
- "기본은 사람 확인 없이 진행": M은 진행하되 한 줄 보고, L은 합의를 거친다.

**리뷰에서 정할 것**
1. M에서 뼈대를 한 줄 보고만 하고 멈추지 않고 진행해도 되는지
2. D4 대안 비교를 M은 조건부, L은 필수로 두는 것
3. 산출물별 D2·D3 표에 빠진 산출물이 있는지 (예: 메시지 초안, 회의 자료, 스킬 문서)

### 5-4. 버그 트랙 (확정: M 가설 3라운드 상한, S에는 패턴 검색 없음, L 이력 조사는 git 기본·사고 성격일 때만 Slack·Notion·muffiny 추가)

**출처:** pstack Bug fix 플레이북, 원칙 Fix Root Causes·Attack the Premise, `tdd` 스킬, wrxp `staged-development`의 "원인 불명 버그는 최소 실험부터".
**파일:** `ha/references/tracks/bug.md` (S에서는 읽지 않음)

**강도 판정**

| 강도 | 조건 |
|---|---|
| S | 원인이 확실하다. 오류 메시지나 스택이 고칠 곳을 직접 가리키고, 수정이 국소적이다 |
| M | 원인을 모른다. 또는 증상과 원인 위치가 다를 수 있다 |
| L | 재발한 버그, 여러 모듈에 걸친 버그, 데이터 손상·보안·운영 장애, 또는 M에서 상향된 경우 |

**S: 바로 고치기**
1. 고친다.
2. 원래 증상이 나던 경로로 1회 확인한다.

**M: 원인 찾고 고치기**
1. **직접 재현한다.** 실제 경로에서 재현한다. 사용자에게 재현을 부탁하는 것은 도구로 닿을 수 없는 구체적 이유가 있을 때만이다.
2. **가설을 좁힌다.** 가설 후보를 적고, 남은 가능성을 가장 많이 가르는 관찰부터 한다. 상태를 모르면 추측하지 말고 로그나 계측을 넣어 읽는다.
3. **근본 원인을 확정한다.** 증상이 보인 곳이 아니라 처음 잘못된 지점을 찾는다. 판별 질문은 "증상을 낸 상태가 정당한 상태인가?"다. 정당하면 그 상태를 처리하지 못한 코드가 원인이고, 정당하지 않으면 그 상태를 만든 곳이 원인이다.
4. **증거가 정당화하는 최소 수정만 한다.** "혹시 몰라" 넣는 방어 코드는 가설일 뿐 수정이 아니다. 반박된 가설 때문에 넣은 코드는 되돌린다.
5. **같은 재현 경로로 확인한다.** 다른 환경에서의 확인은 통과가 아니다.
6. **회귀 테스트는 싼 경우만 넣는다.** 로컬에서 빠르게 돌릴 테스트 경로가 분명할 때만 실패 → 통과를 확인하는 테스트를 추가한다. 통합 테스트가 필요하거나 경로가 불분명하면 생략하고 이유를 남긴다.

**M 비용 장치**
- 가설 검증은 3라운드까지다. 3라운드 안에 원인이 확정되지 않으면 지금까지의 근거를 한 줄로 보고하고 L로 상향한다.
- 같은 전제의 수정이 두 번 실패하면 즉시 멈추고 그 전제를 한 문장으로 적어 직접 검증한다(Attack the Premise). 검증 결과와 함께 L로 상향한다.
- 새 증거 없이 같은 시도를 반복하지 않는다(기존 ha 규칙).

**L: 원인 추적과 재발 방지**
- M의 1~6을 모두 수행하고 다음을 더한다.
- **이력 조사:** 재발이나 회귀면 git 이력과 Slack·Notion 등의 장애 기록에서 언제, 왜 바뀌었는지 찾는다.
- **설계:** 수정이 함수·모듈 경계를 넘으면 DESIGN 단계를 거친다.
- **위임:** 수정 구현은 `code-delegation` 계약으로 위임할 수 있다.
- **커밋 순서:** 실패하는 재현 테스트를 수정보다 먼저 커밋해서, 이력만 봐도 "빨강 → 초록"이 보이게 한다.
- **같은 패턴 전체 수정:** 같은 결함 패턴이 다른 곳에도 있는지 찾아 함께 고친다.
- **신호 제안:** 원인을 찾는 데 오래 걸렸다면, 다음에는 처음부터 보였을 값싼 상시 신호(로그, 경고, 검사)를 제안한다.

**보고 형식**
무엇이 깨졌는지, 근본 원인, 수정 내용, 검증 방법을 적는다. 결정적인 실패 출력과 통과 출력을 짧게 인용한다.

**제외한 pstack 요소**
- 모든 버그 수정의 서브에이전트 위임 의무: L에서만 선택적으로 위임한다.
- 매번 PR 열기: 커밋·PR은 사용자 지시를 따른다.
- 원인 불명 버그마다 여러 모델 설계 비교(`architect`): 단일 문맥 DESIGN으로 대체한다.

**리뷰에서 정할 것**
1. M 가설 검증 상한을 3라운드로 둘지
2. S에도 "같은 패턴이 다른 곳에 있는지 검색 1회"를 넣을지 (비용이 거의 없지만 S의 가벼움이 줄어듦)
3. L에서 이력 조사에 Slack·Notion·muffiny 검색까지 기본으로 포함할지, git 이력만 기본으로 할지

### 5-5. 기능 트랙 (확정: 3가지 결정 모두 추천안 채택)

**출처:** pstack Feature 플레이북, `architect`의 설계 경고 신호(`design-red-flags.md`), 원칙 Model the Domain·Foundational Thinking·Test Behavior Not Implementation·Sequence Verifiable Units·Separate Before Serializing, poteto-mode의 코멘트 규칙, wrxp `staged-development`·`code-delegation`.
**파일:** `ha/references/tracks/feature.md` (S에서는 읽지 않음)

**강도 판정**

| 강도 | 조건 |
|---|---|
| S | 한 파일 안의 변경이고, 동작이 명확하며, 확인 방법이 뻔하다 |
| M | 여러 파일에 걸치거나, 새 데이터 형태나 상태가 생기거나, 기존 구조에 새 요구를 넣는다. 되돌릴 수 있다 |
| L | 모듈 간 계약이나 데이터 스키마가 바뀌거나, 사용 흐름이 아직 정해지지 않았거나, 여러 단계에 걸친다 |

**S: 바로 구현**
1. 구현한다.
2. 실제 동작을 1회 확인한다.

**M: 설계 후 구현**
1. **DESIGN(5-3)을 수행한다.** 기능 트랙의 D3 뼈대는 데이터 형태부터 정한다. 흩어진 조건문 대신 상태 기계, 반복되는 형태 가정 대신 타입 모델, 분기 대신 표·레지스트리처럼 도메인을 담는 구조를 고른다. 현재 모양이 단순하고 자랄 가능성이 낮으면 추상화를 억지로 넣지 않는다.
2. **설계 경고 신호를 점검한다.** 아래 8개 중 해당하는 것이 있으면 뼈대를 고친다.
3. **구현한다.** 기본은 메인 에이전트가 직접 구현한다. `code-delegation`의 조건(합의된 범위, 독립적인 단위)을 충족할 때만 위임한다.
4. **뼈대 기준으로 실행한다(D6).** 벗어나면 기록하고 뼈대를 갱신한다. 같은 모양의 우회가 반복되면 D7로 간다.
5. **실제 화면·실행 경로에서 확인한다.** 다른 환경에서의 확인은 통과가 아니다.
6. **테스트는 동작을 검증한다.** 테스트를 쓰거나 고칠 때 두 가지 가상 수정으로 점검한다. 동작을 깨뜨리는 수정에는 실패해야 하고, 결과는 같고 내부만 바꾸는 수정에는 통과해야 한다. 기대값은 요구사항에서 도출하고 코드 실행 결과에서 가져오지 않는다.
7. **코멘트는 코드가 보여 줄 수 없는 이유만 남긴다.** 단계 설명 주석(예: `// 1단계: 카드 추가`)은 쓰지 않는다.

**L: 단계 개발**
- `staged-development`로 진행한다. DESIGN의 D4 대안 비교와 D5 합의는 `staged-development` 1단계(아웃라인)에 포함한다.
- `staged-development` 2단계(핵심 흐름)는 대표 입력에서 사용자가 보는 결과까지 이어지는 최소 흐름 하나다.
- 3단계에서 M의 2~7을 적용한다.
- **병렬 위임 점검표:** 작업자를 둘 이상 쓸 때만 다음 4가지를 먼저 적는다. 해당 없는 항목은 `해당 없음: 이유`로 남긴다.
  - 먼저 끝나야 하는 선행 단계
  - 서로 다른 파일·계층으로 나뉘는 독립 작업
  - 공유 상태: 기본은 대상을 나누는 것이고, 정말 하나여야 할 때만 순서대로 실행한다
  - 작업자 하나가 낫다면 그 이유
- **쓰기 작업자마다 worktree나 전용 브랜치를 준다.** 브리프에 "이 파일은 건드리지 마라"고 적는 것은 잠금이 아니다.
- **작은 단위로 검증하며 쌓는다.** 단위마다 확인하고 다음으로 넘어간다. 커밋도 그 순서로 쌓는다.
- **공유 기반을 개선했으면 모든 사용처에 반영하고 각각 확인한다.**

**설계 경고 신호 8개 (코드 전용)**

| 신호 | 뜻 |
|---|---|
| 얕은 모듈 | 큰 인터페이스가 숨기는 복잡성이 적다. 호출자가 한 작업을 위해 여러 메서드를 조율해야 한다 |
| 정보 누출 | 같은 내부 결정(표현, 정책, 프로토콜 세부)이 여러 모듈에 나타나서 바꿀 때 함께 고쳐야 한다 |
| 실행 순서로 나눈 모듈 | 불러오기·검증·변환·저장처럼 순서별로 나눠 같은 규칙이 여러 단계에 반복된다 |
| 그냥 넘기는 메서드 | 같은 인자를 같은 모양의 다른 메서드로 넘기기만 한다 |
| 나뉜 소유권 | 둘 이상의 모듈이 같은 상태를 쓰거나 각자 사본을 가진다 |
| 한 작업에 두 가지 방법 | 같은 일을 하는 방법이 둘 이상이라 양쪽 모두 사용처가 늘어난다 |
| 밖에서 가져다 쓸 수 있는 내부 | 모듈 내부를 외부에서 import할 수 있어 사실상 인터페이스가 된다 |
| 손으로 맞추는 목록 | 같은 항목을 여러 곳에 나열해서 추가할 때마다 모두 고쳐야 한다 |

**제외한 pstack 요소**
- 모든 기능 구현의 위임 의무와 `arena` 위임: M은 직접 구현이 기본이다.
- 매번 PR 열기와 커밋 재정리(rebase): 사용자 지시를 따른다.
- 설계 논쟁 시 `interrogate`: 애매 항목 리뷰에서 다시 본다.

**리뷰에서 정할 것**
1. M에서 메인 에이전트 직접 구현을 기본으로 하고, `code-delegation` 조건을 충족할 때만 위임할지
2. 설계 경고 신호 8개를 기능 트랙에 넣을지 (리팩터링 트랙과 공유)
3. L 기능은 `staged-development`를 호출하고 DESIGN을 그 1단계에 합치는 구조로 갈지 (`staged-development`를 ha에 합칠지는 3단계에서 최종 결정)

### 5-6. 조사 트랙 (확정: 3가지 결정 추천안 채택. 출처는 종류로 적고 개인 지정은 플러그인 밖 파일로 분리)

**출처:** pstack Investigation 플레이북, `how`, `why`(근거 확신도 구분, 출처별 조사, 변경 전 제약 목록). wrxp `search-delegation`, 사용자 스킬 `implementation-evidence`와 함께 쓴다.
**파일:** `ha/references/tracks/investigation.md` (S에서는 읽지 않음)
**성격:** 읽기 전용이다. 답이나 추천을 만들고, 코드는 바꾸지 않는다. 변경이 필요하다고 판단되면 조사 결과를 보고한 뒤 버그나 기능 트랙으로 넘긴다.

**질문 유형**

| 유형 | 예 | 출력 |
|---|---|---|
| 동작 (how) | X는 어떻게 동작하나, 이 코드는 어디에 두어야 하나 | 개요, 핵심 개념, 동작 방식, 위치, 주의점 (해당 없는 절은 생략) |
| 이유 (why) | 왜 이렇게 만들었나, 누가 언제 정했나 | 확인된 사실, 합리적 추론, 경쟁 가설, 모르는 것, 조사한 출처 |
| 선택 (decision) | X와 Y 중 무엇이 나은가 | 추천과 장단점 표. 전제가 틀렸으면 전제부터 반박한다 |
| 확인 (are we sure) | 이거 정말 맞나 | 판단과 근거. 맞장구가 아니라 실제 판단을 쓴다 |

**강도 판정과 진행**

| 강도 | 조건 | 진행 |
|---|---|---|
| S | 한 모듈·한 함수·한 문서 범위의 좁은 질문 | 직접 읽고 답한다. 근거는 `파일:줄` 또는 문서 위치로 붙인다 |
| M | 여러 파일·서비스에 걸친 하위 시스템 질문, 또는 git 이력으로 답할 수 있는 이유 질문 | 메인 에이전트가 조사한다. 넓은 범위를 훑어야 하면 검색 에이전트(haiku)에 맡기고 결론만 받는다. 이유 질문은 git blame·log·PR 본문까지 본다 |
| L | 조직 맥락이 필요한 이유 질문, 여러 시스템에 걸친 질문, 변경 결정을 앞둔 조사 | 아래 "출처별 조사"를 수행한다 |

**L: 출처별 조사**
1. **코드 기준점을 먼저 만든다.** 대상 파일과 줄 범위, 핵심 심볼, 최근 커밋, 연결된 PR·티켓 번호를 모은다.
2. **질문에 맞는 출처를 고른다.** git은 항상 포함한다. 나머지는 질문 성격에 따라 고르고, 고르지 않은 출처는 건너뛴 이유를 한 줄로 남긴다.

   플러그인에는 출처 **종류**만 적고 특정 도구 이름은 적지 않는다. 실행할 때 세션에 연결된 MCP를 보고 종류별로 분류한다. 사용자 개인 출처 지정 파일(`~/.claude/wrxp/sources.md`, 플러그인 밖, 선택 사항)이 있으면 그 지정을 우선한다.

   | 출처 종류 | 도구 예 (플러그인에는 예시로만) | 잘 찾는 것 |
   |---|---|---|
   | 소스 이력 | git, `gh` | 구현 당시의 판단과 리뷰 논의 |
   | 긴 문서 | Notion, Confluence | 코드 전에 쓰인 설계 근거 |
   | 실시간 대화 | Slack, Teams | 문서로 남지 않은 논의 |
   | 이슈·티켓 | Jira, Linear, GitHub Issues | 제품·업무상 요구 |
   | 데이터 | Metabase, Tableau | 이 수치가 어디서 왔는가 |
   | 사내 코드 지식 | magma(Magma 레거시), worxsales MCP(WorxSales 구현), `implementation-evidence` 스킬 | 레거시 동작, WorxSales 구현 현황 |

   기준은 "회사 인프라는 포함, 개인 인프라는 제외"다. magma, worxsales MCP, Metabase, Tableau, Slack, Notion 같은 회사 인프라는 플러그인에 이름으로 적는다. 개인 전용 도구만 개인 지정 파일로 뺀다.

   이 사용자의 개인 지정 예 (`~/.claude/wrxp/sources.md`에만 기록): 수집 자료 통합은 muffiny.

3. **출처마다 검색 에이전트 하나씩 병렬로 돌린다.** 에이전트는 haiku로 시작하고, 판단이 필요한 출처만 sonnet으로 올린다. 종합은 메인 에이전트가 한다.
4. **확신도를 구분해서 쓴다.** 확인된 사실, 합리적 추론, 경쟁 가설, 모르는 것을 섞지 않는다. 가장 최근 커밋이 정답이라고 가정하지 않는다(최근성 편향).
5. **조사한 출처 목록을 남긴다.** 출처마다 한 줄씩, 아무것도 못 찾았거나 건너뛴 경우도 이유와 함께 적는다.
6. **변경을 앞둔 조사라면 제약 목록으로 바꾼다.** 유지할 것, 바꿀 것, 피할 것, 위험을 정리해 버그·기능 트랙에 넘긴다.

**제외한 pstack 요소**
- 단순 질문에도 opus 설명 에이전트를 띄우는 방식: S·M은 메인 에이전트가 직접 한다.

**리뷰에서 정할 것**

### 5-7. 기획서·글쓰기 트랙 (확정: L 독자 검토 에이전트 채택, L 핵심 섹션 먼저 채택, 한국어 출력 원칙과 `korean-polish` 모두 wrxp로 공유)

**한국어 규칙 공유 방식 (확정)**
- 사용자의 한국어 규칙은 두 개다. 둘은 같은 기준에서 나왔지만 쓰이는 시점이 다르다.
  - 한국어 출력 원칙 (개인 CLAUDE.md): **쓰는 동안** 지키는 규칙. 항상 적용된다.
  - `korean-polish` (개인 `~/.claude/skills`, Notion에 공유했던 스킬): **완성한 뒤** 제출 직전에 돌리는 교정 절차. 의미·수치·시제·확실성을 바꾸지 않는 계약이 핵심이다.
- 한국어 출력 원칙은 `wrxp/shared/writing-rules.md`의 한국어 절로 옮긴다.
- `korean-polish`는 `wrxp:korean-polish` 스킬로 옮긴다(`agents/openai.yaml` 포함). 글쓰기 트랙 M·L의 6단계 "최종 교정"은 `wrxp:korean-polish`를 이름으로 호출한다.
- 옮긴 뒤 개인 `~/.claude/skills/korean-polish`는 지워서 같은 스킬이 두 번 뜨지 않게 한다. 개인 CLAUDE.md의 한국어 출력 원칙은 플러그인이 없는 환경을 위해 남긴다(3단계에서 중복 여부 재검토).

**출처:** 설계 단계(5-3)의 산출물별 뼈대, pstack `technical-writing`(문서 유형 구분, 제목이 요지를 담기, 문장 규칙), `unslop`(AI 티 나는 표현 목록, 영어 기준이라 언어 무관 항목만), `staged-development`의 정본 기획서 구성.
**파일:** `ha/references/tracks/writing.md`, `wrxp/shared/writing-rules.md` (S에서는 읽지 않음)
**다른 스킬과의 관계:** Slack·DM 공유 메시지는 기존 `structured-share-thing`이 맡는다. 이 트랙은 그 밖의 문서를 맡는다.

**강도 판정**

| 강도 | 조건 |
|---|---|
| S | 짧은 답변, 한두 단락 작성·수정, 기존 문서의 국소 수정 |
| M | 문서 한 편 (기획서, 보고서, 가이드, 회의 자료) |
| L | 외부 공유나 의사결정에 쓰이는 문서, 이해관계자가 여럿인 문서, 긴 문서 |

**S:** 쓰고 한 번 다시 읽어 확인한다.

**M: 설계 후 작성**
1. **DESIGN(5-3)을 수행한다.** 독자가 읽고 무엇을 하는지, 핵심 메시지 한 문장, 섹션 제목과 섹션별 한 줄 요지를 먼저 정한다.
2. **문서 유형을 하나로 정한다.** 가이드·설명 문서라면 따라 하기(튜토리얼), 작업 방법(how-to), 찾아보기(레퍼런스), 이해하기(설명) 중 하나로 정하고 섞지 않는다. 섞이면 나누고 연결한다.
3. **유형별 필수 구성을 갖춘다.**
   - 기획서: 문제, 관찰 가능한 성공 조건, 범위와 제외 범위, 검토한 대안과 선택 이유, 결정이 필요한 항목, 위험
   - 보고서: 결론과 근거, 근거의 확신도(확인/추정), 남은 질문
   - 회의 자료: 회의에서 정할 것, 정하는 데 필요한 정보, 결정 기준
4. **초안을 쓴다.** 작성 규칙(`shared/writing-rules.md`)을 쓰면서 지킨다. 다 쓰고 나서 고치는 것보다 쓰면서 지키는 쪽이 낫다.
5. **사실을 대조한다.** 문서에 쓴 수치, 고유명사, 날짜, 링크, 인용을 원 출처와 다시 맞춘다. 기억이나 요약본으로 확인한 것은 통과가 아니다(검증 규칙).
6. **최종 교정을 한다.** 한국어 산출물은 `wrxp:korean-polish`로 교정한다.

**L: 단계 작성**
- M의 1~6에 다음을 더한다.
- **아웃라인 합의:** 구조안 2개 이상을 비교하고 사용자와 합의한다(D4·D5).
- **핵심 섹션 하나를 먼저 완성한다.** 가장 중요한 섹션 하나를 끝까지 써서 어조와 밀도를 사용자와 맞춘 뒤 나머지를 쓴다. 기능 트랙의 "핵심 흐름 먼저"와 같은 역할이다.
- **독자 검토:** 작성 문맥을 모르는 새 에이전트(sonnet)가 대상 독자 입장에서 읽고, 이해하지 못한 곳과 결정에 필요한데 빠진 정보를 보고한다. 작성자가 자기 글을 검토한 것은 독립 검토가 아니다.

**작성 규칙 (`shared/writing-rules.md` 초안, 언어 무관 항목)**
- 일을 하지 않는 단어는 지운다. 쉬운 일상어를 쓴다.
- 제목이 주제가 아니라 요지를 담는다. ("모드" 대신 "모드를 먼저 고른다")
- 조건을 지시보다 먼저 쓴다. 흔한 경우를 먼저, 예외를 뒤에 쓴다.
- 한 대상은 끝까지 한 이름으로 부른다. 동의어를 돌려 쓰지 않는다.
- 막연한 일반론 대신 구체적으로 쓴다. ("스키마 변경은 문제를 일으킬 수 있다" 대신 "컬럼 이름을 바꾸면 빌드가 실패한다")
- 느낌이 아니라 동작이나 수치를 쓴다. 다른 프로젝트 문서에 그대로 붙여도 말이 되는 문장은 지운다.
- 출처 없는 권위("업계에서는", "전문가들은")를 쓰지 않는다. 출처를 밝히거나 지운다.
- 억지로 셋씩 묶지 않는다. 실제 개수대로 쓴다.
- 설명 문서에서는 장단점을 나열만 하지 말고 판단을 쓴다. 레퍼런스는 판단 없이 사실만 쓴다.
- 한국어 문장 규칙은 사용자의 한국어 출력 원칙(주체·대상 생략 금지, 완결된 문장, 비유·과장 지양 등)을 이 파일에 옮겨 팀이 함께 쓴다.

**제외한 pstack 요소**
- 영어 전용 규칙(엠대시·콜론 금지, 영어 AI 어휘 목록, 능동태 규칙 등): 한국어 출력 원칙으로 대체한다.
- PR·커밋 메시지 작성 규칙: 이번 범위 밖.

**리뷰에서 정할 것**
1. L에서 독자 검토 에이전트(새 문맥, sonnet)를 넣을지
2. L에서 "핵심 섹션 하나 먼저 완성해 어조·밀도 합의" 단계를 넣을지
3. 사용자의 한국어 출력 원칙을 `shared/writing-rules.md`로 옮겨 팀과 공유할지 (지금은 개인 CLAUDE.md에만 있음)

### 5-8. 데이터·수치 트랙 (확정: 3가지 결정 모두 추천안 채택)

**출처:** pstack Perf issue 플레이북, `benchmark-checklist`(수치를 믿기 전 7가지 질문), 원칙 Explain the Number. pstack은 성능 측정 전용이지만, 같은 질문을 데이터 분석·지표 보고(Metabase, Tableau, SQL)에 맞게 옮긴다.
**파일:** `ha/references/tracks/data.md` (S에서는 읽지 않음)
**하위 유형:** 데이터 분석(지표, 추이, 비교, 원인 분해)과 성능 측정(속도, 처리량, 비용).

**강도 판정**

| 강도 | 조건 | 예 |
|---|---|---|
| S | 단일 수치 조회 | 지난달 신규 리드 수 |
| M | 비교, 추이, 원인 분석, 성능 개선 1건 | 3분기 전환율이 왜 떨어졌나, 이 쿼리를 빠르게 |
| L | 의사결정·외부 보고에 쓰이는 수치, 지표 정의 변경, 대시보드 신설 | 경영 보고용 KPI, 새 대시보드 |

**S: 조회하고 정의를 밝힌다**
1. 조회한다.
2. 답에 기간, 필터, 단위, 출처(카드·테이블 이름)를 한 줄로 붙인다.
3. 결과가 0건이거나 비정상적으로 크면 조회 조건부터 의심한다.

**M: 수치를 믿기 전에 확인한다**
1. **주장 문장을 먼저 쓴다.** 보고할 문장을 그대로 적는다. (예: "3분기 리드 전환율은 2분기보다 4%p 낮다") 아래 질문은 이 문장을 검증한다.
2. **7가지 질문에 실행 근거로 답한다.** 코드나 쿼리를 읽고 추측한 답은 근거가 아니다.

   | 질문 | 데이터 분석에서 | 성능 측정에서 |
   |---|---|---|
   | 정의가 맞나 | 분자·분모, 기간 경계, 시간대, 필터, 같은 이름의 다른 정의 | 무엇을 재고 무엇을 빼는지 측정 스크립트를 읽는다 |
   | 실제로 계산됐나 | 행 수, NULL, 조인으로 인한 중복, 테스트 데이터 포함 여부, 캐시된 결과 | 측정 구간 안에서 작업이 실제로 일어났나 |
   | 오류는 없나 | 누락된 기간, 실패한 적재, 빈 세그먼트 | 실패·타임아웃 수, 출력이 올바른가 |
   | 한계를 넘지 않나 | 세그먼트 합이 전체와 같은가, 비율이 0~100% 안인가 | 디스크·네트워크·코어 한계를 넘는 수치가 아닌가 |
   | 무엇이 이 수치를 정하나 | 세그먼트별 기여로 분해해서 변화를 만든 부분을 찾는다 | 병목(제한 요인)을 프로파일로 찾는다. 왜 두 배가 아닌지 설명한다 |
   | 재현되나 | 다른 경로(원천 테이블 직접 조회 등)로 1회 교차 확인한다 | 양쪽을 번갈아 5회 이상 돌리고 중앙값과 범위를 쓴다 |
   | 의미가 있나 | 과거 기간들의 변동 폭보다 차이가 큰가, 표본이 충분한가 | 전체 경로에서 차지하는 비중은 얼마인가 |

3. **성능 개선이면 싼 방법부터 시도한다.** 안 하기 → 다시 안 하기(캐시) → 덜 하기 → 나중에 하기 → 안 보일 때 하기 → 동시에 하기 → 더 싸게 하기 순서다. 앞 단계에서 목표에 닿으면 멈춘다.
4. **보고는 판정부터 한다.** 판정은 증가·감소(또는 빨라짐·느려짐), 차이 없음, 판단 불가 중 하나다. 수치에는 단위, 기간, 정의, 실행 횟수나 교차 확인 결과, 제한 요인을 붙인다. 정의나 실제 계산 여부를 확인하지 못했으면 판정은 "판단 불가"이고, 무엇을 확인하지 못했는지 적는다.

**L: 결정용 수치**
- M의 1~4에 다음을 더한다.
- **지표 정의를 정본에 고정한다.** 분자, 분모, 기간, 필터, 원천을 적는다.
- **독립 재계산:** 작성 문맥을 모르는 새 에이전트가 원천 데이터에서 같은 수치를 다시 계산한다. 결과가 다르면 차이의 원인을 찾을 때까지 보고하지 않는다.
- 보고서로 나가면 기획서·글쓰기 트랙 L과 연결한다.

**제외한 pstack 요소**
- 성능 개선의 위임 의무와 PR 인용 절차.
- Hillclimb(지표 하나를 반복 개선하는 장기 루프): 애매 항목 리뷰에서 다시 본다.

**리뷰에서 정할 것**
1. 7가지 질문을 데이터 분석용으로 옮긴 위 표를 이대로 쓸지
2. L에서 독립 재계산 에이전트(새 문맥, sonnet)를 넣을지
3. 성능 비교의 반복 측정을 pstack대로 "선택을 위한 비교는 5회 이상, 대략적인 값은 1회(1회라고 명시)"로 둘지

**출처:** pstack Refactoring 플레이북, 원칙 Subtract Before You Add·Migrate Callers Then Delete·Outcome-Oriented Execution·Minimize Reader Load·Laziness Protocol, 기능 트랙의 설계 경고 신호 8개.
**파일:** `ha/references/tracks/refactor.md` (S에서는 읽지 않음)
**정의:** 구조는 바꾸고 동작은 바꾸지 않는다. 정리하다가 버그나 빠진 기능을 발견하면 따로 떼어 내고, 구조 변경을 먼저 끝낸다. 동작을 바꾸는 재설계라면 기능 트랙으로 넘긴다.
**적용 대상:** 코드뿐 아니라 문서·스킬 재구성에도 적용한다. 이번 wrxp 정리처럼 문서 구조를 바꿀 때는 "기존 요구·시나리오 목록"이 동작 고정 장치 역할을 한다.

**강도 판정**

| 강도 | 조건 |
|---|---|
| S | 한 파일 안의 이름 변경, 함수 추출·인라인. 기존 테스트가 해당 동작을 덮는다 |
| M | 여러 파일에 걸친 구조 변경, API 모양 변경 |
| L | 여러 모듈에 걸친 이전(마이그레이션), 레이어 재편, 대규모 정리 |

**S: 바로 정리**
1. 정리한다.
2. 기존 검사를 돌린다.
3. 이름을 바꿨다면 문자열·문서·주석에 남은 옛 이름을 검색으로 1회 확인한다. 이름 변경은 문자열 속 사용처를 조용히 놓친다.

**M: 동작을 고정하고 옮기기**
1. **동작을 먼저 고정한다.** 기존 테스트가 대상 동작을 덮는지 확인한다. 덮지 않으면 구조를 건드리기 전에 현재 동작을 기록하는 테스트, 스냅숏, 또는 출력 비교 스크립트를 만든다. 타입 검사와 린트는 동작 고정이 아니다.
2. **목표 모양을 정한다.** 지금 처음 만든다면 어떤 구조일지 적는다. 새 모양은 분기나 잘못된 상태를 지워야 하고, 간접 계층을 더해서는 안 된다. 현재 모양이 이미 명확하면 그대로 둔다. 설계 경고 신호 8개(5-5)로 점검한다.
3. **빼고 나서 더한다.** 죽은 코드, 호출처가 하나뿐인 래퍼, 중복 검증, 고아 참조를 먼저 지운다. 목표 모양에 닿는 가장 작은 변경만 남긴다. "도움이 될지도" 하는 정리는 되돌린다.
4. **작은 단계로 옮긴다.** 단계마다 동작 고정 장치가 통과해야 다음으로 간다. API 모양을 바꾸면 모든 호출처를 옮기고 옛 API를 같은 변경에서 지운다. 호환용 우회 코드나 옛 길과 새 길을 함께 두지 않는다. 단, 외부 사용자가 옛 API에 의존하면 예외로 하고 이유를 남긴다.
5. **동작이 그대로인지 실제로 확인한다.** "컴파일된다"는 확인이 아니다.
6. **남길 가치가 있는지 판단한다.** 성공 기준은 읽는 사람의 부담이 줄었는가다. 따라가야 할 계층 수와 머릿속에 들고 있어야 할 상태가 줄지 않았으면 되돌린다.

**L: 단계 이전**
- `staged-development`로 진행하고, 목표 모양은 DESIGN D4 대안 비교를 거친다.
- **동작 동등성 검사를 도구로 만든다.** 옛 출력과 새 출력을 비교하는 스크립트나, 기록해 둔 기준 결과를 새 코드에 재생하는 장치를 만든다. 사람이 눈으로 비교하지 않는다.
- **중간 깨짐을 계획한다.** 이전 중에 일부가 깨져도 되는 구간을 미리 선언하고, 그 구간 밖에서는 깨짐을 허용하지 않는다. 이전이 끝나면 전체 정적 검사와 실행 검사를 통과해야 한다.
- **커밋 순서:** 빼기 → 모양 바꾸기 → 후속 정리 순서로 쌓는다.
- 기계적인 대량 수정은 `code-delegation`으로 위임할 수 있다. 작업자마다 worktree를 준다.

**보고 형식**
바뀐 구조, 동작을 고정한 장치, 동등성 확인 결과, 읽는 부담의 변화, 남긴 것과 되돌린 것을 적는다. 새 동작은 없어야 한다.

**리뷰에서 정할 것**
1. M에서 테스트가 대상 동작을 덮지 않으면 구조를 건드리기 전에 동작 고정 장치를 반드시 만들지
2. 호환용 우회 코드 금지를 기본으로 하고 외부 사용자 의존만 예외로 둘지
3. "읽는 부담이 줄지 않으면 되돌린다"는 판정 기준을 둘지
4. 문서·스킬 재구성에도 이 트랙을 적용할지

### 5-10. 프로토타입 트랙 (확정: 3가지 결정 모두 추천안 채택)

**출처:** pstack Prototype 플레이북.
**파일:** `ha/references/tracks/prototype.md` (S에서는 읽지 않음)
**정의:** 결정을 싸게 내리기 위한 버리는 실험이다. 산출물은 코드가 아니라 **결정**이다. 실제 구현은 선택된 방향을 기능·글쓰기 트랙에 넘겨서 한다.
**진입 경로:** 사용자가 "시안", "목업", "해 보고 정하자"라고 요청한 경우, 또는 질문 판정에서 `experiment`로 분류되어 PROBE가 확장된 경우.
**결정이 없으면 프로토타입도 없다.** 정할 것이 없으면 기능 트랙으로 보낸다.

**품질 기준이 반대인 유일한 트랙**
- 속도가 우선이다. 코드 품질, 테스트, 추상화는 신경 쓰지 않는다.
- 엄격함은 "올바른 결정을 싸게 고르는 것"에 둔다. 사용자가 요청하지 않은 변형도 제안하고, 안 되면 버리고 다른 방법을 시도한다.

**강도 판정**

| 강도 | 조건 | 진행 |
|---|---|---|
| S | 사실 하나를 확인하는 실험 (PROBE와 같은 수준) | 가장 작은 스크립트나 실행 1회로 관찰하고 결과를 근거로 돌려준다 |
| M | 변형 2~3개를 비교해 고르는 결정 | 아래 1~5 |
| L | 방향 자체가 열려 있는 결정 | 참고 자료를 먼저 모아 사용자가 방향을 고른 뒤 M을 수행한다 |

**M: 변형 비교**
1. **정할 결정을 한 문장으로 적는다.** (예: "목록 화면을 카드형으로 할지 표형으로 할지")
2. **격리된 임시 폴더에 만든다.** 제품 소스와 분리한다. 화면 결정은 가장 가벼운 HTML·CSS·JS로, 동작·시간 결정은 질문을 실행하는 가장 작은 스크립트로 만든다.
3. **변형은 2~3개로 제한하고, 화면 변형은 전환 버튼 하나로 오가게 만든다.** 각 변형에 이름을 붙인다.
4. **결정할 것을 실제로 관찰한다.** 화면은 변형마다 스크린숏을 찍고 상호작용을 직접 해 본다. 동작은 시간·출력·렌더링을 기록한다. 여기서는 관찰이 곧 테스트다.
5. **변형, 근거, 장단점, 추천을 제시한다.** 프로토타입은 버리는 것이라고 분명히 밝히고 임시 폴더 경로를 알린다.

**코드가 아닌 프로토타입**
- 문서: 목차 시안 2~3개나 첫 단락 시안 2~3개
- 슬라이드: 첫 장이나 핵심 장 시안 2~3개
- 데이터: 같은 질문을 다른 지표 정의로 계산한 결과 2~3개

**안전 경계**
- 외부 공개·발송을 하지 않는다. 보여 줄 때는 로컬 미리보기나 비공개 공유를 쓴다.
- 운영 데이터나 외부 시스템에 쓰지 않는다. 필요하면 질문 판정의 `must_ask`로 처리한다.

**리뷰에서 정할 것**
1. M의 변형 개수를 2~3개로 제한할지
2. L에서 참고 자료를 모은 뒤 사용자가 방향을 고를 때까지 만들기를 멈출지
3. 임시 폴더를 저장소 밖(세션 임시 폴더)으로 기본 설정하고, 사용자가 원할 때만 저장소에 남길지

### 5-11. 맞춤 절차 트랙 (확정: 4가지 결정 모두 추천안 채택. 판정 3단계는 5-12 검증 공통 규칙으로 이동)

**출처:** pstack `figure-it-out`(절차 자체를 먼저 설계, 강도를 작업에 맞춤, 가설 루프, 결정 기록), 원칙 Prove It Works·Sequence Verifiable Units·Encode Lessons in Structure.
**파일:** `ha/references/tracks/custom.md` (S에서는 읽지 않음)
**진입:** 다른 트랙이 맞지 않는 작업이다. 예를 들어 환경·도구 설정, 운영 작업, 여러 트랙이 섞인 큰 작업, 처음 해 보는 종류의 일이다.

**강도 판정과 진행**

| 강도 | 조건 | 진행 |
|---|---|---|
| S | 맞는 트랙은 없지만 단순하다 | 그냥 하고 결과를 1회 확인한다 |
| M | 단계가 여럿이지만 되돌릴 수 있다 | 아래 "M: 짧은 절차" |
| L | 크거나, 되돌리기 어렵거나, 사용자가 자리를 비운 사이 진행할 작업이다 | 아래 "L: 절차 설계와 실행" |

**M: 짧은 절차**
1. 완료 조건을 반증할 수 있는 문장으로 적는다. ("설정 후 새 세션에서 X 스킬이 목록에 보이고 호출된다")
2. 3~7단계짜리 절차를 만들고, 단계마다 확인 방법을 붙인다.
3. 절차를 한 줄로 보고하고 진행한다.
4. 단계마다 확인하고 다음으로 넘어간다.

**L: 절차 설계와 실행**
1. **틀 잡기:** 완료 조건(반증 가능한 문장), 규모(대략적인 단위 수와 막힐 지점), 엄격함 수준을 정한다. 되돌리기 어렵고 영향 범위가 넓을수록 엄격하게 한다. 엄격함은 "더 열심히"가 아니라 관문과 산출물의 수다.
2. **절차 설계:**
   - 독립적으로 끝낼 수 있는 단위로 나눈다.
   - 가장 불확실한 것부터 한다.
   - 검증 장치를 작업보다 먼저 만들고, 변경 전 기준값을 기록해서 "이전 값과 새 값"으로 비교할 수 있게 한다.
   - 병렬로 나눌 부분을 정한다. 경계가 분명한 곳만 나눈다.
3. **사용자 검토:** 틀과 단계 목록을 `staged-development` 정본에 쓰고 사용자와 합의한다.
4. **실행 루프:** 단위마다 가설을 적고, 가장 작은 변경을 하고, 실제 결과로 완료 조건에 비춰 확인한다. 나아졌으면 남기고 아니면 되돌린다. 너무 쉽게 통과하면 관찰 방법부터 의심한다. 판정은 확인됨, 확인 안 됨, 판단 불가 중 하나이고 판단 불가는 통과가 아니다.
5. **결정 기록:** 단계가 끝날 때마다 무엇을 왜 했고 근거와 결과가 무엇인지를 정본의 실행 상태·검증 근거에 한 줄씩 남긴다. 별도 기록 파일은 만들지 않는다.
6. **마무리:** 전체를 완료 조건에 비춰 실제 결과로 확인한다. 같은 교정을 반복했다면 그 교정을 검사·스크립트·규칙으로 만들어 남긴다.

**트랙 승격**
같은 종류의 맞춤 절차가 반복되면, 다음 정리 때 그 절차를 정식 트랙으로 만들자고 제안한다.

**리뷰에서 정할 것**
1. M에서 절차를 한 줄 보고만 하고 멈추지 않고 진행할지
2. L의 결정 기록을 별도 파일(pstack `show-me-your-work`의 TSV) 대신 정본 기획서에 남길지
3. 판정 3단계(확인됨, 확인 안 됨, 판단 불가)를 이 트랙만이 아니라 ha 전체의 VERIFY 공통 규칙으로 올릴지
4. 반복되는 맞춤 절차를 정식 트랙으로 승격 제안하는 규칙을 둘지

### 5-12. 검증 공통 규칙과 blast-radius (확정: 3가지 결정 모두 추천안 채택)

**현재 상태:** `ha/references/verification.md`는 이미 단단하다. 실행 전 검증 기준 예약, 작성자·검증자 문맥 분리, 검증 못 한 항목은 통과 아님, 수정 루프 체크포인트(5회마다 에이전트 점검, 10회마다 사용자 점검), 실패 유형별 처리가 있다. 이 구조는 유지하고 아래만 더한다.

**verification.md 추가안**

1. **대체물 규칙 (확정분):** 다른 환경, 목업, 에이전트의 자기 보고, 요약본으로 확인한 결과는 통과가 아니다. 한계를 명시한다.
2. **판정 3단계 (5-11에서 이동):** 결과 기록의 `result`에 `inconclusive`(판단 불가)를 추가한다. 판단 불가는 통과가 아니며, 무엇을 확인하지 못했는지 적는다.
3. **너무 쉽게 통과하면 관찰 방법부터 의심한다.** 검사가 실제 대상을 보고 있는지 먼저 확인한다.
4. **실패 출력은 차이 내용을 인용한다.** "assert 실패"가 아니라 무엇이 기대와 어떻게 달랐는지를 근거로 쓴다. 예외, 빈 결과, 실제 불일치는 모두 빨간색으로 보이지만 의미가 다르다.
5. **성공 보고 전에 실제 상태를 읽는다.** "보냈다", "병합됐다", "시작됐다"를 보고하기 전에 실제 상태와 종료 코드를 확인한다. 잘린 출력이나 자신이 출력한 문장은 증거가 아니다.
6. **근거의 출처도 확인한다.** 결과가 맞아도 과정이 틀릴 수 있다. 판단에 쓴 사실마다 어느 기록에서 왔는지 밝히고, 그 기록이 정본(원문, 원 데이터)인지 확인한다. 사용자 붙여넣기를 재구성한 문장이나 읽지 않은 파일에 기댄 판단은 근거가 아니다.
7. **task-type 표를 트랙 기준으로 바꾼다.** 기존 표(code, writing, planning, research, analysis 등)를 8개 트랙에 맞춰 정리하고, 트랙 파일의 검증 단계와 중복되는 내용은 트랙 쪽으로 옮긴다.

**근거 수준 사다리 (blast-radius에서 가져옴)**
핵심 안전 사실 하나하나를 아래 사다리에서 어디까지 올렸는지 밝힌다. 일반 주장에는 기존대로 확인/추정/추측 표시를 쓴다.

| 수준 | 뜻 |
|---|---|

**blast-radius (영향 범위 확인)**

**출처:** pstack `blast-radius`.
**핵심:** 호출처 목록을 뽑는 것은 일이 아니다. 검색으로 안 보이는 깨짐을 찾고, 변경이 안전한 **단 하나의 근거 사실**을 실행으로 증명하는 것이 일이다.
**절차**
1. 변경을 읽는다. diff에 드러나지 않는 동작 변화까지 포함한다.
2. 안전 근거 사실 하나를 찾는다. 위험해 보이는 변경 대부분은 사실 하나 때문에 안전하다. 시간을 여기에 쓴다.
3. 검색이 멈추는 곳을 본다. 라이브러리 원본과 고정 버전, 실행 시점, API가 돌려주는 JSON, DB 컬럼, 전송 형식, 같은 데이터를 읽는 다른 언어, 기능 플래그, 세 단계 아래의 사용처다.
4. 위험마다 실제 발생 가능성과 비용을 적는다. 확인된 위험과, 확인해서 지운 위험을 나눠 적는다. 없는 호출처나 API를 지어내지 않는다.
5. 안전 근거 사실을 실행으로 증명한다(사다리 4 이상). 증명하지 못했으면 "증명 안 됨"으로 적는다.
**출력:** 변경이 하는 일, 안전 근거 사실과 증명 수준, 위험(`파일:줄`, 가능성, 비용, 확인법), 확인해서 지운 위험, 병합 전 가장 싼 확인 방법.
**배치 (제안):**
- 조사 트랙의 질문 유형으로 추가한다. ("이거 바꾸면 뭐가 깨져?")
- 기능·리팩터링·버그 트랙에서 공유 계약(API, DB 스키마, 전송 형식, 공용 모듈)을 바꾸는 M 변경과 모든 L 변경의 검증 단계에서 자동으로 수행한다.
- 요청이 기존 코드에 대해 단정할 때("이 엔드포인트를 공개로 바꿔")는 설계 전에 수행한다. 그 단정은 가설이고, 사용처 조사가 설계를 결정한다.
**제외:** 여러 모델 비교(`arena`) 단계.

2. 근거 수준 사다리를 "핵심 안전 사실에만" 적용하고 일반 주장은 확인/추정/추측 표시를 유지할지

아래는 첫 초안이다. 재검토안이 채택되면 3단계에서 지운다.

**첫 초안의 현재 상황 분석:** 트랙 리뷰를 거치면서 23개 원칙 대부분이 이미 해당 트랙 안에 녹아 들어갔다. 같은 내용을 `shared/principles.md`에 다시 쓰면 두 곳을 손으로 맞춰야 하는 문제가 생긴다(설계 경고 신호 "손으로 맞추는 목록"). 그래서 원칙 파일에는 **여러 트랙에 공통인 원칙만** 두고, 특정 트랙 전용 원칙은 그 트랙 파일에만 둔다.

**`shared/principles.md` 초안 (공통 원칙 9개)**

1. **가장 작은 변경.** 문제를 푸는 가장 작은 변경을 한다. 같은 결정을 여러 곳에서 반복하지 말고 한 곳에 두고 결과를 넘긴다. 그럴듯한 상용구보다 적은 줄이 낫다.
2. **빼고 나서 더한다.** 더하기 전에 죽은 것, 중복된 것, 쓰이지 않는 것을 먼저 지운다. 관찰된 사용에 맞춰 설계하고, 추측한 예외 상황을 위한 장치는 만들지 않는다. 문서와 프롬프트에도 적용한다.
3. **전제를 공격한다.** 같은 전제를 깐 시도가 두 번 실패하면 그 전제를 한 문장으로 적고, 다음 시도 전에 전제부터 검증한다. 코드 수정뿐 아니라 기획 방향이 반복해서 막힐 때도 적용한다.
4. **처음부터 있던 요구처럼 다시 설계한다.** 새 요구를 기존 설계에 덧붙이지 않는다. "처음부터 이 요구가 있었다면 무엇을 만들었을까"를 묻고, 영향받는 모든 곳(타입, 문서, 예시, 근거)에 반영한다. 생각은 전체로 하고 전달은 단계로 한다.
5. **받는 사람의 경험을 먼저 본다.** 받는 사람은 최종 사용자, 코드를 가져다 쓰는 동료, 다음 유지보수자, 문서 독자다. 모든 기능과 항목은 쓸모를 증명해야 한다. 거친 열 개보다 다듬은 세 개가 낫다.
6. **실제로 확인한다.** 대체물이 아니라 실제 결과를 본다. 세부 규칙은 `ha/references/verification.md`를 따른다.
7. **솔직하게 판단한다.** 추천은 판단이지 맞장구가 아니다. 범위를 넓히자는 제안이나 제시된 방법에 대해 실제 판단을 말하고, 필요하면 "이건 들일 가치가 없다"고 말한다.
8. **(조건부) 지렛대를 만든다.** 같은 작업을 반복하거나 검증을 다시 돌려야 하면 손으로 하지 말고 스크립트를 만든다. 첫 단위는 손으로 해서 방법을 익히고, 그 결과와 스크립트 결과를 비교해 증명한다. 가장 작은 스크립트로 만들고 프레임워크를 만들지 않는다.
9. **(조건부) 교훈을 구조로 만든다.** 같은 지시를 두 번째 쓰게 되면 검사, 스크립트, 규칙으로 바꾼다. 판단이 필요해서 구조로 만들 수 없으면 지시를 눈에 띄게 하고 실패 예시를 붙인다.

**트랙별로 녹아 있는 원칙 (원칙 파일에 다시 쓰지 않음)**

### 5-14. 별도 스킬 후보: 리뷰 에이전트, deslop, no-comments (확정: 별도 스킬 없음. `wrxp:reviewer`는 4단계에서 내장 `code-review`와 비교 후 결정. 독자 검토·독립 재계산은 브리프만 바꿔 `general-purpose` 사용)

**대상:** `thermo-nuclear-review`, `thermo-nuclear-code-quality-review`, `thermos`, 리뷰 에이전트 2개, `deslop`, `no-comments`와 `comment-sicko`. (`why`는 조사 트랙에 흡수되어 이 항목에서 뺀다.)

**원문을 읽고 확인한 것**
- `thermo-nuclear-review`의 실체는 "극도로 철저하게 보라"는 강한 프롬프트 하나다. 범위는 브랜치 diff이고, 버그, 다른 기능을 깨뜨리는 변경, 개발 환경을 깨뜨리는 변경(환경 변수 이름, 포트, 비밀값 읽는 위치), 기능 플래그 누출, 보안을 본다.
- `thermo-nuclear-code-quality-review`는 구조 개선 리뷰다. 1천 줄을 넘기는 파일, 엉뚱한 곳에 끼어든 조건문, 그냥 넘기는 래퍼를 잡는다. 내용 대부분이 이미 확정한 설계 경고 신호 8개(5-5)와 겹친다.
- `deslop`은 다섯 줄짜리 점검 목록이다. 불필요한 주석, 신뢰 경로의 비정상적인 방어 코드, 타입 우회용 `any`, 깊은 중첩, 주변 코드와 다른 스타일을 본다.
- `no-comments`는 주석 제거를 위해 에이전트, `architect`, 규칙화 제안까지 돌리는 무거운 절차다. 주석 규칙은 이미 기능 트랙 M 7단계에 한 줄로 들어가 있다.
- Claude Code에는 이미 내장 스킬 `code-review`(diff 버그 리뷰, 강도 조절), `security-review`, `simplify`(정리·단순화 후 적용)가 있다. pstack 리뷰 스킬과 역할이 크게 겹친다.

**판단: 별도 스킬은 하나도 만들지 않는다**
- `thermos`, `no-comments`, `comment-sicko`: 제외한다. 비용에 비해 새로 얻는 것이 없다.
- `deslop`: 스킬로 만들지 않는다. 다섯 줄을 기능·리팩터링 트랙의 마무리 점검에 넣는다. 정리 작업 자체가 필요하면 내장 `simplify`를 쓴다.
- `thermo-nuclear-code-quality-review`: 스킬로 만들지 않는다. 겹치지 않는 부분(1천 줄 경계, 엉뚱한 곳에 끼어든 조건문)만 설계 경고 신호에 두 줄로 더한다.
- `thermo-nuclear-review`: 스킬 대신 **리뷰 에이전트 하나**(`wrxp:reviewer`)의 지침으로 흡수한다. 이유는 OMC를 지우면 `verifier`·`code-reviewer`(30일간 32회 사용)를 대신할 독립 검토자가 필요하기 때문이다.

**`wrxp:reviewer` 에이전트 초안**
- 새 문맥에서 실행하고 읽기 전용 도구만 쓴다. 작성자와 문맥을 나누는 것이 존재 이유다.
- 모델은 sonnet 기본, 보안·데이터 손실 위험이 있으면 opus로 올린다. (CLAUDE.md의 리뷰 위임 규칙과 같다)
- 지침에 넣을 것:
  - 범위는 이번 변경분이다. 기존 코드의 문제는 보고하지 않는다.
  - 보는 것: 버그, 다른 기능을 깨뜨리는 변경, 개발 환경을 깨뜨리는 변경, 기능 플래그 누출, 보안
  - 의도된 깨짐은 범위가 좁으면 보고하지 않는다. 단, 작성자가 영향을 과소평가한 것 같으면 보고한다.
  - 중요도를 부풀리지 않는다. 부풀린 보고가 쌓이면 아무도 듣지 않는다.
  - 조사를 끝내지 않은 지적을 내지 않는다. ("백엔드에서 처리하면 괜찮다"고 쓰지 말고, 백엔드 코드를 읽을 수 있으면 읽고 결론을 낸다)
  - 핵심 지적에는 근거 수준 사다리(5-12) 단계를 붙인다.
- 호출 시점: 코드 변경 L의 검증 단계, 사용자가 리뷰를 요청할 때. M에서는 자동으로 부르지 않는다(`code-delegation`의 "근거가 충분하면 재검토하지 않는다"를 유지).

**확신하지 못하는 부분**
- `wrxp:reviewer`가 내장 `code-review` 스킬보다 실제로 나은지는 모른다. 내장 스킬은 이 용도로 다듬어졌을 가능성이 크다. 우리 에이전트의 장점은 모델 고정, 읽기 전용, 우리 규칙(사다리, 의도된 깨짐 처리)을 안다는 점뿐이다. 4단계 시뮬레이션에서 같은 diff를 둘 다에 넣어 비교하고, 내장이 같거나 낫다면 에이전트를 만들지 않고 "L 검증은 내장 `code-review`를 호출한다"로 바꾼다.
- 글쓰기 L의 독자 검토와 데이터 L의 독립 재계산도 새 문맥 에이전트다. 이것까지 `wrxp:reviewer` 하나에 모드로 넣을지, 매번 브리프만 바꿔 `general-purpose`를 쓸지는 정하지 못했다. 에이전트 정의를 늘리면 관리할 것이 늘어서, 지금은 브리프만 바꾸는 쪽에 기운다.

**리뷰에서 정할 것**
1. 별도 스킬을 하나도 만들지 않는 판단에 동의하는지
2. `wrxp:reviewer`를 만들되 4단계에서 내장 `code-review`와 비교한 뒤 최종 결정하는 방식으로 갈지
3. 독자 검토·독립 재계산은 에이전트 정의 없이 브리프만 바꿔 `general-purpose`로 돌릴지

### 5-16. `code-delegation` 보강 (제안, 리뷰 중)

**현재 계약에서 유지할 것:** 합의된 범위만 위임, Claude 메인은 `opus` 기본·가벼운 일은 `sonnet`, 작업자가 구현과 자체 검증을 함께 책임, 근거가 충분하면 메인이 재검토하지 않음, 병렬은 파일 소유권이 나뉠 때만.

**보강이 필요한 이유**
- OMC를 지우면 지금 실제로 쓰이는 작업자(`oh-my-claudecode:executor`, 30일간 226회)가 사라진다. 현재 계약은 모델만 정하고 에이전트 종류는 정하지 않아서, CLAUDE.md의 "코드는 executor로" 문장이 그 빈칸을 채우고 있다.
- 작업자는 ha를 읽지 않는다. 지금 계약으로는 트랙에서 정한 규칙(동작 기준 테스트, 코멘트 규칙, 대체물 규칙, 설계 경고 신호)이 작업자에게 전달되지 않는다.

**추가안**

1. **에이전트 종류:** `subagent_type`은 `general-purpose`로 한다. MCP 접근을 빼앗는 읽기 전용 종류는 구현 작업자로 쓰지 않는다. 전용 작업자 에이전트는 만들지 않는다(5-14의 "에이전트 정의를 늘리지 않는다"와 같은 판단).
2. **규칙 전달:** 브리프에 해당 트랙 파일과 `verification.md`의 절대 경로를 넣고, 작업자가 구현 전에 읽게 한다. 메인은 자신이 읽은 스킬 파일의 위치를 알고 있으므로 경로를 넘길 수 있다. 내용을 브리프에 복사하지 않는다.
3. **쓰기 작업자마다 격리:** 병렬로 쓰는 작업자에게는 `isolation: "worktree"`나 전용 브랜치를 준다. 브리프의 "이 파일은 건드리지 마라"는 잠금이 아니다.
   - 주의: Claude Code의 worktree 격리는 `worktree.baseRef` 설정이 `head`가 아니면 원격 기본 브랜치에서 갈라진다. 작업자가 아직 푸시하지 않은 로컬 커밋 위에서 일해야 하면, 메인이 그 커밋 위에 worktree를 직접 만들고 기준 커밋을 브리프에 적는다.
   - git 저장소가 아니면 격리할 수 없으므로 병렬 쓰기를 하지 않는다.
4. **새 에이전트와 이어 쓰기의 기준:** 새 작업은 새 에이전트에 원래 브리프, 이후 지시, 이전 보고를 합쳐서 준다. 이어 쓰기(SendMessage)는 그 에이전트만 가진 상태가 있을 때만 쓴다. 예를 들어 커밋하지 않은 변경이 있는 worktree나 띄워 둔 개발 서버가 그렇다. 중간에 끼어든 지시를 여러 번 이어 붙이면 앞의 지시가 조용히 빠지기 때문이다.
5. **버린 에이전트는 멈춘 것을 확인한다.** 새 에이전트로 갈아탈 때 이전 에이전트를 명시적으로 멈춘다. "완료" 알림은 프로세스가 끝났다는 뜻이 아닐 수 있다. 작업 트리에 대한 보고가 `git status`와 다르면 아직 살아 있는 에이전트를 의심한다.
6. **보고를 그대로 전달하지 않는다.** 메인은 작업자의 diff를 직접 보고 자기 말로 요약한다. 이것은 재검토(다시 테스트하거나 다시 구현하는 것)가 아니라, 작업자 보고에 섞인 사실과 다른 주장을 사용자에게 옮기지 않기 위한 최소한의 확인이다.

**판단이 갈릴 수 있는 부분**
- 6번은 현재 계약의 "근거가 충분하면 재검토하지 않는다"와 긴장이 있다. diff를 직접 보는 비용은 작업 크기에 비례해서, 큰 위임에서는 메인 문맥을 꽤 쓴다. 대안은 "변경 파일 목록과 핵심 부분만 보고 나머지는 작업자 근거를 믿는다"인데, 어디까지가 핵심인지 기준을 정하기 어렵다. 나는 6번을 넣는 쪽이 낫다고 보지만 확신은 중간이다.
- 4번의 "새 에이전트 기본"은 비용이 든다. 새 에이전트는 파일을 다시 읽어야 한다. 대부분의 수정 라운드는 같은 worktree에서 이어지므로 실제로는 이어 쓰기가 더 자주 쓰일 것이다.

**리뷰 결과:** 1~5 확정. 6번은 범위를 줄이기로 함. 축소안은 아래와 같다 (리뷰 중).

**6번 축소안: 대조는 기계적으로, 읽기는 위험 신호가 있는 곳만**

6번의 목적은 diff를 다 읽는 것이 아니라 작업자 보고 속 사실과 다른 주장을 사용자에게 옮기지 않는 것이다. 이 목적이라면 대부분은 기계적 대조로 잡힌다.

1. **변경이 작으면 그냥 다 읽는다.** 변경이 약 150줄 이하이면 어디를 읽을지 고르는 것보다 전부 읽는 편이 싸다.
2. **크면 먼저 기계적으로 대조한다.**
   - 보고한 변경 파일 목록과 `git diff --stat`을 맞춘다. 보고에 없는 파일, 브리프 범위 밖의 파일이 있으면 그 파일은 읽는다.
   - 합격 조건마다 보고에 명령, 종료 코드, 출력 일부가 있는지 본다. 없으면 그 조건은 "확인 안 됨"으로 처리한다. 메인이 검사를 다시 돌리지는 않는다.
3. **위험 신호가 있는 부분만 읽는다.** diff를 검색해서 아래가 걸린 부분만 연다.
   - 지워지거나 약해진 테스트·단언(`assert`, `expect` 삭제, `.skip`, `.only`, 기대값 변경)
   - 남은 임시 표시(`TODO`, `FIXME`, 미구현 예외, 빈 함수 본문)
   - 설정·환경 변수·비밀값·권한 관련 변경
   - 공유 계약(API, DB 스키마, 공용 모듈) 변경. 이 경우는 blast-radius 자동 실행 조건(5-12)과 같다.
4. **요약의 출처를 구분한다.** 사용자에게 주는 요약은 `diff --stat`과 메인이 읽은 부분을 바탕으로 쓴다. 메인이 확인하지 않고 작업자 보고에만 기댄 내용은 "작업자 보고 기준"이라고 표시한다.

비용은 `diff --stat`, 검색 몇 번, 걸린 부분 읽기 정도다. 테스트 약화와 범위 이탈처럼 위임에서 가장 흔하고 위험한 거짓 보고는 이것으로 잡힌다. 반대로 겉보기에 멀쩡한 로직 오류는 이 방식으로 못 잡는다. 그건 원래 작업자 자체 검증과, L에서 리뷰 에이전트가 맡을 몫이다.

**확정:** 6번 축소안 채택. 150줄 기준은 4단계 시뮬레이션에서 실제 위임 크기를 보고 조정할 수 있다.

### 7-2. 저장소를 보고 새로 알게 된 것

**(1) 참조 파일은 건너뛰어질 수 있다. 이미 한 번 사고가 났다.**
v0.1.27 커밋 기록에 따르면, 질문 정책을 참조 파일에만 두었더니 모델이 그 파일을 읽지 않고 질문 없이 실행해 버렸다. 그래서 질문 게이트를 네 진입 파일에 직접 넣었고, 네 사본이 바이트 단위로 같은지 테스트로 묶었다.
우리 설계는 트랙 절차를 전부 `references/tracks/`에 두고 "M·L이면 읽는다"고 했다. 같은 사고가 그대로 재현될 수 있다. 대책은 같은 방식이다. 트랙마다 **빠지면 안 되는 최소 규칙**(S/M/L 기준 한 줄과 핵심 단계 2~3개)을 `ha/SKILL.md` 안의 요약표로 두고, 세부만 참조 파일에 둔다. `code-delegation`의 작업자 브리프도 같다. 경로만 넘기면 작업자가 안 읽을 수 있으므로, 핵심 몇 줄은 브리프에 직접 넣고 세부만 경로로 넘긴다(5-16의 2번 수정).

**(2) `ha/SKILL.md`에 남은 공간이 약 2KB뿐이다.**
테스트가 `ha/SKILL.md`를 16,000바이트 이하로 묶고 있고 지금 13,982바이트다. 넣으려는 것(CLASSIFY, 트랙 요약표, PROBE, DESIGN 진입, 원칙 3줄, 출력 항목)은 한국어로 약 5~6KB로 추정한다. 방법은 둘이다.
- 상한을 올린다. 쉽지만 S 작업을 포함한 모든 호출이 그만큼 더 읽는다. 처음에 걱정한 "1줄 수정에도 무거운 흐름"이 다른 모양으로 돌아온다.
- 본문에서 덜 위험한 것을 참조로 옮긴다. 후보는 CAPABILITY_RESOLVE 세부, `RuntimeParallelism` YAML, Observation·CommittedIntent YAML 틀, 최종 출력 YAML, "중첩 호출이 없는 런타임" 절이다. 합쳐서 약 4~5KB다. 이 중 일부는 테스트가 본문에 있다고 확인하고 있어서(`runtime_parallel_limit` 등) 테스트도 함께 고쳐야 한다.
나는 두 번째를 추천한다. 옮길 후보들은 건너뛰어져도 실행이 조용히 틀어지지는 않는 내용이다. 질문 게이트처럼 건너뛰면 사고가 나는 내용은 본문에 남긴다.

**(3) PROBE 규칙은 네 파일에 똑같이 들어가야 한다.**
질문 게이트가 네 진입 파일에 바이트 단위로 같게 들어 있으므로, `experiment` 분류도 네 곳에 같은 문장으로 넣어야 한다. 기존 테스트가 사본 불일치를 잡아 주므로 위험은 낮다. `haq`·`haqq`·`haqqq`의 상한(6,000바이트)에는 여유가 있다.

**(4) `decompose`, `breakdown`, `agent-match`는 90일 동안 한 번도 쓰이지 않았다.**
세 스킬은 `.middleware/` 기반의 옛 파이프라인이고, ha의 의존성 그래프 실행과 역할이 겹친다. 이 사용자 기준으로는 지워도 잃는 것이 없다. 다만 wrxp는 사내 공유 플러그인이라 팀원이 쓰는지는 이 기록으로 알 수 없다. 전역 규칙 템플릿(`setup/assets/global-rules.md`)도 세 스킬을 안내하고 있어서, 팀원의 CLAUDE.md에도 같은 안내가 들어가 있을 것이다.

**(5) `staged-development`와 ha L의 이중 기록은 한쪽을 정본으로 정하면 풀린다.**
L에서는 ha의 실행 계약(CommittedIntent)을 따로 들고 있지 말고 `staged-development` 정본 기획서에 쓴다. `staged-development`는 30일간 직접 호출도 11번 있었으므로 ha에 합치지 않고 별도 스킬로 둔다.

**(6) 전역 CLAUDE.md의 wrxp 구역은 `wrxp:setup`이 관리한다.**
문구를 고치려면 개인 CLAUDE.md가 아니라 `setup/assets/global-rules.md`를 고쳐야 팀원에게도 반영된다.

- 중간 질문: 실행 중 다음 세 조건 중 둘 이상에 해당하는 판단이 드러나면 그 자리에서 묻는다. ① 결과물이 달라진다 ② 해 보면 알 수 있는 사실이 아니라 취향·제품 판단이다 ③ 나중에 바꾸면 다시 해야 할 일이 크다. 비슷한 판단 여럿은 한 번에 묶는다.
- 레버와의 관계: q 레버는 "시작 전에 얼마나 파고드는가"만 정한다. 중간 질문은 레버와 관계없이 `/ha`에서도 한다. `/ha` 설명은 "질문 0개"에서 "시작 전 질문 0개"로 바꾼다.
- 강도와의 관계: M에도 적용한다. M의 "한 줄 보고 후 진행"은 위 기준에 걸리지 않는 판단에만 쓴다.
- 묻는 방식: 질문 도구(Claude Code는 AskUserQuestion)로 묻고 그 자리에서 멈춘다. 글로만 묻고 작업을 계속하면 이후 턴에 질문이 묻혀 가정대로 진행되기 때문이다. 이미 띄운 백그라운드 작업은 그대로 두고 결과는 답을 받은 뒤 반영한다.
- 하한: 묻지 않고 기본값으로 정한 취향·제품 판단을 기록해 두고, L은 큰 단계가 끝날 때마다, M은 결과를 내기 전에 한 번 그 목록을 보여 주고 확인받는다.
- 자동 상향: M이 같은 전제로 두 번 실패해 L로 올라가면 계획 합의로 넘어가지 않고, 막힌 지점과 전제·검증 결과를 보고한 뒤 멈춘다.
- staged-development 정본은 기능·리팩터링·맞춤 절차 L에만 쓴다. 버그·조사·데이터·글쓰기 L은 각 트랙 절차를 따른다(9-12 해소).
- 남은 확인: Codex에서 그 자리에서 멈추는 질문 도구가 있는지 확인해야 한다.

**9-2 M 구현 주체 → 확정 (5-5 "M은 메인이 직접 구현"을 뒤집음)**
- M은 작업자에게 위임한다. 작업자 선택은 code-delegation 규칙(opus 기본, 가벼운 작업은 sonnet)을 따른다. S는 메인이 직접 한다.
- 취향 판단 처리: 넘기기 전에 메인이 예상되는 취향·제품 판단을 먼저 묻고 지시문에 넣는다. 작업 중 새 판단(9-1 기준)이 나오면 작업자는 그 부분에서 멈추고 질문을 돌려보낸다. 메인이 사용자에게 물은 뒤 같은 작업자에게 답을 보내 이어서 하게 한다.
- 검증: 공유 계약(API, 스키마, 공유 타입, 설정, 문서·규칙 파일의 삭제·이동)을 바꾸는 M에만 새 맥락 검토 1회(sonnet, diff 중심)를 붙인다. 나머지 M은 작업자의 테스트·실제 실행 근거로 끝낸다.
- OMC 과도기: 개인 전역 CLAUDE.md에 "wrxp ha 실행 중에는 트랙 규칙이 OMC 위임 규칙보다 우선한다"는 한 줄을 넣는다. 팀원 영향 없음. OMC 제거는 기존대로 흡수 완료 뒤.

- 검증 추가안·근거 사다리·blast-radius 절차는 "대체물로 확인한 것과 결론이 안 난 것은 통과로 보고하지 않는다(판단 불가 포함)"와 "공유 계약을 바꾸면 안전 근거 하나를 실행으로 확인한다"로 줄이고, blast-radius는 공유 계약 sonnet 검토 브리프에 흡수한다.
- 기본값 하한은 L에도 "취향 기본값이 있을 때만 멈춤"을 똑같이 적용한다(9-1 하한의 L 단계마다 확인을 대체).
- 글쓰기 L의 핵심 섹션 먼저·구조안 비교와 독자 검토는 외부 공유·의사결정 문서에만 적용한다.
- 위임 150줄 규칙, 5-16 #4·#5, 기존 task-type 9행 표, 5-13의 "지렛대"·"같은 교정 두 번이면 규칙화" 원칙, 기록 필드 track·tier는 삭제한다. 작업자 지시문 핵심 줄은 지시문 틀 한 곳에만 둔다.
- ha 상한은 16KB 유지를 목표로 하고, 실측 뒤 넘을 때만 다시 묻는다(9-D #8 대체).
- 효력을 잃은 글(5-5 병렬·worktree, 5-12 "모든 L", 5-13 초안)은 구현 스펙에서 제외한다.

다음: 9-A~9-F를 반영한 간결한 구현 스펙을 10절로 새로 쓰고, 그 스펙만 보고 구현한다.

## 10. 구현 스펙 (2026-10-28, 9-A~9-F 반영)

구현은 이 절만 기준으로 한다. 2~9절의 내용 중 이 절에 없는 것은 효력이 없다. 각 항목 끝의 괄호는 근거가 된 결정이다. `[메인]`은 사용자가 준 방향에서 메인이 도출한 항목이라 이 스펙 확인 때 따로 볼 대상이다.

### 10-1. 바꾸지 않는 것

- 상태 흐름 CAPABILITY_RESOLVE → OBSERVE → IDENTIFY_DECISIONS → QUESTION_GATE → COMMIT_INTENT → ROUTE_AND_EXECUTE → VERIFY. S/M/L 강도와 CLASSIFY 상태는 만들지 않는다. (9-F)
- 네 진입 파일에 같은 글자로 둔 QuestionGate, `must_ask`·`decision_quality`·`skip` 분류, 질문 레버 예산. (v0.1.27)
- RuntimeParallelism과 dependency_edges, Observation 틀. (9-16)
- 수정 루프 5회 에이전트 점검·10회 사용자 점검, 횟수만으로 멈추지 않음, 새 증거 없이 반복 금지. (v0.1.25, 9-F)
- 커밋·병합·푸시는 사용자 요청 시에만. 회사 인프라는 이름으로 적고 개인 도구는 `~/.claude/wrxp/sources.md`에 둔다. (R-014)

### 10-2. 새로 넣는 규칙

**R1. 무거운 경로.** 평소 절차는 모델이 판단한다. 다음 중 하나에 해당할 때만 `references/tracks.md`의 해당 트랙 "무거운 경로" 줄을 따르고, 들어갈 때 이유를 한 줄로 보고한다. (9-F)
- 되돌리기 어려운 변경 또는 외부 공개
- 공유 계약 변경 (정의는 R5)
- 재발 버그
- 사용자가 지정한 경우 ("제대로 해", "무겁게" 등)

무거운 경로에서는 tracks.md의 해당 단계를 작업 목록에 옮긴다. (R-022)

**R2. 질문.**
- `answer_owner`에 `experiment`를 더한다. 판별 문장은 "사용자가 말해 줘야만 아는가, 해 보면 관찰되는가"다. `experiment`는 묻지 않고 PROBE로 확인한다. 실험은 읽기 전용이거나 버릴 수 있는 곳에서만 하고, 외부 변경이 필요하면 `must_ask`다. 실험으로 결론이 나지 않으면 그 결과를 붙여 묻는다. (5-2, 9-F)
- 실행 중 질문 `mid_run_decision`: COMMIT_INTENT 이후에 드러난 판단이 "취향·제품 판단이고, 결과물을 바꾸거나 나중에 바꾸면 재작업이 큰 경우"이면 레버 예산과 관계없이 `/ha`에서도 묻는다. 위임 전 사전 질문, staged-development 개요 확인, 프로토타입 전환 질문, 같은 패턴 발견 시 함께 고칠지가 여기에 속한다. 비슷한 판단은 한 번에 묶는다. (9-1, 9-D #1·#2, 9-11, 9-19)
- QUESTION_GATE에서 이미 기본값으로 정한 항목은 새 증거 없이 다시 묻지 않는다. (9-D #1)
- 묻는 방식: 질문 도구로 묻고 그 자리에서 멈춘다. 질문 도구가 없는 런타임에서는 글로 질문 하나를 쓰고 턴을 끝낸다. 이미 띄운 백그라운드 작업은 두고 결과는 답을 받은 뒤 반영한다. (9-1, 9-D)
- 시안 2~3개는 실제로 물을 때만, 취향 판단(레이아웃, 문체, 구조)에 붙인다. (9-9)
- 기본값 하한: 묻지 않고 대신 정한 판단을 결과의 `defaults_taken`에 적는다. 그중 취향 판단이 있으면 결과를 내기 전에 목록을 보여 주고 확인받는다. 기술 기본값뿐이면 "다르게 원하면 이렇게 말하면 된다"와 함께 보고만 한다. (9-D #9, 9-F, 5-2 추가안 6 흡수)

**R3. 실패.** 같은 전제로 거듭 실패하면 다음 시도 전에 그 전제를 한 문장으로 적고 먼저 확인한다. 숫자 상한과 카운터는 두지 않는다. (9-F)

**R4. 위임.**
- 넘기는 비용보다 메인 맥락을 아끼는 이득이 클 때 작업자에게 위임하고, 사소한 수정은 메인이 직접 한다. (9-F)
- 메인이 직접 하는 일: 버그의 재현과 가설 좁히기, 조사, 데이터, 글쓰기. 버그는 수정만 위임 대상이다. (9-D #4)
- 쓰기 작업자는 병렬로 돌리지 않는다. 병렬은 읽기 전용 작업(조사, 검토)에만 쓴다. worktree 격리는 쓰지 않는다. (9-D #6)
- 작업자 종류는 `general-purpose`, 모델은 기존 code-delegation 규칙(opus 기본, 가벼운 일은 sonnet)을 따른다. (5-16 #1)
- 질문 때문에 멈춘 작업자는 같은 작업자를 이어서 쓴다(Claude Code는 SendMessage, Codex는 `codex exec resume`). (9-D)
- 작업자 지시문 틀에 다음 핵심 줄을 직접 넣는다. 이 문구는 지시문 틀 한 곳에만 둔다. (9-B 4-5, 9-F)
  1. 취향·제품 판단이 새로 나오면 그 부분에서 멈추고 질문을 돌려보낸다.
  2. 커밋하지 않는다.
  3. 새 증거 없이 같은 시도를 반복하지 않고, 같은 전제로 거듭 실패하면 전제부터 확인한다.
  4. 대체물로 확인한 것과 결론이 안 난 것은 통과로 보고하지 않는다.
  5. 대신 정한 판단은 반환 보고에 `defaults_taken`으로 적는다.
- 작업자 보고 확인: 보고한 변경 파일을 `git diff --stat`과 맞추고, 범위 밖 파일, 약해진 테스트, 설정·권한 변경이 걸린 부분만 읽는다. 메인이 확인하지 않은 내용은 "작업자 보고 기준"으로 표시한다. (5-16 #6 축소안에서 150줄 규칙만 뺌) `[메인]`

**R5. 검증.**
- 대체물(다른 환경, 목업, 자기 보고, 요약본)로 확인한 것은 통과가 아니다. 결과 판정에 `inconclusive`(판단 불가)를 두고, 판단 불가는 무엇을 확인하지 못했는지 적는다. (1절, 5-12, 9-F)
- 공유 계약 정의(ha 본문 한 곳): API, DB 스키마, 공유 타입, 전송 형식, 공용 모듈, 설정, 문서·규칙 파일의 삭제·이동. (9-D)
- 공유 계약을 바꾸면 새 맥락 sonnet 검토를 1회 붙인다. 검토 브리프에 "변경이 안전한 근거 사실 하나를 찾아 실행으로 확인하고, 검색이 닿지 않는 사용처(설정, 다른 언어, 전송 형식)를 본다"를 넣는다. 이것이 blast-radius를 대신한다. 이 경우는 "자동 재검증하지 않는다" 문구의 예외로 네 곳(ha Requirements, verification.md 머리, README, global-rules Coding 줄)에 적는다. (9-2, 9-F)
- 실제 화면 확인 순서: 프로젝트 실행 스킬 → 내장 `run` → 브라우저·시뮬레이터 도구. 모두 안 되면 이유를 적고 판단 불가로 보고한다. (9-14)
- 사소한 단일 수정은 ha 본문의 검증 두 줄(실제 경로로 1회 확인, 대체물 확인은 통과 아님)로 끝내고 verification.md는 읽지 않는다. (3-3 검토) `[메인: S가 없어져서 "사소한 단일 수정"으로 옮김]`

**R6. 커밋 순서.** 재현 테스트는 수정보다 먼저 쓰고, 수정 전 실패 출력을 보고에 남긴다. 커밋은 사용자가 허용했을 때만 그 순서로 한다. (9-4)

**R7. 설계 두 줄.** "쓰기 전에 뼈대를 정한다(코드는 데이터 형태와 경계, 문서는 독자·핵심 메시지·목차)", "같은 우회가 반복되면 뼈대를 다시 설계한다". 별도 단계나 파일을 두지 않는다. (9-F)

### 10-3. `references/tracks.md` 초안 (트랙당 3~5줄)

각 트랙은 평소 줄과 "무거운 경로" 줄로 나눈다.

**버그**
- 원인이 확실하면 고치고 원래 증상이 나던 경로로 1회 확인한다.
- 원인을 모르면 직접 재현하고, 남은 가능성을 가장 많이 가르는 관찰부터 한다. 상태를 모르면 추측하지 말고 로그나 계측으로 읽는다.
- 증상이 보인 곳이 아니라 처음 잘못된 지점을 고친다. 증거가 정당화하는 최소 수정만 하고, 반박된 가설 때문에 넣은 코드는 되돌린다.
- 무거운 경로(재발 버그 등): 재현 테스트를 먼저 쓰고(R6), git 이력에서 언제·왜 바뀌었는지 본다. 같은 패턴을 다른 곳에서 찾으면 위치 목록을 붙여 함께 고칠지 묻는다.

**기능**
- 데이터 형태와 경계를 먼저 정한다. 지금 모양이 단순하고 자랄 가능성이 낮으면 추상화를 넣지 않는다.
- 실제 화면·실행 경로에서 확인한다. 테스트 기대값은 요구사항에서 가져오고 코드 실행 결과에서 베끼지 않는다.
- 코멘트는 코드가 보여 줄 수 없는 이유만 남긴다.
- 무거운 경로: staged-development로 진행한다. 공유 기반을 바꿔 모든 사용처 반영이 필요하면 위치 목록을 붙여 묻는다.

**조사** (읽기 전용)
- 코드는 바꾸지 않는다. 변경이 필요하면 보고한 뒤 버그·기능으로 넘긴다.
- 근거마다 `파일:줄`이나 문서 위치를 붙이고, 확인된 사실·추론·모르는 것을 섞지 않는다.
- 이유 질문은 git 이력부터 보고, 조직 맥락이 필요하면 질문에 맞는 출처(Slack, Notion, magma, worxsales MCP, Metabase, Tableau, `~/.claude/wrxp/sources.md`)만 고른다. 넓은 탐색의 위임은 search-delegation 기준을 따른다.
- 변경을 앞둔 조사는 유지할 것·바꿀 것·피할 것·위험으로 정리해 넘긴다.

**글쓰기·기획서**
- 독자가 읽고 무엇을 하는지, 핵심 메시지 한 문장, 목차를 먼저 정한다.
- 수치·고유명사·날짜·링크는 원 출처와 대조한다.
- `shared/writing-rules.md`를 쓰면서 지키고, 한국어 산출물은 마지막에 `wrxp:korean-polish`로 교정한다. Slack·DM 공유 글은 structured-share-thing이 맡는다.
- 무거운 경로(외부 공유·의사결정 문서): 구조안 2개를 비교해 합의하고, 핵심 섹션 하나를 먼저 맞춘 뒤, 작성 맥락을 모르는 sonnet이 독자 입장에서 읽는다.

**데이터·수치**
- 답에 기간·필터·단위·출처를 붙인다. 0건이거나 비정상적으로 크면 조회 조건부터 의심한다.
- 비교·원인 분석은 정의, 실제 계산(행 수, NULL, 조인 중복), 다른 경로 교차 확인을 실행으로 확인한다. 판정은 증가·감소, 차이 없음, 판단 불가 중 하나다.
- 성능은 제한 요인을 찾고, 선택을 위한 비교는 반복 측정해 범위를 쓴다.
- 무거운 경로(의사결정·외부 보고용 수치): 보고 아래에 지표 정의 표(분자·분모·기간·필터·원천)와 쿼리를 붙이고, 새 맥락 에이전트가 원천에서 다시 계산한다. 다르면 1회 조사하고, 그래도 다르면 두 값과 차이 후보를 적어 판단 불가로 보고한다.

**리팩터링**
- 동작은 바꾸지 않는다. 버그나 새 동작은 떼어 낸다.
- 기존 테스트가 동작을 덮지 않으면 먼저 동작 고정 장치(테스트, 출력 비교)를 만든다. 타입 검사와 린트는 고정 장치가 아니다.
- 빼고 나서 더한다. 호출처를 옮기고 옛 API는 같은 변경에서 지운다(외부 의존은 예외). 이름을 바꾸면 문자열·문서·주석에 남은 옛 이름을 검색한다.
- 읽는 부담이 줄지 않았으면 되돌린다. 무거운 경로: staged-development로 진행한다.

**프로토타입**
- 산출물은 결정이다. 정할 결정을 한 문장으로 적고, 결정이 없으면 기능으로 보낸다.
- 저장소 밖 임시 폴더에서 변형 2~3개를 빠르게 만들고, 실제로 관찰한 근거(스크린숏, 실행 결과)로 추천한다.
- 외부 공개와 운영 데이터 쓰기는 하지 않는다. PROBE에서 넘어올 때는 먼저 "이 결정을 위해 프로토타입을 만들까요?"를 묻는다.

**맞춤 절차**
- 맞는 트랙이 없으면 반증 가능한 완료 조건과 단계별 확인 방법을 먼저 적는다.
- 운영 스크립트는 다시 실행해도 같은 결과가 나오게 한다.
