# 실행 환경 준비 (2026-10-06 확인, 2026-10-23 보완)

## QA 작업 폴더
QA 작업 폴더(QA_HOME)는 시나리오·원천·결과가 있는 폴더입니다. 없으면 `worxsales-qa-bootstrap`으로 만듭니다. 폴더 구성의 정본은 bootstrap 스킬의 [작업 폴더 구성](../../worxsales-qa-bootstrap/references/workspace.md)입니다. `config.json`에는 다음 값이 있습니다.

| 키 | 의미 |
|---|---|
| scenario_db_id | Notion 「WorxSales 테스트 시나리오」 DB ID |
| desktop_worktree | 빌드에 쓴 desktop worktree. playwright-core를 여기서 불러옴 |
| app_path | 빌드한 WorxSales.app |
| api_origin | 앱이 접속하는 백엔드 |
| cdp | 이 폴더가 가리키는 앱 슬롯의 CDP 주소(기본 http://127.0.0.1:9333) |
| build | 결과 JSON의 build 값으로 쓰는 문자열 |

시나리오 원본은 `scenarios/<메뉴>/*.json`, 원천 문서는 `sources/`, 실행 결과는 `runs/<run_id>/`에 둡니다. 실행자는 시나리오 원본으로 만든 배치 파일을 읽습니다. 기능정의서·목업이 바뀌면 실행 전에 `sources/`를 다시 받고, 바뀐 화면의 시나리오를 고친 뒤 Notion DB에도 동기화합니다. 내용이 바뀐 행의 이전 결과는 옛 기준이므로 새 기준으로 다시 실행합니다. Notion 자격 증명은 bws의 `NOTION_API_KEY`이며, `bws-run`은 인자를 다시 나누므로 래퍼 스크립트로 실행합니다.

## 앱 빌드와 실행
```shell
cd <QA_HOME>
sh <skill>/scripts/build_dev_app.sh <desktop 저장소> <빌드 폴더>/desktop-dev-<커밋>
sh <skill>/scripts/launch_app.sh     # 혼자 실행할 때만. ready / login needed
```
- develop 최신 앱은 로그인 화면에서 연결 환경(DEV/STG/PRD)을 고릅니다. 고르지 않고 로그인하면 의도하지 않은 환경에 붙을 수 있으므로 매번 확인합니다. 2026-10-09 기준으로 DEV에 회원·그룹 데이터가 더 많고 열린 화면도 많습니다. STG는 고객 데이터가 필요한 행을 다시 돌릴 때만 따로 씁니다. PRD는 고르지 않습니다.
- 로그인은 사내 Keycloak SSO(포탈 계정)입니다. 앱에는 입력창이 없고 기본 브라우저가 열립니다. 백엔드는 계정 이메일로 MAGMA 재직 사원을 찾습니다.
- 앱의 「로그인」·「다시 시도」 버튼과 브라우저에서 이미 로그인된 본인 계정 고르기는 실행자가 합니다. 비밀번호·MFA 입력은 사용자가 합니다.
- 토큰은 앱 메모리에만 있습니다. 앱을 다시 켜면 다시 인증해야 합니다. 브라우저에 Keycloak 세션이 남아 있으면 「다시 시도」로 통과하며, `launch_app.sh`가 이 버튼을 누릅니다.
- `worxsales-backend.dev.worxphere.io`는 사내망 DNS에서 조회되지 않았습니다. 같은 dev 백엔드가 `worxsales-backend.dev.jobko.io`로 응답하므로, 빌드 스크립트가 이 주소를 기본값으로 쓰고 앱의 접속 허용 목록에는 worktree 안에서만 추가합니다.
- 세션은 몇 시간 쉬면 끊겨 로그인 화면으로 돌아갑니다. DEV를 고르고 「다시 시도」·「로그인」을 누르면 브라우저 SSO로 다시 들어갑니다.
- 앱을 조작할 때는 `scripts/app.mjs`만 씁니다. CDP 연결을 끊을 때 `browser.close()`를 부르면 로그인된 앱이 닫힐 수 있으므로 쓰지 않습니다.
- `app.mjs` 명령은 `timeout 60`(Homebrew coreutils)으로 감쌉니다. 응답 없는 명령을 무한정 기다리다 실행자가 멈춘 사례가 있습니다.
- 사용자 브라우저(예: CDP 9222)는 탭이 많으면 Playwright `connectOverCDP`가 멈출 수 있습니다. 브라우저 작업은 조율자가 raw CDP로 하고, 실행자는 앱 밖의 브라우저를 조작하지 않습니다.

## 역할
- 모든 재직자는 영업자입니다. MAGMA 직책(JIKCHAK 3·6)이면 영업팀장·관리자가, REP 구분이 S이면 영업운영이 붙습니다.
- dev·stg에서는 권한 관리자가 자기 자신에게 팀장·영업운영 역할(「조회만」/「수정 가능」, 최대 90일)을 부여할 수 있습니다. 부여는 공용 dev 데이터 변경이므로 사용자가 허락한 실행에서만 합니다.
- 로그인 계정의 역할과 담당 회원은 계정마다 다릅니다. 첫 실행 전에 「역할 전환」 목록과 본인 담당 회원(서비스별 담당이 본인)을 화면에서 확인하고, 조율자가 레인 WORKER.md에 적습니다. 담당 데이터가 없으면 「본인 담당」 행은 「실행 불가」(사전조건 데이터 없음)입니다.
- 담당은 서비스(JK/AM)마다 다를 수 있습니다. 저장 전에 그 서비스 문맥의 담당자가 본인인지 화면에서 확인합니다.
- 역할 확인·판정·부여 규칙은 [역할과 권한](roles.md)을 따릅니다.

## 화면 상태 메모
- develop 초기 빌드에서는 상단 프로필과 홈 대시보드가 합성 표시값이었습니다. 표시된 이름이 로그인 사용자와 다르면 합성값으로 보고 판정 근거로 쓰지 않습니다.
- 「합성 예시」「준비 중」 표시가 있는 영역은 실데이터가 연결되지 않은 것이므로 「미구현」으로 판정합니다.

## 병렬 실행
- 실행자마다 앱 슬롯 하나를 둡니다. 슬롯마다 설정 폴더(`.slots/app-<port>/config.json`에 자기 CDP 포트)와 사용자 데이터 폴더(`.userdata/<port>`)를 따로 쓰고, 실행자는 받은 슬롯 외의 앱을 건드리지 않습니다. 앱 조작은 `QA_HOME=<슬롯 설정 폴더> node <skill>/scripts/app.mjs ...`로 합니다.
- 실행자는 앱을 끄거나 다시 띄우지 않습니다. 로그인 화면이 나오면 「로그인」·「다시 시도」만 누릅니다. 앱 교체(새 빌드 배포)는 조율자가 실행자 사이에 합니다.
- 같은 계정을 여러 앱이 함께 쓰므로 다른 실행자가 만든 QA 기록이 목록에 보일 수 있습니다. 고치지 않고, 개수·목록 확인에 영향을 주면 details에 적습니다.
- 결과 폴더는 공유합니다. 자기 배치 행의 결과 파일과 PNG, 자기 임시 폴더(`runs/<run_id>/_tmp/<배치 이름>/`) 외의 파일은 지우거나 옮기거나 덮어쓰지 않습니다. 와일드카드 `rm`은 쓰지 않습니다. `pkill`·`killall`처럼 이름으로 프로세스를 끄는 명령도 쓰지 않습니다. 다른 실행자의 `app.mjs` 명령까지 끊기기 때문입니다. 자기 명령이 멈추면 기다리거나 그 PID만 끕니다. 세션 공용 scratch 폴더에는 임시 파일을 두지 않습니다.
- 배치 번호는 이미 있는 가장 큰 번호 다음을 씁니다. 옮겨 둔 배치 파일의 번호도 다시 쓰지 않습니다.
- 이전 실행자가 남긴 작업 탭은 첫 행 전에 닫습니다.
- `app.mjs`의 시간 초과는 그 행의 차단 사유로 기록합니다.
- 실행자는 Notion에 직접 게시하지 않고 결과 파일만 남길 수 있습니다. 조율자가 모아서 게시하면 앱 슬롯이 게시를 기다리며 놀지 않습니다.
- 최신 빌드를 따라갈 때는 결과의 `build`에 그 앱이 실제로 쓰는 빌드 문자열을 넣습니다. 같은 행을 새 빌드로 다시 실행하면 DB에는 최신 빌드의 결과가 보이고, 이전 결과는 「이전 실행 기록」으로 내려갑니다.
