# 배포 경로와 병존 검토

Jenkins와 GitLab CI의 병존은 정상적인 전환 상태일 수 있다. GitLab CI가 처음 도입됐거나 일부 환경에서만 시범 운영 중이면, 그 사례를 전사·전 환경의 확정 표준으로 바꾸지 않는다. 이 문서는 요청서를 검토하는 기준이며 CI 구현·배포·중지 명령이 아니다.

## 먼저 현재 경로와 요청 경로를 구분한다

이번 요청에 관계된 서비스·환경별로 아래 관계를 파악한다. 여러 경로가 섞였을 때만 표로 출력하고 단순한 기존 Job 조사에는 한 문장으로 충분하다. 다른 환경까지 불필요하게 조사하지 않는다.

| 서비스·환경 | 현재 지원되는 경로와 근거 | 실제 최근 실행·적용 근거 | 이번 목표/변경 | 전환 상태 |
| --- | --- | --- | --- | --- |
| 해당 대상 | 담당팀 합의/가이드 + Job/Pipeline/App 링크 | 실행 결과, 배포된 산출물 등 확인된 범위 | 유지·신규·이관·조사 | 미착수·준비·시범·전환·기존 경로 종료 중 확인된 상태 |

**빌드·테스트를 지시하는 도구 → 실제 실행기 → 산출물 저장소 → 배포 설정을 갱신하는 주체 → 배포를 적용하는 도구/대상**을 구분한다. GitLab CI 안에서 CodeBuild가 실행될 수도 있고, Jenkins와 GitLab CI 모두 ArgoCD를 이용할 수도 있다. 확인된 관계만 적는다. GitLab과 ArgoCD를 상호 대체하는 배포 방식으로 분류하지 않는다.

다음은 단독으로 배포 경로의 근거가 되지 않는다.

- GitLab에 저장소나 `.gitlab-ci.yml`이 있음: SAST 전용일 수 있다.
- Pipeline이 초록색임: 빌드·push·배포 job이 실행됐는지, skip/manual 상태인지 확인해야 한다.
- 오래된 Jenkins URL이 있음: 현재도 사용·지원 중인지 별도 확인이 필요하다.
- 다른 프로젝트의 최신 가이드: 적용 대상·도입 시점·예외가 다를 수 있다.

근거가 모자라면 “현재 경로 미확인”으로 표시하고 실제 최근 Job/Pipeline과 대상 환경을 묻는다. Jenkins에서 동작했다는 사실이 새 GitLab 실행 Role의 권한을 증명하지 않으며, GitLab 성공이 Jenkins 자격 증명의 유효성을 증명하지 않는다.

## 요청 유형별 필수 입력

### 기존 Jenkins 유지·장애·변경

현재 서비스에 Jenkins 경로가 지원된다는 근거가 있으면 그 범위에서 검토한다. 이번 요청과 무관한 GitLab CI 전환을 선행 조건으로 붙이지 않는다.

- 해당 Jenkins Job과 실패/변경 대상 build URL, 환경, 저장소·브랜치/모듈, 실제 실패 단계.
- 원인 판단에 필요한 경우 Pipeline script/Jenkinsfile의 위치, 실행 Agent, 관련 권한 식별자와 변경 내역. 비밀값은 제외한다.
- build/test, 이미지 push, 배포 설정 갱신, 동기화, 앱 기동 중 어느 단계인지 분리한다. 이미지 빌드 전 Gradle 실패에 ECR·ArgoCD 설정 변경을 확정 해결책으로 요구하지 않는다.
- 기존 Job을 수정할지 별도 Job을 만들지, 영향을 받는 환경과 담당을 명시한다. 단순 조사 접수에 이 정보를 모두 강제하지 않는다.

### 신규 GitLab CI 구성·실패

해당 서비스·환경에 적용할 경로가 합의됐는지 확인한다. 최초 도입이라 합의가 없으면 지원 방식·담당 범위를 결정하는 검토 문의로 작성한다.

- 저장소·ref, 해당 CI 파일/컴포넌트와 적용 버전, Pipeline/Job URL, 실제 실행할 단계와 배포 대상.
- 필요한 경우 Runner/CodeBuild 등 실행기, 빌드 이미지 저장 위치, 실행 Role·Secret 조회·대상 리소스 권한. 이름이나 최신 버전을 임의로 채우지 않는다.
- 개발팀이 수정할 애플리케이션 CI와 인프라팀이 관리할 공용 템플릿·배포 설정의 경계를 구분한다. Jenkins 설정을 새 CI에 복사했다는 이유로 동일한 권한·동작을 보장하지 않는다.
- 현재 준비 단계에 아직 필요하지 않은 새 ECR ARN·Runner ID·최종 배포 성공을 구성 접수의 조건으로 요구하지 않는다. 완료될 때 받아야 할 정보로 구분한다.

### Jenkins → GitLab CI 이관·환경별 병존

`기존 유지`, `신규 경로 준비`, `검증 후 전환`, `기존 경로 중지/삭제`를 구분한다. DEV 시범 성공을 STG/PRD 전환 승인으로 확대하지 않는다.

영향 있는 전환/기존 경로 종료 요청에는 다음을 확인한다. 준비·검토 요청이면 미결 사항과 결정 역할로 남긴다.

1. **환경별 범위:** 어떤 서비스·환경만 바꾸며 어디는 기존 경로를 유지하는가?
2. **작업 대응 관계:** 기존 build/test/push/deploy와 필수 수동 승인·배포 관련 작업이 새 경로의 어느 단계에 대응하는가? 해당 작업이 없으면 추가하지 않는다.
3. **중복 실행 방지:** 두 경로가 같은 환경·이미지 태그·배포 설정을 갱신할 수 있는가? 그렇다면 전환 시 사용할 경로와 기존 트리거 중지 시점·담당을 합의한다. 동일 대상을 동시에 갱신하는 병렬 배포를 검증 방법으로 제안하지 않는다.
4. **실제 적용 근거:** 새 경로가 만든 커밋/이미지 tag 또는 digest가 해당 배포 설정과 실행 앱에 적용됐는지, 필요한 동작 검증을 했는지 확인한다. 시스템이 제공하는 동등한 추적 근거를 사용하며 특정 도구를 강제하지 않는다.
5. **권한·설정 차이:** 실행 주체, 자격 증명 참조, 배포 대상, 환경변수/Secret, 네트워크 등이 바뀌는 부분만 확인한다. 권한 전체 복제나 공유 설정 직접 수정을 해결책으로 쓰지 않는다.
6. **전환·복구·종료:** 반영 신호, 확인 역할, 실패 시 사용할 경로/버전과 복구 담당, 기존 Job의 보존·중지·삭제 조건을 구분한다. 새 경로와 앱 검증 전 기존 Job 삭제를 완료 요청으로 내지 않는다.

검토 결과와 제출 문안 모두 환경별 상태를 유지한다. 예: “DEV GitLab CI 시범 검증 중, STG/PRD Jenkins 유지.” 이를 “GitLab CI 전환 완료”로 축약하지 않는다.
