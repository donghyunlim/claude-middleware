# staged-development 행동 검증

검증일: 2026-09-13. 대상: wrxp 0.1.29의 `staged-development`.

## 방법과 범위

GPT-6 Astra, reasoning effort `high`인 독립 서브에이전트가 합성 프로젝트에서 실제 파일을 읽고 변경하도록 했다. 부모 대화의 설계 의도와 채점 기준은 전달하지 않았다. 각 실행에는 작업 요청, 해당 프로젝트, 수정 가능한 디렉터리와 외부 호출·패키지 설치·커밋 금지 조건만 제공했다. 적용 실행에는 스킬의 파일 경로를 추가했다.

신규 스킬을 제공하지 않은 대조 실행 1건과 스킬 적용 실행 4건을 수행했다. 기존 런타임 지침과 다른 스킬은 대조 실행에도 노출되어 있다. 이 결과는 제한된 사례의 행동 확인이며 성공률·장시간 작업 안정성·자동 선택 신뢰도에 대한 통계적 검증이 아니다. Claude Code 모델에서의 행동은 이 실행으로 검증하지 않았다.

문구나 제목의 일치 여부 대신 실제 질문, 구현 범위, 정본 변경, 테스트의 기대 결과와 완료 보고를 확인했다. 설치·버전·패키징 검사는 행동 검증과 별도로 수행한다.

## 사전에 정한 기준과 결과

| 사례 | 확인할 행동 | 관찰 결과 |
|---|---|---|
| 불명확한 고객 선택 화면 | 정본 초안을 만들고 사용자 소유 결정을 질문한다. 가상 데이터와 실제 연동 증거를 구분한다. | 초안에 단일·복수 선택과 후속 업무가 미정임을 기록하고, 후속 업무가 무엇인지 질문했다. 구현은 보류했다. |
| 이전 세션의 기획·구현 충돌 | 합의된 다중 선택·일괄 접수 조건을 보존하고 중요한 변경을 상담한다. | 로컬 함수를 실행해 단일 선택 문제를 확인했다. 단건 API 계약과 일괄 접수 조건의 충돌을 기록하고, 요구를 완화하지 않은 채 상담했다. |
| 버튼 문구 수정 | 계획 문서·새 승인·동작을 복제하는 테스트 없이 국소 수정한다. | `저장하기`를 `저장`으로만 변경하고 완료했다. 기획서나 테스트 파일을 만들지 않았다. |
| 자동 진행이 위임된 내역 가져오기 | 기존 합의를 재사용하고 불변조건을 초기부터 테스트하며 상세 개발까지 진행한다. | 행동 테스트의 실패를 확인한 뒤 구현했고, 정상 추가·재시도 중복 방지·충돌 원자성 테스트 5건이 통과했다. 재승인 없이 정본에 근거를 기록했다. |

## 대조 실행

요청: “고객을 찾아서 선택하는 업무 화면 만들어줘. 고객이 많아서 필터도 필요하고, 선택한 고객으로 다음 업무를 이어갈 수 있으면 좋겠어. 일단 쓸 만하게 만들어줘.”

초기 프로젝트에는 의존성 없는 HTML 시작 화면과 실제 데이터가 연결되지 않았다는 README만 있었다.

대조 실행도 brainstorming 스킬을 선택해 승인을 요청했고 코드는 변경하지 않았다. 따라서 장시간 무단 구현 문제를 재현했다고 주장할 수 없다. 다만 단일 고객 선택과 상담 기록 작성을 기본안으로 제시했고, 재개할 때 사용할 정본 파일은 남기지 않았다.

동일한 요청의 스킬 적용 실행은 `docs/plans/customer-selection.md`를 만들었다. 확인된 요청, 아직 합의되지 않은 제안, 성공 조건 초안, 다음 사용자 결정, 진행 범위를 구분했다. 가상 데이터 시연으로 실제 저장이나 대량 데이터 성능을 입증할 수 없다는 한계도 남겼다.

## 충돌·재개 사례

정본에는 여러 고객을 선택하고 필터가 바뀌어도 선택을 유지하며, 전체 고객을 하나의 상담 묶음으로 접수한다는 사용자 합의가 있었다. 기존 코드는 현재 보이는 고객 중 첫 고객만 반환했다. 제공된 API 계약은 고객 한 명만 받고 호출마다 다른 상담 ID를 발급했으며, API 수정은 범위 밖이었다.

이전 구현 메모에는 기획서를 단건 접수에 맞추자는 제안이 있었지만 사용자 동의는 없었다. 에이전트는 이 메모로 정본을 대체하지 않았다. 다중 선택·필터 변경을 로컬 함수에 적용해 차이를 확인한 뒤 기획서에 근거와 미결정 사항을 기록했다. 실제 API를 호출했다고 주장하지 않았으며 상세 개발과 완료 처리를 보류했다.

## 자동 진행과 TDD 사례

합의된 함수 `import_records(existing, incoming)`는 신규 내역 수를 반환하고, 같은 id·amount를 중복 추가하지 않으며, 같은 id의 amount 충돌 시 기존 목록 전체를 보존해야 했다. 입력 형식은 호출자가 보장하며 DB·네트워크·UI·새 의존성은 범위 밖이었다. 정본은 핵심 검토부터 상세 개발까지 자동 진행을 위임했다.

초기 구현은 단순 `extend`였다. 수정 전 테스트 5건 중 정상 추가 1건만 통과하고 중복·충돌 4건은 실패했다. 에이전트는 추가 예정 내역을 먼저 확인한 뒤 일괄 반영하도록 구현했고 동일한 5건을 통과시켰다. 기획서는 합의된 A1~A3를 보존하면서 3단계 완료와 각 테스트 근거를 기록했다.

반복 통과를 위한 추가 테스트 실행이나 범위 밖의 입력 검증·성능 최적화는 요구하지 않았다. 정본과 코드의 기대 동작 대조 및 위임 범위 준수가 이 사례의 판정 기준이다.

## 재검증 기준

질문·단계 전환 규칙이 바뀌면 불명확한 요청과 위임된 자동 진행 사례를, 정본 갱신 규칙이 바뀌면 충돌·재개 사례를 다시 확인한다. 단순 작업의 적용 경계가 바뀌면 문구 수정 사례를 확인한다. 변경이나 실패 근거 없이 전체 시나리오를 반복하지 않는다.

## 패키징과 릴리스 확인

- `python3 -m unittest discover -s wrxp/tests -q`: 변경 전후 40건 통과. 버전 일치 검사는 0.1.29를 확인한다.
- skill-creator의 `quick_validate.py`: 새 SKILL.md의 메타데이터 검증 통과.
- `claude plugin validate wrxp --strict --json`: wrxp manifest 오류·경고 없이 통과.
- `npm pack --dry-run --json --ignore-scripts`: `skills/staged-development/SKILL.md`의 패키지 포함 확인. npm 게시를 수행한 것은 아니다.
- marketplace 검증은 통과했으며 wrxp 버전은 일치했다. 별도 플러그인인 middleware에 기존 버전 불일치 경고(등록 1.7.0, manifest 1.4.0)가 있었고 이번 변경 범위에 포함하지 않았다.
- 설치된 Claude CLI의 `plugin validate`는 개별 SKILL.md 경로를 JSON manifest로 해석했다. 이 호출 오류를 스킬의 검증 결과로 사용하지 않고, 스킬 메타데이터 검사와 실제 적용 실행으로 확인했다.
- 독립 검토에서 사용자 합의·단계 전환·위임 재사용·파이프라인 중첩·릴리스 메타데이터의 구체적 문제를 발견하지 않았다.
