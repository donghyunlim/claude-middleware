# 쓰기 범위

실행 단계에서 작업자가 할 수 있는 쓰기 조작은 작업 폴더의 `refresh/write_scope.json`이 정합니다. 기본값은 executor와 같은 「조회·차단 확인만」이고, 이 파일은 사용자의 답으로만 넓어집니다.

## `refresh/write_scope.json`

```json
{
  "since": "YYYY-MM-DD",
  "envs": {"run": "DEV", "bold": ["DEV", "STG"], "never": ["PRD"]},
  "self": {"mail": ["<사용자 본인 메일>", "<plus 주소 가능>"], "phones": ["<본인 휴대폰>", "<본인 법인폰>"]},
  "allowed": ["…허용한 조작…"],
  "denied": ["…금지한 조작…"],
  "decisions": [
    {"date": "YYYY-MM-DD", "question": "무엇을 물었는지", "answer": "사용자 답 원문", "by": "user"}
  ]
}
```

- 처음 만들 때는 bootstrap 스킬의 `assets/write_scope.json` 템플릿을 씁니다. 템플릿은 「조회·차단 확인만」이라 `allowed`가 비어 있습니다. 넓은 항목(QA- 테스트 데이터 저장, 본인 역할 부여, 본인 대상 발송 등)은 효력 없는 `_examples`에만 있고, 사용자가 답한 항목만 `allowed`로 옮깁니다.
- `self`의 메일·전화번호는 작업 폴더의 데이터입니다. 스킬 문서나 WORKER 틀에 적지 않고, 레인 WORKER.md를 만들 때 이 파일에서 옮깁니다. `self`가 비어 있으면 실제 발송·통화는 하지 않습니다.
- `decisions`에는 사용자 답을 **원문 그대로** 적습니다. AI가 추정한 허락은 적지 않습니다. 오타가 있어도 고치지 않고, 뜻을 해석해 `allowed`·`denied`에 반영한 문장을 따로 씁니다.
- 나중 결정이 앞의 `denied` 항목을 풀면 그 항목을 `denied`에서 빼거나 「(YYYY-MM-DD 허용으로 대체)」를 붙여, 두 목록이 서로 어긋나지 않게 합니다. 작업자는 WORKER.md의 「Write scope」 절만 읽으므로 그 절에는 지금 유효한 규칙만 씁니다.

## 바뀌지 않는 선

사용자가 따로 넓히지 않는 한 다음은 어느 환경에서도 하지 않습니다.
- 앱 밖의 실제 사람에게 닿는 조작: 사용자 본인이 아닌 받는 사람에게 메일·문자·팩스·Slack 보내기, 본인이 아닌 번호로 전화 걸기
- PRD 환경 로그인·조작(로그인 화면의 연결 환경은 DEV, 필요할 때만 STG)
- 다른 사람에게 권한 부여
- 파일 저장 창을 여는 버튼(네이티브 창이라 자동화로 닫을 수 없음), UI 시연 모드

## DEV·STG의 과감한 시험

사용자가 `envs.bold`에 DEV·STG를 허용하면(2026-10-22 결정의 예), 그 환경에서는 다음도 해도 됩니다. 각 조작은 `allowed`에 적힌 것만 합니다.
- 다른 QA·테스트 사용자의 테스트 데이터 수정, 다른 담당 회원에 QA 레코드 저장
- 세그먼트 업로드 「적용하기」, 공통 과업 필터 저장(과업 배포)
- 담당 변경, 본인 권한 회수(순차 단계에서만, [조율 규칙](orchestration.md#역할-묶음))

앱 밖의 실제 사람에게 닿는 조작과 PRD는 이때도 금지입니다. 바꾼 레코드는 레인의 `_dev_data_created.txt`에 한 줄씩 적습니다.

## 본인에게만 닿는 조작 (이중 확인)

결과가 사용자 본인 계정·본인 담당 QA 데이터에만 미치면 허용 목록에 없더라도 실행할 수 있다고 사용자가 정했을 때(2026-10-22 결정의 예) 작업자는 다음을 지킵니다.
1. 실행 **전**에 영향 대상(레코드, 회원 담당, 작성자, 받는 사람, 공유 범위)을 화면에서 읽습니다.
2. 실행 **후**에 다시 읽어 다른 사용자·고객 데이터가 바뀌지 않았는지 확인합니다.
3. 결과 JSON의 `details.self_only_check`에 `{"before": "…", "after": "…"}`로 남깁니다.
4. 하나라도 다른 사람에게 닿을 수 있으면(팀 전체 배포, 공용 데이터 교체, 고객 발송·통화, 타인 레코드, 타인 권한) 하지 않고 「실행 불가」(이번 실행의 쓰기 범위 밖)입니다.

### 실제 발송·통화

- 받는 사람(받는 사람·참조·숨은 참조 전부, 문자·통화 번호)이 모두 `self`의 값일 때만 「발송」·「보내기」·「걸기」를 누릅니다.
- 누르기 **직전에** 받는 사람 칸을 `text`로 읽고 그림으로 남긴 뒤 `details.self_recipient`에 적습니다. 확인 창 없이 바로 보내지는 버튼이 많으므로 누른 뒤에 확인하면 늦습니다.
- 고객 회원 주소가 자동으로 들어가 지울 수 없거나 본인으로 바꿀 수 없으면 보내지 않고 「실행 불가」(받는 사람을 본인으로 바꿀 수 없음)입니다.
- 다른 사람이 작성한 견적·기록에서 「다음: 작성 및 발송」처럼 서버에 저장하는 단계로 넘어가지 않습니다. 쓰기 범위가 그 조작을 명시해 허용한 경우만 예외입니다. 발송 행은 본인이 만든 `QA-` 견적으로 합니다.

## 새로 쓰기 범위 밖이 된 행

- `history.py`가 회차마다 쓰기 범위 밖 행 집합을 만들고, 직전 회차에 없던 TC ID를 `write_blocked_new`에 넣습니다. 흔한 이유는 기획 범위 확장(새 발송·연동 화면)입니다.
- 보고에 TC ID와 막힌 조작을 조작별로 묶어 적고, **새로 막힌 조작마다 한 번만** 허용 여부를 묻습니다. 이미 답을 받은 조작은 다시 묻지 않습니다.
- 사용자가 허용하면 `allowed`에 조작을 더하고 `decisions`에 날짜·질문·답을 적은 뒤, 다음 실행에서 그 행만 큐에 넣습니다. 답이 없거나 애매하면 넓히지 않습니다.
- WORKER.md의 「Write scope」 절은 이 파일에서 옮겨 씁니다. `denied`에 걸리는 행은 「실행 불가」, 사유 「이번 실행의 쓰기 범위 밖」입니다(파일 저장 버튼은 「네이티브 저장 창(자동화 불가)」).
