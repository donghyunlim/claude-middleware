# Handoff

사용자가 요청한 시점에 현재 작업을 새 세션이 이어받을 수 있도록 한 문서로 기록한다. 핵심은 사용자의 의도 세트 세 가지와 AI 기획, 현재 상태, 문제점이다. 세션의 좋고 나쁨이나 "원래 무엇을 했어야 했다"는 판단은 쓰지 않고, 관찰된 사실과 근거를 담백하게 기록한다.

## 작성 원칙

- **사용자 의도와 AI 기획을 섞지 않는다.** 사용자가 말하거나 승인한 것은 의도(§1)에, AI가 제안·설계한 것은 기획(§2)에 쓴다. 사용자가 AI 제안을 승인했다면 승인한 내용 자체를 §1-2에 결정으로 옮긴다. 보고만 하고 사용자가 답하지 않은 제안은 승인으로 보지 않는다.
- **사실만 기록한다.** 문제는 증상·근거·확인된 원인 순으로 쓰고, 원인이 확인되지 않았으면 가설로 표시한다. 평가어(잘됨·잘못됨·아쉬움·교훈)와 회고를 쓰지 않는다. 관찰된 결과는 그대로 쓴다: "테스트 2개 실패(exit 1)"는 사실이고, "검증이 부실했다"는 평가다.
- **원문을 기준으로 한다.** 긴 세션은 앞부분이 요약·압축되어 기억이 부정확하다. 사용자 의도는 아래 절차의 원문 추출 결과에서 인용한다.
- **다음 세션이 알 수 없는 것을 쓴다.** 코드·커밋·문서에 이미 있는 내용은 위치만 남기고, 대화에만 있던 결정·맥락·세션 종속 자료는 본문에 옮긴다.
- 비밀값은 기록하지 않는다. 필요한 자격 증명은 키 이름과 조회 방법만 쓴다.
- 시각은 사용자의 현지 시간대로 쓰고 시간대를 표기한다. 추출 스크립트의 시각은 UTC다.

## 절차

1. **작업 디렉터리를 고정하고 새 작업을 멈춘다.** 호출 시점의 작업 디렉터리를 프로젝트 폴더로 기록해 두고, 이후 `cd`로 옮기지 않는다. 핸드오프 직전에 진행하던 작업이 끝났는지, 중간 상태인지를 확인해 §3에 그대로 기록한다. 핸드오프 자체는 §3에 쓰지 않으며, 남은 작업을 서둘러 마무리하지 않는다.
2. **사용자 원문을 확보한다.** 스크립트는 이 스킬의 기본 디렉터리(스킬을 불러올 때 표시되는 경로) 아래에 있다. 디렉터리를 옮기지 말고 절대 경로로 실행한다.

   ```bash
   python3 "<skill-dir>/scripts/user_turns.py"                    # 현재 세션을 자동으로 찾는다 (Claude Code·Codex)
   python3 "<skill-dir>/scripts/user_turns.py" --session-id <id>  # 다른 세션
   python3 "<skill-dir>/scripts/user_turns.py" --log <path.jsonl> # 로그 경로를 직접 지정
   ```

   출력은 `U1`, `U2`… 번호와 시각이 붙은 사용자 입력 목록이다. 작업 중 보낸 메시지와 질문 도구의 답(`[question tool answer]`)도 같은 번호 체계에 포함된다. 답 없이 닫힌 질문은 결정으로 기록하지 않는다. 현재 세션은 `CLAUDE_CODE_SESSION_ID`(Claude Code)와 `CODEX_THREAD_ID`(Codex)로 찾고, 둘 다 있으면 로그가 가장 최근에 기록된 세션을 사용한다. 둘 다 없으면 현재 디렉터리의 최신 Codex 세션을 사용하며 경고를 출력하므로, 첫 메시지가 이 작업과 맞는지 확인한다. 잘린 메시지가 인용에 필요하면 `--max-chars 0`으로 다시 읽는다. 로그를 찾지 못하거나 스크립트가 경고와 함께 종료되면 대화 기억으로 작성하되 §1에 "원문 미확인"을 명시한다.
3. **이전 핸드오프를 확인한다.** 이 세션이 다른 핸드오프에서 시작했는지는 사용자 입력에 언급된 핸드오프 경로로 판단한다. 경로가 없으면 프로젝트 폴더의 `handoffs/`에서 같은 작업의 최신 문서를 찾고, 특정할 수 없으면 "이전 핸드오프: 미확인"으로 쓴다. 이전 문서가 있으면:
   - 이전 문서는 수정하지 않고 새 파일을 만든다.
   - 최초 의도는 이전 문서의 §1-1을 그대로 승계한다. 새 세션의 첫 메시지를 최초 의도로 쓰지 않는다.
   - 결정 목록은 이전 문서의 행을 출처 표기 그대로 옮기고 번호를 이어서 붙인다. 재개 메시지에 "이어서, 이번엔 X도"처럼 새 지시가 있으면 다음 번호의 결정으로 기록한다.
4. **상태의 근거를 모은다.** 해당하는 것만 확인한다: 브랜치·커밋·미커밋 변경, 마지막으로 실행한 검사와 결과, 산출물 경로, 세션 종속 자원과 외부 변경(§3-1).
5. **문서를 작성하고 저장한다.** 아래 구조를 따른다. 저장 위치는 사용자가 지정한 경로, 없으면 프로젝트 폴더의 `handoffs/`이다. 프로젝트 폴더가 연결된 git worktree 안이면(`git rev-parse --git-dir`와 `--git-common-dir`의 결과가 다르고 submodule이 아닌 경우) 주 체크아웃의 루트(`git rev-parse --path-format=absolute --git-common-dir`의 상위 디렉터리)를 사용해 worktree를 지워도 문서가 남게 한다. 파일명은 `YYYY-MM-DD-<작업-슬러그>.md`로 하고, 같은 이름이 있으면 `-2`, `-3`을 붙인다. `.gitignore`와 커밋 여부는 이 스킬이 바꾸지 않는다.
6. **콜드리드로 검증한다.** 아래 "콜드리드 검증"을 수행하고 드러난 빈틈을 문서에 보완한다.
7. **사용자에게 경로와 재개 문장을 전달한다.** 새 세션에 그대로 붙여 넣을 한 줄을 절대 경로로 함께 준다. 예: `/Users/me/project/app/handoffs/2026-09-27-login-fix.md 읽고 §0부터 이어서 진행해 줘.`

## 문서 구조

```markdown
# <작업 이름> · 핸드오프

작성: <YYYY-MM-DD HH:MM 시간대> · 세션 <id> · 프로젝트 폴더: <경로> · 이전 핸드오프: <경로 | 없음 | 미확인>

## 0. 재개 방법
- 첫 행동: <새 세션이 가장 먼저 할 일 1~3개, 순서대로>
- 다시 하지 말 것: <끝난 조사와 결론의 위치, 사용자가 기각한 대안(D번호)>
- 상태 확인: <핸드오프 이후 달라졌는지 확인하는 명령. 예: git status, 마지막 검사 명령>

## 1. 사용자 의도
### 1-1. 최초 의도
<사용자 원문 인용 (출처)>. 인용이 길면 핵심 문장만 인용하고 나머지는 요지로 쓴다.

### 1-2. 작업 중 결정
| # | 결정 | 사용자 원문 (출처) | 계기 |
|---|---|---|---|
| D1 | <결정된 내용 자체> | "<원문>" (00ab706b:U3) | <무엇에 대한 답인지> |

- 출처는 `<세션 ID 앞 8자리>:U번호`로 쓴다. 세션마다 U번호가 1부터 다시 시작하므로 승계한 행과 새 행을 구분하기 위해서다.
- "추천안대로", "2번으로" 같은 답은 가리키는 내용을 풀어서 결정 칸에 쓴다.
- 사용자가 대안을 기각했으면 "X를 하지 않는다"를 결정으로 쓰고 이유를 계기 칸에 남긴다. AI 추천과 다른 선택지를 골랐으면 고른 내용을 결정으로 쓰고, 계기 칸에 "AI 추천: <추천안>"을 남긴다.
- 앞선 결정을 바꾼 경우 결정 칸에 "D1 대체"를 적고 D1은 지우지 않는다.

### 1-3. 최종 의도
1-1과 1-2를 종합한 현재 시점의 의도. 1-1·1-2에 근거가 없는 내용을 추가하지 않는다.

## 2. AI 기획
### 2-1. 핵심 포인트
AI가 제안·설계한 내용의 요점과 그 이유.

### 2-2. 최종 기획
현재 따르고 있는 기획. 항목별로 상태를 표시한다: 승인(D번호) / 미승인·보고함 / 미승인·보고 안 함.

## 3. 현재 상태
- 완료: <항목 · 근거(커밋, 검사 결과, 파일 경로)>
- 진행 중: <핸드오프 직전 작업 · 어디까지 했는지>
- 미착수: <항목>

### 3-1. 세션 종속 자원과 외부 변경
- 세션이 끝나면 사라지는 것: <scratchpad·/tmp 파일, 세션 한정 설정>
- 세션 밖에서 계속 동작하는 것: <백그라운드 작업, 예약 작업·반복 실행, 임시 worktree>
- 외부에 이미 반영한 것: <발송한 메시지, PR, 배포, 외부 문서 수정>

## 4. 문제점
- <증상> · 근거: <오류 메시지, 명령과 결과> · 원인: <확인됨: … | 가설: …>

## 5. 미결 사항
사용자 결정을 기다리는 질문, 확인하지 못한 사실.
```

해당 내용이 없는 절은 "없음"으로 남긴다. 각 절은 다음 세션이 판단에 쓰는 정보만 담고, 작업 로그나 대화 흐름을 시간순으로 옮기지 않는다. 사라질 자료 중 다음 세션에 필요한 내용은 본문에 옮기거나 `handoffs/` 아래로 복사하고 새 경로를 적는다.

## 콜드리드 검증

이 세션의 맥락이 없는 새 서브에이전트에게 저장한 문서 경로만 전달하고, 문서만 읽고 다음 질문에 답하게 한다. 문서에 없는 내용은 추측하지 말고 "문서에 없음"으로 답하도록 지시한다.

1. 사용자가 최종적으로 원하는 것은 무엇인가?
2. 새 세션이 가장 먼저 할 일은 무엇인가?
3. 다시 하지 말아야 할 것은 무엇이며 이유는 무엇인가?
4. 사용자 결정을 기다리는 사항은 무엇인가?
5. 현재 상태의 근거는 어디에서 확인하는가?

답이 이 세션의 사실과 다르거나 "문서에 없음"인 항목만 문서에 보완한다. 재검증은 보완 범위가 컸을 때 한 번만 한다. 서브에이전트를 사용할 수 없으면 검증을 생략하고 사용자에게 생략 사실을 알린다.
