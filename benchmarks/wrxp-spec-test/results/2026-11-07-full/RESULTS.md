# wrxp vs pstack 확장 실측 (2026-11-07)

부서별 대화형 시나리오를 15개로 늘리고 반복을 4회로 올렸습니다. pstack을 비교 대상에 넣었고, 공신력 있는 최신 에이전트 벤치마크 3종을 붙였습니다.

- **모델:** 모든 조건에서 claude-opus-5-5(Claude Code 2.1.318)를 썼습니다.
- **대상 버전:** wrxp 0.1.78, pstack(`michael-denyer/pstack-claude`) 0.9.132(커밋 `df9bc05`)
- **비용:** 벤치마크 실행비 약 545달러입니다. 채점자 호출과 중단된 실행까지 넣으면 약 560달러로 추정합니다. 예산은 700달러였습니다.

## 1. 부서별 대화형 시나리오 (360회)

숨은 의도를 아는 모의 사용자(Sonnet 5.5)가 같은 세션에서 질문에 답하고 수정을 요청합니다(최대 3턴). 방법은 [이전 결과](../2026-11-06-hard/RESULTS.md)와 같습니다.

과제는 15개입니다. 앞선 5개에 10개를 더했습니다.

| 부서 | 과제 |
|---|---|
| 개발 | 주문 CSV, 쿠폰, 재고 버그, API v1→v2 이전, 리포트 성능 개선 |
| 데이터 | 이탈률, 코호트 리텐션 |
| 기획 | 로드맵 조율, RICE 우선순위 |
| 마케팅 | 재활성화 캠페인 |
| 재무 | 예산 대비 실적 |
| 법무 | 공급 계약 검토 |
| HR | 온보딩 일정 |
| CS | 환불 매크로 |
| 영업 | 견적서 |

새 과제 10개는 다음 기준을 만족합니다.
- 숨긴 테스트가 원본 fixture에서는 실패하고, 참조 해법에서는 모두 통과합니다.
- 그럴듯한 오답을 내면 테스트가 2개 이상 실패합니다.

### 해석

- **질문 tier(haq, haqq)의 효과가 표본을 늘려도 재현됐습니다.** 숨은 결정이 있는 과제(견적서, 코호트, 계약 검토, 온보딩, 내보내기, 쿠폰)에서 첫 납품 점수가 30~70%p 올랐습니다.
- **haqq가 haq보다 조금 더 좋았습니다.** 결정할 것이 많은 과제에서 차이가 났습니다(RICE 60%→100%, 캠페인 65%→90%, 내보내기 75%→100%).
- **비용 정정:** 앞선 5과제 실험에서는 "비용 변화 없음"으로 보였습니다. 15과제에서는 haq·haqq의 건당 비용이 미적용보다 약 0.4달러(약 52%) 높았고, 구간이 0을 포함하지 않습니다. 질문 한 번이 재작업 한 번을 완전히 대신하지는 못합니다. 대신 사용자의 수정 요청이 줄어듭니다.
- **pstack은 이 과제들에서 첫 납품을 올리지 못했습니다.** pstack의 라우팅 기준은 여러 파일, 설계 판단, 원인 모를 버그 같은 코드 작업입니다. 부서 업무의 숨은 의도를 묻는 동작은 거의 없었습니다(질문 답변 0.1~0.2회). `/pstack:poteto-mode`를 직접 부르면 법무 과제처럼 일부에서 올랐지만, 전체 차이는 구간 경계(0)에 걸칩니다.
- **질문으로 풀리지 않는 과제에는 차이가 없었습니다.** 재고 버그, API 이전, 성능 개선, CS 매크로가 그렇습니다. 재고 버그에서는 haq·haqq가 오히려 조금 낮았습니다.

## 2. τ²-bench (고객 응대 에이전트, Sierra Research)

retail·airline 도메인의 `test` 분할에서 고정 시드로 4과제씩 뽑았고, 조건마다 2회 실행했습니다(96회).

- **에이전트 쪽:** Claude Code를 그대로 쓰고, 도메인 도구는 MCP로 노출했습니다([tau2/tau2_mcp.py](../../tau2/tau2_mcp.py)). 시스템 프롬프트에는 τ²-bench의 에이전트 지시문과 도메인 정책을 그대로 붙였습니다.
- **사용자 쪽:** τ²-bench의 사용자 시뮬레이터 지시문과 시나리오를 그대로 쓰되, 모델은 Sonnet 5.5로 생성했습니다. 기본 사용자 모델(GPT-4.1 계열)은 이 환경에서 쓸 수 없었습니다.
- **채점:** τ²-bench의 `EnvironmentEvaluator`(DB 상태 보상)를 그대로 썼습니다. 정답 행동 재생 시 1.0, 빈 대화 시 0.0이 나오는 것을 먼저 확인했습니다. 외부 LLM 판정이 필요한 보상 요소(의미 기반 전달 확인, NL 단언)는 이 환경에서 쓸 수 없어 제외했습니다.

| 도메인 | 지표 | 미적용 | 전역만 | 전역+haq | 전역+haqq | pstack | pstack+poteto |
|---|---|---:|---:|---:|---:|---:|---:|
| airline | pass^1 | 100% | 100% | 100% | 100% | 88% | 100% |
| retail | pass^1 | 75% | 75% | 50% | 62% | 88% | 75% |
| 전체 | pass^1 | 88% | 88% | 75% | 81% | 88% | 88% |
| 전체 | pass^2 | 75% | 75% | 62% | 75% | 75% | 75% |
| 전체 | 1건 비용 | $1.02 | $1.14 | $1.10 | $1.30 | $1.41 | $1.48 |

### 해석

- 조건마다 16회라 차이는 과제 1~2개 수준입니다. 유의한 차이로 보지 않습니다.
- 실패 원인은 대부분 모의 고객이 중간에 대화를 포기하는 경우(OUT-OF-SCOPE)였습니다. 같은 과제에서 모든 조건이 같이 실패한 경우도 있었습니다(주소가 불완전한 변경 요청 등).
- haq의 retail 실패 중 하나(task 100)는 여러 품목을 한 번에 바꾸면서 최종 DB가 정답과 달라진 경우입니다. 실패 기록을 읽어 봤지만, 질문 tier 때문에 고객 응대 정책을 어겼다는 근거는 찾지 못했습니다.

## 3. SWE-bench Verified

`SWE-bench/experiments`에 공개된 4개 실행 결과에서 2~3개 실행만 해결한 문항 8개를 골랐습니다.

- **문항 구성:** 이슈 원문, 테스트 패치, FAIL_TO_PASS·PASS_TO_PASS는 공개 로그에서 재구성했습니다([swebench/](../../swebench/)).
- **검증:** 패치 없이는 미해결, 참조 패치로는 해결되는 것을 8문항 모두에서 확인했습니다.
- **실행 방식:** 에이전트는 호스트에서 코드를 고치고, `./envrun`으로 공식 Docker 이미지 안에서 테스트를 돌립니다.

**결과:** 96회 모두 해결했습니다(모든 조건 100%). 이 8문항에서 Opus 5.5는 천장이고, 조건 차이는 비용과 시간에서만 나타났습니다. 비용은 미적용 $0.32, haqq $0.46, pstack+poteto $0.49였습니다.

## 4. Terminal-Bench 2

`laude-institute/terminal-bench-2`의 과제 8개를 공식 이미지로 실행했습니다(96회, [tbench/](../../tbench/)). 카테고리는 소프트웨어 공학, 디버깅, 파일 작업, 데이터 처리, 보안, 데이터 과학, 일정 관리입니다. 테스트는 `test.sh`를 그대로 돌렸습니다.

환경 제약상 원 벤치마크와 다른 점이 있습니다.
- 컨테이너에는 네트워크가 없어 인터넷이 필요 없는 과제만 골랐습니다.
- 테스트 패키지는 오프라인 키트로 공급했습니다.

| 과제 | 미적용 | 전역만 | 전역+haq | 전역+haqq | pstack | pstack+poteto |
|---|---:|---:|---:|---:|---:|---:|
| query-optimize | 1/2 | 0/2 | 1/2 | 1/2 | 2/2 | 2/2 |
| polyglot-c-py | 1/2 | 1/2 | 1/2 | 1/2 | 1/2 | 1/2 |
| 나머지 6개 | 12/12 | 12/12 | 12/12 | 12/12 | 12/12 | 12/12 |

조건 차이는 query-optimize 하나에서만 났습니다. 이 과제의 통과 조건은 "정답 쿼리 실행 시간의 1.05배 이내"인데, 실행 당시 다른 실험(SWE-bench 채점)이 같은 4코어 머신을 쓰고 있었습니다. 부하에 따라 결과가 흔들릴 수 있어 조건 효과로 해석하지 않습니다. pstack 조건은 평균 시간이 가장 짧았습니다(71~79초, 미적용 133초).

## 종합

| 질문 | 답 |
|---|---|
| 모델 지능을 올리는가 | 아니요. SWE-bench Verified는 모든 조건이 100%였고, Terminal-Bench 2와 τ²-bench는 표본 오차 안의 차이였습니다(2차 실험의 표준 벤치마크 10종도 같은 결론). |
| 요구가 덜 정해진 실무에서 첫 결과물이 나아지는가 | **haq·haqq는 그렇습니다.** 첫 납품 +22~28%p, 수정 요청 −0.45~−0.57회. 15과제 중 10과제가 개선됐습니다. |
| pstack은 어떤가 | 코드·터미널 과제에서는 wrxp와 비슷하거나 약간 빨랐습니다. 숨은 의도가 있는 부서 업무에서는 미적용과 차이가 없었습니다. |
| 비용 | haq·haqq는 부서 업무 1건당 +0.4달러(+52%), 코드·터미널 과제 1건당 +0.10~0.17달러(+30~75%)입니다. pstack은 부서 업무 +0.2~0.3달러, 코드·터미널 +0.06~0.17달러입니다. |
| 전역 블록만 켜면 | 정확도 효과는 없고, 비용이 약간(+0.1달러) 듭니다. 앞선 실험에서 본 응답 언어 일관성 효과는 그대로 유효합니다. |

**권고:** 요구가 덜 정해진 기획·영업·HR·데이터·법무 작업에는 haqq를 씁니다. 정답이 정해진 코드 수정이나 단순 작업은 그냥 진행하는 편이 비용 면에서 낫습니다. 이번 데이터로는 wrxp와 pstack을 함께 쓸 이유를 찾지 못했습니다. wrxp는 사람의 의도를 맞추는 데, pstack은 코드 작업 절차에 초점이 있습니다.

## 한계

- **모의 사용자는 실제 사용자가 아닙니다.** 부서 시나리오와 τ²-bench 모두 Sonnet 5.5가 사용자를 연기했습니다. τ²-bench의 공식 사용자 모델과 다르므로, 수치를 공개 리더보드와 직접 비교할 수 없습니다.
- **τ²-bench 보상은 DB 상태 기준입니다.** LLM 판정 요소는 빠졌고, 과제도 8개뿐입니다.
- **SWE-bench Verified는 8문항이 모두 천장이었습니다.** 더 어려운 문항(모든 공개 실행이 실패한 문항)을 넣어야 차이를 볼 수 있습니다.
- **Terminal-Bench 2는 컨테이너 네트워크 없이 돌렸습니다.** 그래서 시스템 관리 과제는 뺐고, 성능 측정 과제는 머신 부하의 영향을 받았습니다.
- **기존 5과제의 수치가 달라졌습니다.** 이전 실험과 같은 과제지만 반복 수가 다릅니다(3→4). 그래서 내보내기 haq의 첫 납품 점수가 100%에서 75%로 바뀌는 식의 변동이 있습니다.
- **채점 신뢰도:** 부서 과제 중 로드맵 하나만 LLM 채점자를 쓰고, 나머지 14개는 숨긴 테스트로 채점합니다.
