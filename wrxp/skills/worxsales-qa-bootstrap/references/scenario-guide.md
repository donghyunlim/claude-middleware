# 시나리오 작성 규칙

이 파일은 `init_workspace.sh`가 작업 폴더의 `scenarios/GUIDE.md`로 복사합니다. 작업 폴더에 맞게 고친 내용(문서 파일 이름, 메뉴 목록)은 그 사본에 둡니다. 시나리오를 쓰거나 고치는 에이전트는 이 규칙, 공통 문서, 담당 화면 원문만 읽습니다.

## 근거 우선순위
1. 역할·권한 정리 문서(`sources/common/`): 역할, 조회 범위, 「조회만」 차단 동작. 화면 정의와 충돌하면 이 문서가 우선합니다.
2. 화면 인벤토리의 CBT 제공 범위(`sources/common_inventory/`)와 각 화면 원문의 CBT 절: 지금 CBT에서 실제로 제공하는 범위입니다.
3. 기능정의서 화면 정의(`sources/<menu>/<화면>.md`): 필드, 필수값, 검증, 오류, 수용 기준입니다.
4. 정책 확인 필요 목록과 정책 결정 DB(`sources/common_policy/`): 아직 정하지 않은 규칙은 `확정 필요(보류)`입니다. 정책 결정 DB 행은 본문보다 `[속성] 상태`와 `[속성] 결정 내용`을 먼저 봅니다.
5. 목업은 참고만 합니다. 목업과 기능정의서가 다르면 기능정의서를 따르고, 차이는 `sources/_mockups/`의 비교 기록에만 남깁니다.
- 용어사전(`sources/common_glossary/`)은 용어 뜻이 애매할 때만 찾아봅니다.
- 문서에 없는 동작을 지어내지 않습니다. 문서에 "확정 필요"로 적힌 규칙은 `policy`를 `확정 필요(보류)`로 둡니다.

## CBT 제공 범위
- 제목이 `[CBT 미제공]`, `[미제공]`, `[제거]`, `[제거 대상]`이거나 `(범위 제외)`인 화면은 시나리오를 만들지 않습니다. 그 화면으로 들어가는 진입점이 다른 제공 화면에 있었다면, 부모 화면 파일에 「진입점이 노출되지 않는다」를 확인하는 행 1건(`상태·예외`, P2)만 둡니다.
- 제공 화면 안의 일부 기능이 CBT 미제공·제거 대상이면 그 기능의 동작 행은 만들지 않고, 노출되지 않음을 확인하는 행을 화면당 최대 1건만 둡니다.
- 인벤토리가 「모든 화면에서 미제공」으로 정한 기능(2026-10 기준 예: Excel 다운로드)은 메뉴 대표 화면에서만 「진입점이 없다」 1건을 둡니다.

## 메뉴 값과 TC ID
- `menu` 값은 `scenarios/menus.json`의 목록에서 그대로 고릅니다. 목록은 기능정의서 최상위의 메뉴 페이지 제목으로 만들고, 새 메뉴가 생기면 목록에 더한 뒤 `validate.py`를 다시 돌립니다.
- TC ID는 `TC-<메뉴 2자리>-<화면 2자리>-<일련 3자리>`입니다. 메뉴 대표 화면은 화면 `00`입니다.
- 화면 정의가 없는 메뉴(예: 역할·권한 문서의 한 절이 원천인 권한 관리)는 번호를 90번대로 두고 `screen`에 그 번호를, 파일은 `scenarios/<번호>/00.json`을 씁니다.

## 출력 형식
화면 하나당 `scenarios/<menu 2자리>/<화면 2자리>.json` 하나입니다. 내용은 아래 객체의 JSON 배열이며 UTF-8, `ensure_ascii=false`로 씁니다. 이름이 `_`로 시작하는 파일(변경 기록, ID 목록)은 시나리오가 아닙니다.

| 키 | 값 |
|---|---|
| tc_id | `TC-07-08-001` |
| title | `<화면 요약> - <검증 내용>`, 60자 이내 |
| menu | `7. 고객` (menus.json의 값) |
| screen | `7-8` |
| screen_url | 원문 파일 머리의 source URL |
| role | `영업자` / `영업팀장·관리자` / `영업운영` / `권한 관리자` |
| access | `수정 가능` / `조회만` |
| services | `["JK"]`, `["AM"]`, `["JK","AM"]` (서비스 구분이 무의미하면 둘 다) |
| target | `본인 담당` / `다른 담당` / `범위 밖` / `해당 없음` |
| type | `정상` / `필수값 누락` / `형식·경계값` / `권한 거부` / `조회만 차단` / `상태·예외` / `이동·복귀` |
| precondition | 사전조건(역할 선택, 대상 데이터 상태) |
| steps | 번호 붙인 절차, 줄바꿈 구분. 화면에 보이는 버튼·필드 이름을 「」로 그대로 씀 |
| inputs | 넣을 값. `필드=값` 줄바꿈 구분. 없으면 "" |
| omit | 비우거나 빼는 값. 없으면 "" |
| required | 이 동작의 필수 필드 목록(문자열) |
| expected | 기대결과. 관찰 가능한 결과(문구·건수·상태·버튼 활성)로 씀 |
| checkpoints | 증거 그림에 빨간 박스로 표시할 요소. 접근 가능한 이름이나 표시 문구 |
| evidence | 근거 ID와 문서. 예: `7-AC03; 7-8 ④; 역할·권한 2-1` |
| policy | `확정` / `확정 필요(보류)` / `범위 제외` |
| impl | 기본 `미확인`. 역할·권한 문서가 「정책과 다르게 개발된 곳」이나 「조회만이어도 쓰기가 막히지 않는 곳」으로 적은 동작이면 `정책과 다름` |
| priority | P0(권한·데이터 손상·핵심 흐름) / P1(일반 기능) / P2(표시·편의) |
| run_mode | `합성 데이터` / `실서버 필요` / `수동` |
| external | 실제 발송·MAGMA 요청·외부 저장이 일어나면 true |

## 행을 만드는 기준 (중복 금지)
- **입력 화면**: 정상 1건(필수값 모두 입력), 필수값마다 누락 1건, 형식·경계값(문서에 형식·길이·중복 규칙이 있을 때만), 저장 실패·취소 시 입력 유지 같은 상태·예외.
- **조회·탭 화면**: 정상 조회, 0건, 권한 없음과 실패의 구분, JK·AM 분리, 이동·복귀. 문서에 있는 필터·정렬은 의미 있는 조합만 씁니다.
- **역할 축**: 동작마다 역할·권한 문서의 규칙을 그대로 행으로 옮깁니다.
  - "본인만" 동작은 영업자·본인 담당(정상), 영업자·다른 담당(권한 거부), 영업팀장·관리자·다른 담당(문서대로 거부 또는 허용)으로 나눕니다.
  - "누구나" 동작은 영업자·다른 담당(정상) 1건으로 확인합니다.
  - 「조회만」은 그 화면에서 막아야 할 버튼마다 1건(`조회만 차단`, 기대결과에 차단 안내 문구)을 두고, 허용 동작은 1건으로 묶습니다.
  - 영업운영에 메뉴가 없으면 메뉴 대표 화면에서만 1건을 둡니다.
  - 마스킹처럼 역할별로 표시가 달라지는 항목은 역할별로 1건씩 둡니다.
- 같은 기대결과를 역할만 바꿔 반복하지 않습니다. 기대결과가 다를 때만 행을 나눕니다.
- 화면 하나에 보통 6~20건입니다. 기준이 단순한 화면은 적게 만듭니다.
- **발송·통화 행**: 받는 사람은 「사용자 본인(작업 폴더 `refresh/write_scope.json`의 `self`)」로 적습니다. 실제 고객 번호·주소나 임의로 지은 실번호를 적지 않습니다. 고객 회원에게만 보낼 수 있는 동작이면 사전조건에 그렇게 적어 둡니다(실행 단계에서 쓰기 범위 밖으로 처리됩니다).

## 처음 쓰기 (빈 작업 폴더)
1. 메뉴를 묶음으로 나눠 에이전트가 병렬로 씁니다. 각 에이전트에게 이 규칙, 공통 문서, 담당 화면 원문의 경로와 「문서에 없는 동작을 만들지 않는다」를 줍니다.
2. 작성에 참여하지 않은 검증 에이전트가 메뉴마다 무작위 표본(전체 40~50행 이상)을 원문과 대조합니다. 결과(정확·경미·오류 수)와 고친 내용을 `docs/DB_만들기.md` 이력 표에 적습니다.
3. `validate.py`가 오류 0일 때만 DB에 올립니다.

## 기존 행 고치기 (원천이 바뀐 메뉴)
이미 DB에 올라간 행에는 실행 결과가 붙어 있으므로 다시 쓰지 않고 고칩니다.
- TC ID를 바꾸거나 다시 매기지 않습니다. 뜻이 같은 행은 같은 TC ID로 필드만 고칩니다.
- 새 원천에서 더 이상 맞지 않는 행은 지우지 않고 `policy`를 `범위 제외`로 바꾸고, `expected` 앞에 `[범위 제외 <날짜>: 사유] `를 붙입니다.
- 새로 필요한 행은 그 화면의 마지막 일련번호 다음 번호로 추가합니다.
- 비교 기준은 이전 원천 스냅샷(`sources/_snapshot_<날짜>/`)과 새 원천입니다. 바뀐 부분만 반영합니다.
- 고친 메뉴마다 세 파일을 남깁니다: `scenarios/<menu>/_changes_<날짜>.md`(TC ID별 수정·범위 제외·추가와 이유), `_changed_ids_<날짜>.txt`(고치거나 추가한 TC ID), `_oos_ids_<날짜>.txt`(범위 제외로 바꾼 TC ID). 재실행 행 고르기가 이 파일을 읽습니다.
