# cloudinfra-review 0.1.38 행동 검증

검증일: 2026-09-28. 대상: 명시 호출 전용 인프라 요청 검토 스킬. 실제 업무에서 도출한 기준을 일반화했으며 아래 사례는 모두 가상 입력이다. 사내 대화 원문·개인 이름·실제 인프라 주소는 포함하지 않는다.

## 방법과 범위

- 스킬 작성 전, 스킬·이전 대화·저장소·외부 도구에 접근하지 않는 독립 서브에이전트에 외부 콜백 요청 A를 주고 실제 제출 문안을 작성하게 했다.
- 스킬 작성 후, 새 컨텍스트의 독립 서브에이전트 두 개가 A~C와 D~F를 나누어 처리했다. 전달 자료는 스킬 경로와 가상 사용자 입력뿐이며 기대 답은 전달하지 않았다. 에이전트는 스킬과 해당 참고 문서를 읽을 수 있었다.
- 호스트의 네이티브 서브에이전트가 부모의 모델 설정을 상속했다. 별도 모델 선택·하위 모델 폴백은 하지 않았다.
- 각 사례는 1회씩 실행했다. 출력 내용은 주 에이전트가 아래 관점으로 확인했다. 통계적 성능 비교·승인율·실제 담당자의 수용 여부를 측정한 것이 아니다.
- Slack 게시·클라우드 변경·실제 API 테스트는 하지 않았다. 런타임에 플러그인을 재설치해 자동 선택 여부를 관찰하는 통합 테스트도 하지 않았다.

## 작성 전 관측

입력 A의 원문:

> 이 클라우드인프라 요청을 엄격히 검토해서 제출할 문안으로 손봐줘. 급하니 질문으로 멈추지 말고 일단 완성해줘. DEV의 atlas-backend를 그대로 쓰며 PartnerBridge가 통화 결과를 HTTPS POST와 고정 API Key로 보냅니다. atlas-openapi.dev.example.com 도메인과 인증서, 연동 API만 허용하는 라우팅을 내일까지 구성해 주세요. 외부 IP와 실제 API 경로는 아직 개발팀이 못 정했습니다. 필요하면 표준 ALB/CF/WAF를 알아서 잡아주세요.

스킬 없는 응답은 경로·IP 미정과 전체 경로 임시 개방의 문제를 인식했고, 불필요한 ALB/CF/WAF 동시 도입을 피했다. 따라서 이러한 기본 판단이 새 스킬만으로 생겼다고 주장하지 않는다.

그러나 제출 문안에는 다음 문장이 있었다.

> 내일까지 도메인·인증서 구성과 가능한 인프라 준비 작업을 진행해 주세요.

현재 구조·도메인 정책·준비 상태가 없는 상황에서 전체 완료 희망일을 특정 하위 작업의 수행 요청으로 재배정했다. 스킬은 **검토 문의와 작업 준비 상태**, **희망 일정과 실행 확약**, **요청자 정보와 담당팀 결정**을 명시적으로 구분하도록 작성했다.

## 정적·구조 검사

기존 실행기를 사용했다.

```sh
python3 wrxp/skills/test-runner/scripts/run_tests.py --cwd "$PWD" --timeout 120 -- \
  python3 -m unittest discover -s wrxp/tests -p test_wrxp_invariants.py -v
```

원문 결과:

```text
Ran 33 tests in 0.011s

OK
```

프로세스 종료 코드: 0. 신규 검사 2개는 Claude/Codex의 명시 호출 제한 설정과 기존 스킬·공유 규칙·훅에 자동 연결이 없는지를 확인한다. 나머지는 기존 패키징·버전·파이프라인 불변조건이다. 사용자에게 제공하는 검토 판단의 정확성은 이 테스트 수로 증명하지 않는다.

기본 `quick_validate.py`는 Claude 전용 frontmatter인 `disable-model-invocation`을 허용 목록에 포함하지 않아 실제 파일에 대해 종료 코드 1을 반환했다. 이 필드는 기존 wrxp 스킬과 같은 Claude 확장이므로 원본에서 제거하지 않았다. 실제 파일의 Claude 확장과 Codex `agents/openai.yaml`을 별도로 확인하고, 확장 필드만 제거한 임시 복사본에 공통 검증기를 적용해 종료 코드 0(`Skill is valid!`)을 확인했다. 단순히 원본 전체가 이 검증기를 통과했다고 보고하지 않는다.

`git diff --check`는 종료 코드 0이었다. 해당 검사는 미추적 새 파일의 내용 검토나 실제 플러그인 설치를 대신하지 않는다.

## 추가 검증: Jenkins와 GitLab CI의 병존

사용자가 두 경로가 병존하며 GitLab CI가 최초 도입 단계라고 보충했다. 최초 6개 시나리오는 이 배포 전환 범위를 직접 검증하지 않았으므로 별도로 확인했다.

보완 전 스킬에 J와 M을 먼저 적용했다. 기존의 일반 원칙만으로도 J는 Jenkins 경로의 조사 요청으로, M은 실제 배포 검증 전 전환 완료/Job 중지가 부적절한 검토 문의로 처리됐다. 따라서 기존 스킬이 두 방식을 혼동하는 실패가 재현됐다고 주장하지 않는다.

다만 기존 참고 문서에는 환경별 현재 경로, CI와 실행기/CD의 구분, 중복 실행 방지, 전환·복구·기존 Job 종료 조건이 명시되어 있지 않았다. 이 범위를 `references/deployment-paths.md`로 추가하고, 스킬 본문에서 배포 요청일 때 읽도록 연결했다. 두 방식의 예시도 추가했다.

새 컨텍스트의 서브에이전트 두 개에 보완된 스킬과 아래 가상 입력만 전달했다. J/M은 보완 전과 같은 입력이며 G/U는 추가 범위다. 각각 1회 실행했고 외부 조회·게시·배포는 하지 않았다.

실제 응답 발췌:

- J: “지난주 다른 팀의 GitLab CI 안내만으로 이번 요청에 신규 CI 전환을 선행 조건으로 붙일 근거는 없습니다.”
- M: “현재 상태는 DEV 시범 검증 중입니다.” / “중복 실행 방지·복구 방법·기존 Job 보존 및 중지 조건을 합의해 주세요.”

4개 추가 시나리오에서 의도한 판정을 관측했다. 이번 보완은 Markdown 지침·예시·참조 연결이며 명시 호출 메타데이터·테스트 코드·버전 값은 바꾸지 않았다. 앞서 통과한 33개 구조 검사는 반복하지 않았고, 변경 후 스킬의 로컬 참조 5개가 실제 파일로 연결되는 것을 확인했다. 합계 10개 가상 시나리오의 관측이며 실제 Jenkins/GitLab 배포 성공이나 두 런타임의 모든 판단을 보증하지 않는다.

## 아직 검증하지 않은 것

- 플러그인 업데이트 후 실제 Codex/Claude UI의 목록 표시와 명시 호출 동작.
- 조직별 최신 정책·신청 도구·인프라 구성과의 적합성.
- 실제 요청의 승인율·응답 시간·핑퐁 감소량.
- 반복 실행에 따른 변동성, 모델별 성능 차이, 접근할 수 없는 긴 스레드의 실제 도구 처리.
