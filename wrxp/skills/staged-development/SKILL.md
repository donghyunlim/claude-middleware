# Staged Development

사용자와 합의한 기획서를 정본으로 유지하며 아웃라인 → 핵심 구현 → 상세 개발 순서로 진행한다. 현재 단계에서 허용된 범위를 완수하고, 다음 단계의 전환 조건을 확인한다. 사용자의 최신 지시와 이미 확인된 합의·위임을 재사용한다.

## 시작과 적용 범위

- 대화, 지정된 기획서, 관련 코드에서 이미 확인된 내용을 먼저 파악한다. 저장소 전체 조사나 모든 스킬의 선행 실행을 요구하지 않는다.
- 규모뿐 아니라 사용자 판단의 필요성, 불확실성, 오판의 재작업 비용으로 적용한다. 명세가 확정된 반복 수정은 변경 규칙·예외·검증 범위를 짧게 정한 뒤 처리한다. 단순하고 영향이 작은 수정은 기획서와 단계 승인을 생략한다.
- 원인 불명 버그의 첫 단계는 기대 동작·재현·원인을 구분하는 최소 실험이다. 작은 수정으로 해결되면 별도의 상세 개발 단계를 만들지 않는다.
- 사용자가 지정한 기존 기획서를 정본으로 재사용한다. 없다면 프로젝트 관례에 맞춰 작업별 `docs/plans/<task>.md`를 만든다. 파일 작성이 허용되지 않는 모드에서는 대화에 초안을 제시하고, 작성 가능한 시점에 저장한다.

## 정본 기획서

아래 정보를 한 문서에 짧게 유지한다. 새 템플릿·회의록·계획 파일을 단계마다 추가하지 않는다.

| 구분 | 기록할 내용 |
|---|---|
| 합의된 의도 | 목적, 대표 사용 상황, 이번 범위와 제외 범위 |
| 성공 조건 | 사용자에게 관찰되는 동작과 구체적인 입력·기대 결과; 필요한 핵심 불변조건 |
| 결정과 질문 | 합의된 결정과 근거가 되는 사용자 답변, 미해결 질문, 아직 승인되지 않은 변경 제안 |
| 실행 상태 | 현재 단계, 자율 진행 범위, 다음 검토물, 검토 주체, 작업 상한 또는 재상담 조건 |
| 검증 근거 | 성공 조건별 확인 결과, 테스트·시연·실험 근거, 미검증 사항과 가짜 데이터의 한계 |

진행 상태와 검증 근거는 에이전트가 갱신한다. 사용자에게 중요한 목적·범위·성공 조건 변경은 제안으로 기록하고 합의한 뒤 반영한다. 사용자가 미리 위임한 결정은 그 범위 안에서 처리하고 근거를 남긴다. 구현이나 테스트가 통과했다는 이유로 합의된 조건을 완화하거나, 가정을 사용자 결정으로 기록하지 않는다.

작업 시작·재개, 단계 전환, 중요한 변경 시 정본을 확인한다. 현재 대화의 새 합의가 오래된 문서보다 우선하며, 그 근거와 함께 문서를 갱신한다. 매 도구 호출마다 읽거나 작업 로그를 전부 옮기지 않는다.

## 1. 아웃라인과 핵심 가정

짧은 초안을 먼저 제시한다. 결과를 바꿀 사용자 소유 결정만 한 번에 보통 1~3개 묻고, 추천안·이유·선택의 영향을 함께 설명한다. 코드나 문서에서 확인할 사실은 제한된 조사로 해결한다. 기능 요청을 받았다는 사실만으로 미정인 사용 흐름까지 합의됐다고 보지 않는다.

틀리면 설계나 범위를 크게 바꾸는 가정을 가장 작은 실험으로 확인한다. 화면 흐름·대표 데이터·입력과 기대 결과·실제 연동 제약 중 해당 가정을 판별할 근거를 고른다. 성공 예시와 함께 가정을 깨뜨릴 사례도 확인한다. 목업은 실제 연동의 증거가 아니며, 작은 실험으로 제품 전체가 입증됐다고 표현하지 않는다.

**전환:** 방향과 성공 조건에 대한 사용자 합의가 있고, 중요한 미결정 사항이 해결되었거나 다음 단계에서 확인할 범위가 합의되면 2단계로 간다. 기존 대화나 기획서에 충분한 합의가 있으면 다시 승인받지 않는다. 아웃라인을 완벽하게 다듬기 위해 상세 설계를 선행하지 않는다.

## 2. 핵심 흐름 구현과 검토

대표 입력에서 사용자가 보는 결과까지 이어지는 최소 흐름 하나를 실제로 연결한다. 공통 기반 전체를 만드는 것으로 핵심 구현을 대신하지 않는다. 권한·데이터 보존·중복 처리처럼 설계를 좌우하는 불변조건과 핵심 실패 경로는 이 단계부터 검증한다.

정본의 성공 조건과 실제 결과를 대조하고 근거를 보여준다. 합의된 기대 결과로 판정할 수 있고 자동 검토가 위임된 항목은 자동으로 검토한다. 새로운 UI나 업무 흐름의 첫 실물은 사용자가 확인하는 것을 기본으로 하되, 명시적으로 위임된 검토는 반복 승인 없이 수행한다.

**전환:** 핵심 흐름과 초기 불변조건이 확인되고, 필요한 사용자 검토 또는 위임된 자동 검토가 끝났을 때 3단계로 간다. 의도·범위·핵심 설계가 달라져야 한다면 해당 부분의 상담으로 돌아간다. 에이전트의 자신감이나 테스트 개수는 전환 근거가 아니다.

## 3. 상세 개발과 검증

합의된 범위 안에서 세부 동작, 예외 처리, 필요한 회귀 방지를 자율적으로 완성한다. 기대 동작이 확정된 로직은 실패하는 행동 테스트 → 최소 구현 → 정리의 TDD를 사용한다. 핵심 동작이 일찍 확정되면 2단계에서도 적용한다. 문구·여백 같은 변경에 구현을 그대로 복제하는 테스트를 강제하지 않는다.

테스트의 기대 결과는 합의된 성공 조건에서 도출한다. 구현 결과를 정답으로 삼지 않는다. 변경에 필요한 프로젝트 검사와 식별된 위험 검증이 통과하면 완료한다. 새 변경·실패·구체적인 미해결 우려 없이 검증을 반복하거나 범위를 넓히지 않는다. 완료 보고는 정본의 성공 조건별 근거와 남은 한계를 연결한다.

## 상담과 실행 경계

- 사용자 경험·업무 규칙을 대신 결정해야 하거나, 근거가 합의된 가정을 깨뜨리거나, 주요 범위·구조를 바꿔야 하거나, 작업 상한에 도달해도 판단 근거가 부족하면 상담한다.
- 각 작업 구간에서 다음 검토물과 수행 범위를 정한다. 긴 작업은 시간이나 실험 횟수 등 관찰 가능한 상한을 정하되 사용자의 기존 한도를 우선한다. 새 근거 없이 같은 시도를 반복하면 상한 전에도 재평가한다.
- 상담에는 확인한 사실, 남은 결정, 선택지와 추천 이유를 제시한다. 답이 필요한 구현은 멈춘다. 질문을 보낸 뒤 기다리는 시간이 지났거나 답이 없다는 이유로 동의로 처리하지 않는다. 답과 무관한 이미 허용된 작업만 계속한다.
- 다음 단계의 자동 진행은 합의된 위임 범위 안에서만 허용한다. 사용자의 명시적인 진행 방식 변경은 정본에 반영하고 따른다. 이 스킬은 런타임의 도구 제한이나 외부 변경 권한을 확대하지 않는다.

## 위임과 다른 스킬

서브에이전트에는 정본 경로, 해당 성공 조건, 현재 단계, 담당 파일·작업 범위와 다음 검토 지점을 전달한다. 정본의 합의 변경은 조정 에이전트가 담당하며, 작업자는 발견한 차이를 보고한다. 모델은 사용자가 선택한 모델과 런타임 가용성을 따른다. 이 절차만을 위해 모델 변경이나 대규모 병렬 위임을 강제하지 않는다.

`ha`, `cast`, `decompose`, `breakdown` 또는 다른 개발 스킬은 현재 단계에 필요한 부분에만 사용한다. 전체 파이프라인을 중첩 실행하지 않는다. 다른 스킬의 질문 생략·끝까지 실행·포괄적 테스트 지침이 사용자가 선택한 단계 경계와 충돌하면, 충돌을 밝히고 현재 합의된 범위에 맞춰 적용한다.
