## 관찰

- **드리프트 사례:** 리뷰어는 AI가 스스로 작성한 목표 문장이 사용자의 요구(팀 효용 검증)를 "미평가 명시"로 낮췄다는 점, 그리고 발행·무결성 검증으로 완료를 판정했다는 점을 드리프트로 지적했다. 로그 행 번호와 코드 위치까지 근거로 제시했다. 사용자가 이후 실제로 지적한 내용, 즉 제품을 이해하고 설명하는 부담을 AI에 맡긴다는 목적이 문서 생성·게시 작업으로 바뀌었다는 점과 방향이 같다.
- **드리프트 사례에서 놓친 점:** 재생 시점 직전의 AI 보고(상위 기획은 맞고 세부 구현만 벗어났다는 결론)를 "대체로 허용"으로 판정했다. 사용자가 다음 발화에서 직접 반박한 것이 바로 이 결론이다. 리뷰어가 사용자에게 제안한 질문도 사용자의 제안(개념 라우팅)을 실행 방식으로 좁혀 되묻는 틀에 머물렀다. 판정 기준에 "AI가 사용자의 제안을 기능 목록으로 옮긴 것"을 명시할지는 다음 버전의 개선 후보다.
- **드리프트 없던 사례:** 리뷰어는 인터뷰 결정을 U번호와 함께 재구성했다. 또 스펙 승인을 구현 착수 승인으로 확대하면 안 된다는 경계를 짚었다.
- **재생 준비에서 드러난 제약:**
  - 드리프트 사례는 이전 핸드오프를 상대 경로(`.gstack/.../checkpoints/...md`)로 언급했기 때문에, `/…/handoffs/*.md` 절대 경로만 찾는 자동 추적에서 빠졌다(`prior_handoffs: []`). 실제 사용에서는 `--handoff`로 넘겨야 한다.
  - 드리프트 없던 사례의 Claude 로그에는 승인 질문 직전의 AI 안내문이 text 블록으로 남아 있지 않았다. 그래서 `ai-state.md`는 커밋 기록을 근거로 메인이 작성했다.
- 두 번 실행해 두 번 통과했으므로 리뷰어 지시문은 수정하지 않았다.

## 한계

- 재생은 저장소 상태를 제외했다(`--no-repo-state`). 실제 사용 시에는 git 상태가 함께 전달된다.
- 두 사례만으로 오탐·미탐 비율을 말할 수 없다. 자동 실행 빈도는 배포 후 `handoffs/realign/` 건수로 확인한다.
- 제한 시간 600초는 후보별로 적용된다. 폴백이 일어나면 한 회차가 600초를 넘을 수 있다.
- 발화 영역에는 150KB 상한이 적용되지만, `ai-state.md`와 반박문에는 크기 제한이 없다.
