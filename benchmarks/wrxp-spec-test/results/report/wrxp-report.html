wrxp 효과 실측 보고서

wrxp는 모델을 더 똑똑하게 만들지 않습니다. 대신 요구가 덜 정해진 일에서 처음 넘기는 결과물이 맞을 가능성을 크게 높입니다. 그 효과는 질문 tier(haq, haqq)에서 나오고, 비용은 실행당 약 50% 늘어납니다.

실행 약 2,200회 · 실행 비용 약 850달러 · 표준 벤치마크 10종, 공개 에이전트 벤치마크 3종, 부서 시나리오 15개

+22~28%p요구가 덜 정해진 부서 업무에서 첫 납품 점수 향상(haq·haqq, 95% 구간이 0을 넘음)
0~1%haq·haqq 질문 중 이미 파일에 있던 것을 물은 비율
$1.99첫 납품 성공 1건당 비용(haqq). 미적용은 $3.21
±0표준 벤치마크와 SWE-bench Verified 정답률 차이
약 30%향상분 가운데 모의 사용자가 묻지 않은 것까지 말해 준 몫. 그래서 위 향상은 상한값입니다.

요약과 사용법

  1. 모델 능력은 그대로입니다. MMLU-Pro, GPQA Diamond, MATH-500, HumanEval, SWE-bench Verified 등에서 조건 간 차이는 표본 오차 안이었습니다. Opus 5.5가 이미 천장에 가깝습니다.
  2. 요구가 덜 정해진 실무에서는 첫 결과물이 확실히 좋아집니다. haq·haqq는 15개 부서 과제 중 10개에서 첫 납품 점수를 올렸고, 사용자의 수정 요청을 과제당 0.45~0.57회 줄였습니다.
  3. 실제 작동 방식은 "질문 몇 개와 기본값 미리 보여 주기"입니다. 직접 묻는 숨은 결정은 12~16%뿐입니다. 대신 작업 전에 "따로 말씀 없으면 이렇게 하겠다"는 목록을 보여 주고, 사용자가 그 목록을 고칩니다.
  4. 전역 CLAUDE.md 블록의 효과는 응답 언어입니다. 켠 조건은 한국어 질문에 모두 한국어로 답했습니다. 정확도 효과는 없습니다.
  5. pstack은 부서 업무에서 효과가 없었습니다. 코드·터미널 과제에서는 비슷하거나 약간 빨랐고, 보고 충실도는 유의하게 낮았습니다.

사용자가 드러낸 숨은 결정은 어디서 나왔나

조건답변이 있었던 실행실행당 드러난 결정물은 것기본값을 고친 것과잉 공개
미적용53.225%50%25%
전역만113.523%54%23%
전역+haq406.117%52%31%
전역+haqq445.824%46%30%
pstack73.339%57%4%
pstack+poteto96.419%71%10%

해석. haq·haqq가 첫 결과물을 맞히는 주된 경로는 작업 전 기본값 공개였습니다. 드러난 결정의 절반이 이 경로에서 나왔고, 직접 질문은 17~24%였습니다. 질문은 정확했습니다. 94~98%가 실제 숨은 결정을 짚었고, 파일에 이미 있는 것을 물은 경우는 거의 없었습니다.

주의. haq·haqq 실행에서 드러난 결정의 약 30%는 에이전트가 묻지도 보여 주지도 않았는데 모의 사용자가 먼저 말했습니다. "묻지 않은 세부를 먼저 알려 주지 않는다"는 지시를 Sonnet이 어긴 것입니다. 그래서 첫 납품 향상은 상한값으로 봐야 하고, 엄격한 모의 사용자로 다시 재야 합니다.

그 밖의 발견은 이렇습니다.

  • 가정 공개율은 조건 간 차이가 없습니다(68~79%). Opus 5.5는 원래 자기가 정한 값을 보고에 적습니다. wrxp는 그 시점을 결과물 앞으로 옮깁니다.
  • 보고 충실도는 pstack이 유의하게 낮았습니다(78~80%). 도구 기록에 없는 "다시 계산해 확인했다"류 주장이 많았습니다. haq·haqq(86~87%)와 미적용(91%)의 차이는 유의하지 않습니다.
  • 수정 1회 해결률은 모든 조건이 79~88%로 비슷합니다. 지적받은 뒤 고치는 능력은 모델 자체의 능력입니다.

권고

wrxp에 반영할 것

  1. 결과 틀을 산출물에서 분리합니다. 형식·길이·금지어 제약이 있는 결과물에서는 "제가 정한 것·확인한 것"을 빼거나 산출물 밖으로 옮깁니다.
  2. 같은 원인의 버그는 함께 고치고 보고하는 쪽을 기본으로 합니다. 9회 중 9회가 같은 질문으로 멈췄고, 미적용은 묻지 않고 모두 고쳤습니다.
  3. 작업 전 기본값 공개를 명시적인 강점으로 다듬습니다. 효과의 주된 경로이므로 /ha(질문 0개)에서도 쓸 수 있는지 검토할 만합니다.
  4. README의 논문 인용 수치를 실측값으로 바꿉니다. "모호한 요청 정확도 33.3%→100%" 같은 수치는 이번 실측으로 재현되지 않았습니다.

  • 요구가 덜 정해진 기획·영업·HR·데이터·법무 작업은 /haqq로 시작합니다.
  • 정답이 정해진 코드 수정은 그냥 진행합니다.
  • wrxp와 pstack을 함께 쓸 근거는 이번 데이터에 없습니다(함께 설치한 조건은 측정하지 않음).

한계와 다음 단계

  • 모의 사용자는 실제 사용자가 아닙니다. 의도를 정확히 알고, 지시를 어기고 먼저 말하기도 했습니다.
  • 판정자는 Sonnet 5.5 하나입니다. 과제별 정답지와 일부 표본만 사람이 검토했습니다.
  • τ²-bench는 DB 상태 보상만 썼습니다. 사용자 모델도 공식과 달라 리더보드와 직접 비교할 수 없습니다.
  • Terminal-Bench 2는 컨테이너 네트워크 없이 돌렸습니다. SWE-bench는 쉬운 문항만 들어갔습니다.
  • 측정하지 못한 것: 불필요한 질문 비율, 과잉 차단율, "모르겠다"는 사용자, 수정 5·10회 점검, 사람 독자의 이해도.

다음 실험(제안, 약 150~250달러)

  1. 질문받은 것과 보여 준 기본값에만 답하는 엄격한 모의 사용자로 부서 시나리오를 다시 측정합니다.
  2. 숨은 결정이 없는 쌍둥이 과제로 불필요한 질문 비율을 잽니다.
  3. 위험·안전 시나리오 각 8개로 무단 위험 행동률과 과잉 차단율을 잽니다.
  4. "모르겠다"고 답하는 사용자 조건을 추가합니다.
  5. 결과 틀을 고친 뒤 IFEval을 다시 잽니다.
